# Стек проекта глобальной стратегии

Документ фиксирует рекомендуемый технологический стек для проекта глобальной пошаговой стратегии с большой физической картой, клетками, провинциями, регионами, городами, населением, логистикой, морем, движением юнитов и запечёнными слоями карты.

Главная идея стека:

```text
Godot показывает игру.
C# считает игру.
Python готовит карту.
JSON/YAML хранят баланс.
Бинарные файлы хранят тяжёлую статическую карту.
PNG/WebP тайлы хранят запечённый визуал.
```

---

# 1. Короткий итог

Рекомендуемый стек:

```text
Игровой движок: Godot 4 .NET
Ядро игры: C#
UI / сцены / карточки / экраны: GDScript
Тяжёлые оптимизации, если понадобятся: C++ через GDExtension
Генерация карты: Python
Баланс: JSON или YAML
Статическая карта: JSON на этапе разработки, BIN для релиза
Запечённая физическая карта: PNG/WebP тайлы
ID-карта для кликов по клеткам: PNG lossless
Сохранения: JSON на этапе разработки, compressed binary для релиза
Версионность: Git + Git LFS
Основная платформа старта: Windows
Дополнительные платформы позже: Linux / macOS
```

Итоговая формула:

```text
Godot 4 .NET
+ C# core
+ GDScript UI
+ Python map pipeline
+ JSON/YAML balance
+ binary world data
+ baked map tiles
+ PNG ID-map
+ Git + LFS
```

# 2. Почему не делать всё на одном языке

Для маленькой игры можно было бы сделать всё на GDScript. Но у этого проекта другая природа:

```text
20 000+ клеток
переходы между клетками
города
население
провинции
регионы
экономика
логистика
торговля
AI
сейвы
кэши
dirty flags
запечённые слои карты
```

Поэтому лучше разделить ответственность:

| Часть проекта | Лучший инструмент |
|---|---|
| Визуал, сцены, UI | Godot + GDScript |
| Ядро симуляции | C# |
| Генерация карты | Python |
| Баланс | JSON / YAML |
| Большая статическая карта | BIN |
| Запечённая карта | PNG / WebP тайлы |
| Клики по клеткам | PNG ID-map |
| Возможные тяжёлые оптимизации | C++ GDExtension |

Главное правило:

```text
GDScript показывает и отправляет команды.
C# считает правила игры.
Python генерирует данные до запуска игры.
Godot Renderer рисует карту.
JSON/BIN хранят данные.
```

# 3. Игровой движок: Godot 4 .NET

## Почему Godot

Godot подходит для проекта, потому что:

```text
+ удобен для 2D/карточного/стратегического UI
+ не перегружен как Unreal
+ проще контролировать архитектуру
+ хорошо подходит для data-driven игры
+ можно использовать GDScript и C# вместе
+ можно делать кастомный рендер карты слоями
+ можно спокойно строить инди-проект без тяжёлой коммерческой экосистемы
```

Для нашей игры Godot будет отвечать за:

```text
отрисовку карты
загрузку тайлов
UI
панели
карточки
анимации
юнитов
маршруты
подсветку клеток
input мыши/клавиатуры
сцены
звуки
локализацию
```

## Плюсы Godot

```text
+ лёгкий движок
+ быстрый запуск проекта
+ удобная работа со сценами
+ хороший UI-инструментарий
+ можно писать на GDScript и C#
+ подходит для инди
+ можно полностью контролировать pipeline карты
+ нет необходимости писать свой движок
```

## Минусы Godot

```text
- меньше готовых решений, чем в Unity
- C# в Godot требует .NET-версию редактора
- часть документации и примеров чаще на GDScript
- большие стратегии всё равно потребуют кастомной архитектуры
- нельзя рассчитывать, что движок сам решит проблему большой карты
```

## Вывод

```text
Godot 4 .NET — хороший выбор для визуала, UI, карты и интеграции проекта.
Но ядро симуляции лучше держать отдельно от сцен Godot.
```

# 5. GDScript для UI, сцен и визуала

GDScript всё равно нужен, но не как язык всей игры.

На GDScript удобно писать:

```text
карточки клеток
окна провинций
окна регионов
панели городов
кнопки
tooltip
анимации UI
подсветку выбранной клетки
визуальные контроллеры
работу со сценами
простые эффекты
```

## Плюсы GDScript

```text
+ максимально удобен внутри Godot
+ быстро писать UI
+ быстро менять сцены
+ удобно связывать кнопки и панели
+ меньше кода для визуальных вещей
+ хорошо подходит для прототипирования экранов
```

## Минусы GDScript

```text
- хуже для большой симуляции
- слабее строгая архитектура
- хуже для больших структур данных
- больше риск размазать формулы по UI
- производительность может стать проблемой раньше
```

## Главное правило

```text
GDScript не считает экономику.
GDScript не считает население.
GDScript не считает pathfinding.
GDScript не меняет напрямую CellState.
```

GDScript делает так:

```text
Игрок нажал кнопку
↓
GDScript отправил команду в C# core
↓
C# проверил правила
↓
C# изменил состояние мира
↓
C# создал событие
↓
GDScript обновил UI
```

## Пример

```text
GDScript:
"Игрок нажал построить дорогу"

C#:
проверил условия
списал ресурсы
изменил road_level
поставил dirty flags
пересчитал movement cache
создал RoadBuiltEvent
```

## Вывод

```text
GDScript — для отображения, UI и команд.
C# — для настоящей игровой логики.
```

# 9. Баланс: JSON или YAML

Баланс лучше хранить отдельно от кода.

Плохо:

```text
if relief == "hills":
    movement_cost *= 1.25
    defense += 20
```

Хорошо:

```json
{
  "hills": {
    "movement_cost": 1.25,
    "defense_value": 20,
    "pasture_potential": 15,
    "road_cost": 1.2
  }
}
```

Код должен читать таблицы баланса и применять модификаторы.

## Плюсы data-driven баланса

```text
+ легко менять цифры
+ меньше правок кода
+ проще балансить
+ проще делать моды
+ проще сравнивать версии
+ проще документировать механику
```

## Минусы

```text
- нужна система загрузки баланса
- нужна валидация данных
- при плохой структуре JSON станет мусором
- нужно следить за версиями схем
```

## Вывод

```text
Баланс — только в данных, не вшивать в код.
```

# 10. Визуальные форматы карты

Так как карта должна быть запечённой для производительности, визуал хранится отдельно от логики.

## 10.1 Физическая карта

Форматы:

```text
PNG
WebP
```

Для красивого визуала лучше WebP, потому что он легче.

Пример:

```text
terrain_z0_x0_y0.webp
terrain_z1_x0_y0.webp
terrain_z1_x1_y0.webp
relief_z1_x0_y0.webp
water_z1_x0_y0.webp
```

## 10.2 ID-карта

ID-карта должна быть только lossless:

```text
PNG
```

Нельзя использовать:

```text
JPG
WebP lossy
любое сжатие с потерями
```

Причина:

```text
ID-карта хранит точные цвета клеток.
Если формат исказит цвет, клик попадёт не в ту клетку.
```

Схема:

```text
visual_map.webp — можно
id_map.png — обязательно lossless
```

## 10.3 Overlay

Динамические слои лучше не запекать:

```text
политический слой
население
снабжение
торговля
разорение
выделение
маршруты
```

Они рисуются в Godot поверх запечённой карты.

# 11. Карта и рендер в Godot

Карта не должна состоять из 20 000 тяжёлых Node.

Плохой вариант:

```text
20 000 клеток = 20 000 Node2D
каждая клетка сама рисует себя
каждая клетка ловит мышку
каждая клетка считает логику
```

Правильный вариант:

```text
MapRenderer рисует карту слоями.
Клетки — это данные, а не тяжёлые сцены.
```

## Слои карты

```text
MapRoot

  StaticBorderLayer
  DynamicOverlayLayer
  RouteLayer
  CityLayer
  UnitLayer
  SelectionLayer
  UILayer
```

# 12. ID-карта для кликов

Если визуальная карта запечена картинкой, Godot сам не знает, где какая клетка. Поэтому нужен технический слой выбора.

Лучший вариант для MVP:

```text
невидимая ID-карта
```

Принцип:

```text
каждая клетка на ID-карте закрашена уникальным цветом
игрок кликает по карте
координата мыши переводится в координату карты
берётся пиксель ID-карты
цвет превращается в cell_id
открывается карточка клетки
```

Пример:

```text
cell_id 1523 = RGB(0, 5, 243)
```

## Плюсы ID-карты

```text
+ очень быстро
+ не нужны тысячи CollisionPolygon
+ легко определить клетку под мышью
+ хорошо работает с запечённой картой
+ удобно для больших карт
```

## Минусы ID-карты

```text
- нужно аккуратно генерировать
- координаты visual map и id map должны идеально совпадать
- ID-карта должна быть lossless
- нужен mapping color → cell_id
```

## Вывод

```text
Для нашей игры ID-карта — лучший способ клика по клеткам на старте.
```

# 13. Сохранения

Сейв не должен хранить статическую карту.

Плохо:

```text
сохранять полигоны всех клеток
сохранять физическую карту
сохранять все статические данные
```

Правильно:

```text
игра хранит StaticWorldData
сейв хранит только изменения партии
```

## Сейв на этапе разработки

```text
save_001.json
```

Плюсы:

```text
+ легко читать
+ легко дебажить
+ можно руками проверить данные
```

Минусы:

```text
- тяжёлый
- медленный
- игрок может сломать файл
```

## Сейв для релиза

```text
save_001.bin.gz
```

Плюсы:

```text
+ быстро
+ компактно
+ лучше для релиза
+ сложнее случайно испортить
```

Минусы:

```text
- сложнее отладка
- нужна миграция версий
- нужен отдельный сериализатор
```

## Структура сейва

```text
SaveGame {
  version
  current_turn
  map_version
  world_seed

  cell_states[]
  city_states[]
  unit_states[]
  polity_states[]
  active_events[]
  market_states[]
}
```

## Обязательно

```text
version
```

Формат сейва будет меняться, поэтому нужна версия и миграции.

# 14. Нужна ли база данных

Для runtime-игры база данных не нужна.

Не нужно тащить:

```text
PostgreSQL
MySQL
SQLite как обязательную runtime-базу
```

Для одиночной стратегии лучше:

```text
статические данные = файлы
состояние партии = save-файл
баланс = JSON/YAML
```

## Когда SQLite может пригодиться

SQLite можно использовать для tools:

```text
редактор карты
редактор регионов
локальная база исторических городов
```

# 23. Главные риски стека

## Риск 1. Слишком много технологий

```text
Godot + C# + GDScript + Python + JSON + BIN + GIS
```

Это мощно, но сложнее, чем “всё на GDScript”.

Как избежать проблемы:

```text
идти по этапам
не добавлять C++ до необходимости
не делать BIN до рабочего JSON-прототипа
не строить весь мир до маленькой карты
```

---

## Риск 2. UI начнёт считать логику

Плохой путь:

```text
кнопка в UI напрямую меняет CellState
карточка сама считает еду
tooltip сам считает движение
```

Правильный путь:

```text
UI отправляет команду
core меняет состояние
core возвращает ViewModel
UI показывает результат
```

---

## Риск 3. Карта станет слишком тяжёлой

Плохой путь:

```text
одна огромная PNG
20 000 Node2D-клеток
каждая клетка ловит мышку
```

Правильный путь:

```text
тайлы
ID-map
данные отдельно
динамические overlay
юниты отдельным слоем
```

---

## Риск 4. JSON станет слишком большим

Решение:

```text
JSON на этапе разработки
BIN для релиза
```

---

## Риск 5. Оптимизация раньше времени

Не надо сразу писать C++ и бинарный формат.

Правильная последовательность:

```text
сначала рабочий JSON-прототип
потом профилирование
потом оптимизация
```

# 26. Самое важное правило

```text
C# core = правда игры
GDScript UI = отображение и команды
Python tools = генерация данных
Godot renderer = визуал
JSON/BIN = данные
```

Если соблюдать это разделение, проект можно развивать годами.

Если смешать всё вместе, проект начнёт ломаться уже на этапе добавления дорог, логистики, горных перевалов и нормального AI.
