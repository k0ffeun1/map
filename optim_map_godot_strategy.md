# Оптимизация карты в Godot для глобальной стратегии

Версия: 1.0  
Цель файла: заложить правильную архитектуру карты сразу, до появления лагов и технического долга.

---

## 0. Главная идея

Карта в глобальной стратегии должна быть разделена на две части:

```text
1. Данные карты
2. Отрисовка карты
```

Нельзя делать так, чтобы визуальные объекты были главным источником правды.

Плохая архитектура:

```text
Каждая клетка = отдельная Node2D / Area2D / Polygon2D
Каждая клетка сама хранит terrain, owner, resource, population
Каждая клетка сама рисуется, сама ловит клики, сама обновляется
```

Хорошая архитектура:

```text
MapData хранит все данные клеток
MapRenderer только рисует карту
InputController считает, куда кликнул игрок
PathfindingManager считает пути
EconomySystem считает экономику
Godot-ноды есть только там, где объектов мало: города, армии, флоты, UI
```

Главное правило:

```text
Клетка = запись в данных, а не отдельный объект сцены.
```

## 1. Какие типы карт у тебя будут

Для твоей игры лучше сразу думать не как об одной карте, а как о наборе режимов.

### 1.1. Физическая карта

Показывает:

```text
сушу
море
озёра
реки
горы
леса
пустыни
болота
равнины
побережье
```

Это основной красивый режим.

### 1.2. Политическая карта

Показывает:

```text
страны
границы государств
спорные территории
вассалов
оккупированные клетки
```

### 1.3. Экономическая карта

Показывает:

```text
доход
плодородие
торговый потенциал
ресурсы
уровень развития
производство
```

### 1.4. Культурная карта

Показывает:

```text
культуры
культурные группы
ассимиляцию
напряжение
```

### 1.5. Религиозная карта

Показывает:

```text
религии
святые места
религиозное влияние
конфессиональные конфликты
```

### 1.6. Военная карта

Показывает:

```text
армии
фронты
зоны контроля
укрепления
снабжение
маршруты движения
```

Вывод:

```text
Не надо рисовать все оверлеи одновременно.
Включай только нужный режим карты.
```

```text
ne_10m_land   — суша
```

Рекомендуемая структура источников:

```text
- профили местности
- соседство
- игровые id
```

## 3. Правильный пайплайн подготовки карты

Godot не должен быть главным редактором географии мира.

Правильный процесс:

```text
GIS-данные
↓
QGIS / Python-скрипт
↓
чистка, упрощение, проекция
↓
генерация игровых клеток
↓
экспорт game_map.json
↓
Godot загружает готовую карту
↓
Godot рисует и запускает игру
```

### 3.1. Что делать в QGIS / Python

До Godot нужно сделать:

```text
1. Упростить реальные полигоны.
2. Починить invalid geometry.
3. Удалить микроскопические острова, если они не нужны.
4. Вырезать озёра из суши.
5. Разделить мир на регионы.
6. Сгенерировать игровые клетки.
7. Посчитать соседство.
8. Посчитать центры клеток.
9. Назначить базовые профили местности.
10. Экспортировать в компактный JSON или бинарный формат.
```

### 3.2. Что делать в Godot

В Godot нужно делать:

```text
1. Загрузить готовые данные.
2. Отрисовать полигоны/тайлы.
3. Обрабатывать клики.
4. Обновлять только изменённые части.
5. Запускать игровые системы.
```

Не надо в рантайме каждый раз:

```text
- парсить тяжёлые GIS-файлы;
- генерировать все клетки мира заново;
- пересчитывать всю геометрию;
- пересобирать все границы без необходимости.
```

## 4. Реальные регионы и игровые клетки

Реальные административные регионы лучше использовать как контейнеры.

Пример:

```text
Испания
└── Галисия
    ├── Ла-Корунья
    ├── Сантьяго
    ├── Виго
    ├── Луго
    └── Оренсе
```

```text
Россия
└── Мордовия
    ├── Саранск
    ├── западные леса
    ├── речные равнины
    ├── восточные поля
    └── южные холмы
```

Нельзя делать так:

```text
Галисия = одна игровая клетка
Мордовия = одна игровая клетка
Техас = одна игровая клетка
Якутия = одна игровая клетка
```

Почему плохо:

```text
1. Реальные регионы сильно отличаются по размеру.
2. Европа станет слишком дробной, а Сибирь слишком огромной.
3. Геймплей будет несбалансированным.
4. Важные города и побережья потеряются.
```

Лучше:

```text
страна → реальный регион → игровые клетки → профиль местности
```

## 5. Как разбивать регионы на игровые клетки

### 5.1. Общий принцип

Клетки должны появляться из географии и геймплея.

Не так:

```text
случайно нарезал сушу на полигоны
```

А так:

```text
берег
реки
горы
города
порты
перевалы
ресурсы
исторические области
↓
по этим факторам размещаются точки клеток
↓
генерируются полигоны
```

### 5.2. Где клетки должны быть мельче

```text
побережье
устья рек
крупные реки
портовые зоны
столицы
торговые центры
горные перевалы
перешейки
острова
богатые равнины
границы крупных держав
исторически важные регионы
```

### 5.3. Где клетки должны быть крупнее

```text
пустыни
тайга
тундра
степи без городов
плотные леса без дорог
горы без перевалов
болота
внутренние слаборазвитые земли
океан
```

### 5.4. Хорошая клетка

Хорошая клетка:

```text
имеет понятный центр
по ней удобно кликнуть
не слишком узкая
не похожа на щель
имеет игровую роль
имеет логичные границы
связана с соседями
подходит для иконки ресурса/города/армии
```

Плохая клетка:

```text
очень длинный тонкий треугольник
микрополигон
клетка без центра
клетка с острыми углами
клетка, которая касается соседей только углом
клетка, которую невозможно нормально выбрать мышкой
```

## 6. Как учитывать реки

Не все реки должны резать клетки.

Раздели реки на два типа:

```text
major_river — большая река
minor_river — малая река
```

### 6.1. Большая река

Большая река может быть:

```text
границей между клетками
барьером движения
источником защиты
торговой артерией
источником плодородия
```

Данные клетки рядом с большой рекой:

```json
{
  "has_major_river": true,
  "river_side": "left",
  "river_crossing": false,
  "fertility_bonus": 0.25,
  "defense_bonus": 0.10
}
```

### 6.2. Малая река

Малая река чаще является тегом внутри клетки:

```json
{
  "has_minor_river": true,
  "fertility_bonus": 0.10
}
```

### 6.3. Устье реки

Устье реки лучше делать отдельной важной клеткой.

Почему:

```text
порт
торговля
плодородие
рыба
болота/дельта
стратегическая переправа
```

## 7. Как учитывать озёра

Озёра нельзя просто игнорировать.

Варианты:

### 7.1. Маленькое озеро

```text
Остаётся внутри сухопутной клетки как тег.
```

Пример:

```json
{
  "has_lake": true,
  "lake_size": "small"
}
```

### 7.2. Среднее озеро

```text
Вырезается из суши, но не обязательно становится отдельной игровой клеткой.
Соседние клетки получают тег lake_shore.
```

### 7.3. Большое озеро

```text
Становится отдельной водной клеткой.
```

Пример:

```json
{
  "terrain": "lake",
  "is_water": true,
  "allows_ships": true,
  "resource": "fish"
}
```

---

## 8. Как учитывать побережье

Побережье — один из самых важных слоёв.

У каждой береговой клетки должны быть признаки:

```json
{
  "is_coastal": true,
  "coast_type": "bay",
  "port_potential": true,
  "sea_neighbors": ["sea_bay_001"]
}
```

Типы побережья:

```text
bay          — бухта
cliff        — скалистый берег
delta        — дельта
beach        — пологий берег
fjord        — фьорд
strait       — пролив
peninsula    — полуостров
island       — остров
```

Правила:

```text
важная бухта = отдельная клетка
порт = отдельная клетка
устье реки = отдельная клетка
пролив = отдельная стратегическая зона
длинный пустой берег = крупная клетка
маленький остров = одна клетка
большой остров = несколько клеток
```

## 9. Структура данных карты

### 9.1. Главный файл

Лучше иметь не кучу разрозненных файлов в Godot, а один собранный файл:

```text
game_map.json
```

Или позже:

```text
game_map.bin
```

Для прототипа JSON удобнее.

### 9.2. Структура клетки

```json
{
  "id": "esp_galicia_001",
  "name": "Ла-Корунья",
  "country_id": "ESP",
  "admin_region_id": "ESP_GALICIA",
  "polygon": [[1200, 540], [1260, 555], [1280, 610], [1225, 650]],
  "center": [1240, 590],

  "is_land": true,
  "is_water": false,
  "is_coastal": true,

  "terrain": "coastal_hills",
  "biome": "temperate",
  "elevation": 0.35,
  "humidity": 0.65,
  "temperature": 0.55,
  "fertility": 0.55,
  "forest": 0.40,

  "has_major_river": false,
  "has_minor_river": true,
  "has_lake": false,

  "resource": "fish",
  "port_potential": true,

  "movement_cost": 1.3,
  "defense_bonus": 0.15,

  "neighbors": ["esp_galicia_002", "esp_galicia_003"],
  "sea_neighbors": ["sea_biscay_004"],

  "owner_id": "CAS",
  "culture_id": "galician",
  "religion_id": "catholic",
  "city_id": "city_la_coruna"
}
```

### 9.3. В Godot данные лучше хранить не как Dictionary на каждую клетку

Для прототипа можно использовать Dictionary.  
Но для большой карты лучше перейти к массивам.

Плохо для большой карты:

```gdscript
var cells = {
    Vector2i(10, 20): {
        "terrain": "plains",
        "owner": "france",
        "resource": "grain"
    }
}
```

Лучше:

```gdscript
var terrain: PackedInt32Array
var owner: PackedInt32Array
var resource: PackedInt32Array
var population: PackedInt32Array
var fertility: PackedFloat32Array
```

Плюсы:

```text
быстрее доступ
меньше памяти
проще сохранение
проще массовые расчёты
```

## 11. Что рисовать через TileMapLayer, а что нет

### 11.1. TileMapLayer подходит для

```text
квадратных тайлов
гексагональных тайлов
регулярной сетки
фоновой физической подложки
текстурных слоёв
тумана войны по сетке
режимов карты по сетке
```

### 11.2. TileMapLayer плохо подходит для

```text
неровных Voronoi-клеток
реальных административных полигонов
сложных границ регионов
рек как кривых линий
границ государств
```

### 11.3. Для твоих неровных клеток лучше

```text
MapData хранит polygon points
CellFillRenderer рисует заливку
CellBorderRenderer рисует границы
SelectionRenderer рисует подсветку
```

То есть игровые клетки лучше рисовать полигонами или мешами, а не тайлами.

### 11.4. Где всё-таки использовать TileMapLayer

```text
туман войны, если он сеточный
декоративные текстуры земли
мелкие паттерны леса/пустыни
режимы карты, если ты переведёшь мир в растровую сетку
```

## 13. Главная оптимизация: не обновлять всю карту

Нельзя делать так:

```gdscript
func _process(delta):
    for cell in all_cells:
        update_cell_visual(cell)
```

Правильно:

```text
обновлять карту только когда что-то изменилось
обновлять только изменённые клетки
```

### 13.1. Dirty cells

```gdscript
var dirty_cells: Array[int] = []

func mark_cell_dirty(cell_id: int) -> void:
    if not dirty_cells.has(cell_id):
        dirty_cells.append(cell_id)

func update_dirty_cells() -> void:
    for cell_id in dirty_cells:
        update_cell_visual(cell_id)
    dirty_cells.clear()
```

### 13.2. Когда помечать клетку dirty

```text
поменялся владелец
поменялся режим карты
изменилась видимость
появился пожар/событие/осада
построено здание
изменилась культура/религия
выбран другой юнит
```

### 13.3. Что нельзя делать

```text
каждый кадр перерисовывать все клетки
каждый кадр пересчитывать границы всех стран
каждый кадр пересчитывать туман войны всего мира
каждый кадр искать путь для всех юнитов
каждый кадр обновлять все надписи городов
```

## 14. Чанки

Даже если визуально карта состоит из полигонов, внутренне её удобно делить на чанки.

Пример:

```text
1 chunk = 64×64 условных координат карты
или
1 chunk = набор клеток в регионе/квадрате
```

### 14.1. Зачем нужны чанки

```text
быстро понять, что видно на экране
обновлять только часть карты
сохранять только изменённые части
ускорить поиск клетки под мышью
ускорить поиск соседних объектов
ускорить рендер больших карт
```

### 14.2. Данные чанка

```json
{
  "id": "chunk_12_08",
  "bounds": [1200, 800, 1600, 1200],
  "cell_ids": [101, 102, 103],
  "city_ids": ["city_1", "city_2"],
  "unit_ids": ["army_4"]
}
```

### 14.3. Что делать по чанкам

```text
отрисовка
выбор мышью
туман войны
подсветка
сохранение
поиск объектов
```

## 15. Spatial index для клика по клетке

Если у тебя 50 000 клеток, нельзя при каждом клике проверять все полигоны.

Плохо:

```gdscript
for cell in all_cells:
    if point_inside_polygon(mouse_pos, cell.polygon):
        return cell
```

Правильно:

```text
1. Определить чанк под мышью.
2. Проверить только клетки этого чанка.
3. Сделать point_inside_polygon только для 5–30 кандидатов.
```

Пример:

```gdscript
func get_cell_under_mouse(mouse_pos: Vector2) -> int:
    var chunk_id = chunk_index.get_chunk_at(mouse_pos)
    var candidates = chunk_index.get_cells_in_chunk(chunk_id)

    for cell_id in candidates:
        if Geometry2D.is_point_in_polygon(mouse_pos, map_data.cell_polygons[cell_id]):
            return cell_id

    return -1
```

## 16. Отрисовка полигонов

### 16.1. Простой прототип

Можно сделать один Node2D и рисовать через `_draw()`:

```gdscript
extends Node2D

var visible_cells: Array[int] = []

func _draw() -> void:
    for cell_id in visible_cells:
        var points = map_data.cell_polygons[cell_id]
        var color = get_cell_color(cell_id)
        draw_colored_polygon(points, color)

    for cell_id in visible_cells:
        var line = map_data.cell_polygons[cell_id].duplicate()
        line.append(line[0])
        draw_polyline(line, Color(0.15, 0.12, 0.08, 0.35), 1.5)
```

Минус:

```text
если клеток очень много, один огромный draw может стать тяжёлым
```

### 16.2. Лучше для большой карты

Разбить отрисовку по чанкам:

```text
ChunkRenderer_0_0
ChunkRenderer_0_1
ChunkRenderer_1_0
...
```

Каждый ChunkRenderer рисует только свои клетки.

Плюсы:

```text
можно обновлять только один чанк
можно скрывать чанки вне камеры
можно кэшировать геометрию чанка
```

### 16.3. Ещё лучше

Для статичных слоёв можно заранее собрать Mesh/Polygon:

```text
terrain mesh
cell fill mesh
border mesh
country border mesh
```

И обновлять только при изменениях.

## 17. Границы клеток

Граница должна быть красивой, но дешёвой.

### 17.1. Обычная граница

```gdscript
draw_polyline(points, Color(0.02, 0.02, 0.02, 0.35), 3.0)
draw_polyline(points, Color(0.65, 0.58, 0.45, 0.45), 1.2)
```

### 17.2. Выбранная клетка

```gdscript
draw_colored_polygon(points, Color(1.0, 0.72, 0.18, 0.18))
draw_polyline(points, Color(1.0, 0.76, 0.25, 0.90), 4.0)
draw_polyline(points, Color(0.15, 0.08, 0.01, 0.70), 1.2)
```

### 17.3. Важное правило

Не рисуй одну и ту же границу дважды, если можешь этого избежать.

Проблема:

```text
клетка A рисует свою границу
клетка B рисует ту же границу
получается двойная толщина и лишняя работа
```

Лучше на этапе подготовки данных создать список рёбер:

```json
{
  "edge_id": 1001,
  "from_cell": 12,
  "to_cell": 13,
  "points": [[100, 100], [140, 120]],
  "edge_type": "normal"
}
```

Тогда границы можно рисовать один раз.

## 18. Границы стран и регионов

Границы бывают разного уровня:

```text
граница клетки
граница ADM-региона
граница государства
береговая линия
река
```

Их нельзя рисовать одинаково.

Рекомендуемые стили:

```text
граница клетки        — тонкая, мягкая
граница региона       — чуть толще
граница государства   — заметная, контрастная
береговая линия       — отдельный стиль
река                  — линия воды, не обычная граница
```

### 18.1. Когда обновлять границы стран

Только когда меняется владелец клетки.

Событие:

```text
Франция захватила клетку 102
↓
проверить соседей клетки 102
↓
обновить границы вокруг 102 и соседей
```

Нельзя:

```text
после каждого изменения пересчитывать все границы мира
```

---

## 19. Туман войны

Туман войны должен обновляться локально.

### 19.1. Статусы видимости

```text
unknown     — никогда не видел
discovered  — видел раньше, сейчас не видит
visible     — видит сейчас
```

### 19.2. Когда обновлять

```text
после движения армии
после движения флота
после постройки сторожевой башни
после изменения дипломатического доступа
после события разведки
```

### 19.3. Как обновлять

```text
1. Взять старый радиус видимости юнита.
2. Взять новый радиус видимости юнита.
3. Пометить dirty только эти клетки.
4. Обновить FogLayer только вокруг них.
```

## 20. Зум и LOD

Очень важная оптимизация для глобальной карты.

### 20.1. Дальний зум

Показывать:

```text
континенты
страны
крупные города
крупные армии
главные границы
крупные реки
```

Не показывать:

```text
мелкие ресурсы
названия всех клеток
малые города
мелкие реки
детали местности
```

### 20.2. Средний зум

Показывать:

```text
регионы
города
ресурсы
основные дороги
армии и флоты
границы клеток
```

### 20.3. Ближний зум

Показывать:

```text
названия клеток
иконки построек
мелкие ресурсы
подробные границы
локальный рельеф
```

### 20.4. Простая логика

```gdscript
func update_lod(zoom: float) -> void:
    city_labels.visible = zoom < 1.5
    resource_icons.visible = zoom < 1.2
    minor_rivers.visible = zoom < 0.9
    cell_borders.visible = zoom < 2.0
```

## 21. Иконки городов, ресурсов и юнитов

### 21.1. Города

Городов мало, их можно делать отдельными Node2D.

```text
CityIcon
CityLabel
CityBanner
```

Но не надо делать отдельные UI-панели для каждого города.

### 21.2. Ресурсы

Если ресурсов много, возможны варианты:

```text
1. Рисовать ресурс как часть CellRenderer.
2. Создавать иконки только для видимых клеток.
3. Показывать ресурсы только на среднем/ближнем зуме.
```

### 21.3. Юниты

Армии и флоты — отдельные Node2D, потому что их относительно мало.

Но нельзя:

```text
каждый солдат = отдельная Node
каждый корабль в эскадре = отдельная Node
```

Одна армия = один объект на карте.

## 22. Pathfinding

### 22.1. Нельзя считать путь постоянно

Плохо:

```text
каждый кадр считать пути для всех армий
```

Правильно:

```text
игрок навёл мышь на новую клетку → посчитать путь
игрок подтвердил приказ → сохранить маршрут
начался новый ход → выполнить шаг маршрута
```

### 22.2. Граф движения

Карта должна иметь граф:

```text
cell_id → neighbors
neighbor → movement_cost
```

Пример:

```json
{
  "cell_id": 100,
  "neighbors": [
    { "id": 101, "cost": 1.0 },
    { "id": 102, "cost": 2.5 },
    { "id": 103, "cost": 1.4 }
  ]
}
```

### 22.3. Кэш путей

Можно кэшировать:

```text
путь от армии к цели
стоимость прохода между соседями
морские маршруты
торговые маршруты
```

Но кэш надо сбрасывать при изменениях:

```text
владелец клетки изменился
дорога построена
мост разрушен
война началась
клетка стала заблокирована
```

---

## 23. ИИ и производительность

ИИ не должен думать всем миром каждый кадр.

Правильно:

```text
страны думают по очереди
сложные расчёты разбиваются на несколько кадров
далёкие страны считают упрощённо
текущие войны считают подробно
```

Пример:

```text
Кадр 1: Испания анализирует армии
Кадр 2: Франция анализирует армии
Кадр 3: Англия анализирует флот
Кадр 4: Османы анализируют экономику
```

Для пошаговой стратегии лучше вообще большую часть ИИ считать между ходами.

## 24. Сохранения

### 24.1. Не сохраняй всю карту каждый раз

Базовая карта почти не меняется.

Раздели:

```text
base_map.json       — неизменяемая география
save_game.json      — состояние партии
```

### 24.2. base_map.json

Хранит:

```text
полигоны
соседство
реки
озёра
базовый terrain
биом
базовые ресурсы
центры клеток
```

### 24.3. save_game.json

Хранит:

```text
владелец клетки
население
постройки
армии
флоты
культура
религия
видимость
текущие войны
экономика
```

### 24.4. Dirty save

При изменениях помечай:

```text
dirty_cells
dirty_countries
dirty_armies
dirty_cities
```

И сохраняй только изменённые данные.

## 25. Память

### 25.1. Опасные вещи

```text
Dictionary на каждую клетку
Node на каждую клетку
Label на каждую клетку
материал на каждую клетку
уникальная текстура на каждую клетку
слишком подробные полигоны
повторяющиеся массивы точек
```

### 25.2. Хорошие практики

```text
использовать id вместо строк
использовать PackedInt32Array / PackedFloat32Array
хранить общие справочники terrain/culture/religion
хранить полигоны отдельно от динамического состояния
использовать chunk index
использовать один материал на слой
```

Пример справочника:

```gdscript
enum Terrain {
    SEA,
    PLAINS,
    FOREST,
    HILLS,
    MOUNTAINS,
    DESERT,
    SWAMP,
    TUNDRA
}
```

В клетке хранить не `"forest"`, а `Terrain.FOREST`.

### 26.1. Не делай уникальный материал на каждую клетку

Плохо:

```text

cell_002_material
cell_003_material
...
```

Хорошо:

```text

```


Это уменьшает количество переключений текстур.

## 32. Когда переходить к более сложной системе

### 32.1. Переходить на чанки

Когда:

```text
клеток больше 5 000
клики начинают проверять слишком много полигонов
перерисовка всей карты становится заметной
```

### 32.2. Переходить на mesh-кэш

Когда:

```text
клеток больше 10 000–20 000
слои почти статичны
частая перерисовка _draw() становится дорогой
```

### 32.3. Переходить с JSON на бинарный формат

Когда:

```text
карта долго грузится
JSON стал слишком большим
сохранения стали тяжёлыми
```

## 33. Профилирование с первого дня

Оптимизация без измерений опасна.

```text

draw calls
visible cells
visible chunks
dirty cells
dirty chunks
pathfinding time
map update time
AI update time
save size
memory usage
```

### 33.1. Пример debug-счётчиков

```gdscript
var debug_visible_cells := 0
var debug_dirty_cells := 0
var debug_path_ms := 0.0
var debug_map_draw_ms := 0.0
```

### 33.2. Что считать нормой для прототипа

Для первого прототипа:

```text

```

## 34. Типичные ошибки

### Ошибка 1. Каждая клетка как Node2D

Последствия:

```text
много памяти
медленная сцена
тяжёлые клики
тяжёлые обновления
сложно сохранять
```

### Ошибка 2. Каждая клетка как Area2D с CollisionShape

Последствия:

```text
перегруз физики
сложная обработка мыши
лишняя работа движка
```

Для стратегии лучше вручную определять клетку под мышью через spatial index.

### Ошибка 3. Все слои включены всегда

Последствия:

```text
лишняя отрисовка
визуальная каша
падение FPS
```

Решение:

```text
режимы карты включают только нужные оверлеи
```

### Ошибка 4. Полная перерисовка карты каждый кадр

Решение:

```text
dirty cells
dirty chunks
event-based updates
```

### Ошибка 5. Слишком точные GIS-границы

Реальные данные часто слишком подробные.

Решение:

```text
simplify
smooth
remove tiny details
игровая деформация
```

### Ошибка 6. Слишком много текста на карте

Названия городов, областей, рек и ресурсов должны появляться по зуму.

## 35. Практический порядок разработки

### День 1–2. Данные

```text
1. Взять ne_10m_land, ne_10m_lakes, rivers.
2. Подготовить ADM1 для 2–3 стран.
3. Выбрать тестовые регионы: Галисия, Мордовия, например.
4. Упростить полигоны.
```

### День 3–4. Генерация клеток

```text
1. Внутри региона поставить seed-точки.
2. Сгенерировать Voronoi.
3. Обрезать по границе региона.
4. Удалить плохие клетки.
5. Посчитать соседство.
```

### День 5–6. Экспорт

```text
1. Экспортировать game_map.json.
2. Проверить id.
3. Проверить polygon.
4. Проверить center.
5. Проверить neighbors.
```

### День 7–8. Godot

```text
1. Загрузить game_map.json.
2. Отрисовать клетки.
3. Добавить клик по клетке.
4. Добавить selected cell.
5. Добавить hover.
```

### День 9–10. Оптимизация базы

```text
1. Добавить visible chunks.
2. Добавить dirty cells.
3. Добавить LOD по зуму.
4. Добавить debug-панель FPS/visible/dirty.
```

## 38. Самое важное резюме

Если коротко, делай так:

```text
1. Реальные GIS-данные используй как основу.
2. Реальные регионы используй как контейнеры.
3. Игровые клетки генерируй внутри регионов.
4. Клетки храни как данные, не как Node.
5. Godot должен рисовать готовые данные, а не генерировать мир каждый раз.
6. Обновляй только dirty cells / dirty chunks.
7. Используй LOD: на дальнем зуме меньше деталей.
8. Города и армии можно делать Node, клетки — нельзя.
9. Туман, границы, подсветку обновляй локально.
10. Профилируй с первого дня.
```

Главная мысль:

```text
Оптимизация карты — это не “починить лаги потом”.
Это правильная архитектура данных, рендера и обновлений с самого начала.
```

## 39. Источники и технические заметки

- Godot 4 использует `TileMapLayer` как современный подход для tilemap-слоёв; старый `TileMap` помечен как устаревший в официальной документации.
- `TileMapLayer` полезен для тайловых карт, потому что он оптимизирован для большого числа тайлов и обновляет изменения батчами в конце кадра.
- Для нерегулярных Voronoi/административных полигонов лучше использовать собственный рендер полигонов/мешей, а `TileMapLayer` оставить для тайловых/сеточных слоёв.
- Профилирование нужно вести с самого начала: FPS, draw calls, visible cells, dirty cells, время pathfinding и время обновления карты.
