# Морские клетки: структура данных и архитектура

**Проект:** глобальная историческая стратегия на Godot 4  
**Репозиторий:** `k0ffeun1/map`  
**Статус документа:** архитектурное решение для подготовки системы морских клеток  
**Область документа:** только структура морских клеток, геометрия, граф, связи и хранение данных

---

# 1. Главный вывод

Морская клетка не должна храниться одним большим JSON-объектом, в котором смешаны:

- геометрия;
- принадлежность водной территории;
- соседство;
- переходы;
- связи с сушей;
- состояние текущей партии;
- временные эффекты;
- флот;
- погода;
- ресурсы.

Правильная архитектура следует уже внедрённой в репозитории модели провинций:

```text
геометрия
≠
статический паспорт
≠
граф переходов
≠
изменяемое состояние партии
```

Логическая морская клетка собирается из нескольких записей с одинаковым стабильным ID:

```text
WaterCellGeometry
WaterCellStatic
WaterTransition
WaterLandLink
WaterCellState
```

Важно:

```text
water_cell_ids.json не создаётся на первом этапе.
Он добавляется только после стабилизации геометрии клеток.
```

# 3. Стабильный ID морской клетки

Формат ID:

```text
water_cell:<numeric_id>
```

Примеры:

```text
water_cell:0
water_cell:1
water_cell:2487
```

Не использовать ID вида:

```text
atlantic_cell_005
mediterranean_023
gibraltar_cell_1
```

Причина:

при корректировке границ клетка может быть перенесена из одной WaterArea в другую.

Например:

```text
до уточнения:
water_cell:2487 → Atlantic Ocean

после уточнения:
water_cell:2487 → Bay of Biscay
```

ID клетки не должен зависеть от:

- названия водной территории;
- текущей классификации;
- порядка клеток в массиве;
- владельца;
- сценария;
- будущего состояния партии.

---

# 4. Решение по реестру ID

## 4.1. Длинное название не использовать

Не использовать:

```text
water_cell_numeric_id_registry.json
```

Название избыточно длинное и неудобное.

Итоговое короткое имя:

```text
assets/migrations/water_cell_ids.json
```

---

## 4.2. Что должен содержать water_cell_ids.json

Файл нужен для закрепления постоянного числового ID за уже существующей морской клеткой.

Пример будущей структуры:

```json
{
  "schema_version": 1,
  "next_id": 5483,
  "ids": {
    "water_generation:seed_000001": 0,
    "water_generation:seed_000002": 1,
    "water_generation:seed_000003": 2
  }
}
```

Генератор использует его так:

```text
внутренний ключ клетки
↓
поиск в water_cell_ids.json
↓
получение постоянного numeric_id
↓
формирование ID water_cell:<numeric_id>
```

Пример:

```text
water_generation:seed_000001
↓
numeric_id = 0
↓
water_cell:0
```

---

## 4.3. Почему реестр не нужен прямо сейчас

У провинции обычно есть естественный устойчивый ключ:

```text
spain__sevilla
france__mayenne
```

У автоматически сгенерированной морской клетки такого естественного ключа нет.

Если полностью изменить:

- количество seed-точек;
- размер клеток;
- границы WaterArea;
- алгоритм Poisson sampling;
- Voronoi;
- профиль плотности;
- морскую маску;

то старая клетка может:

- исчезнуть;
- разделиться на две;
- объединиться с соседней;
- сильно изменить форму;
- сместиться;
- поменять принадлежность WaterArea.

На этом этапе трудно честно определить, какая новая клетка соответствует старой.

Поэтому реестр до стабилизации геометрии будет создавать ложное ощущение постоянства.

---

## 4.4. Утверждённое решение

### Сейчас, во время активной разработки

Генератор выдаёт ID последовательно:

```text
water_cell:0
water_cell:1
water_cell:2
...
```

При полной перегенерации водной сетки ID могут изменяться.

Это допустимо, пока:

- геометрия не утверждена;
- нет релизных сценариев;
- нет пользовательских сейвов;
- нет модов;
- нет ручных ссылок на конкретные клетки;
- нет стабильной игровой логики, завязанной на ID.

### После утверждения геометрии

Создаётся:

```text
assets/migrations/water_cell_ids.json
```

После этого:

- numeric_id больше не переиспользуются;
- удалённые ID не выдаются новым клеткам;
- новые клетки получают новые номера;
- старые ссылки можно мигрировать;
- сценарии и сейвы не ломаются от небольших изменений карты.

Итог:

```text
water_cell_ids.json — нужен позже;
на первом этапе — не создавать.
```

Пример:

```json
  "geometry_version": "2026.07.13",
  "world_px": 8192.0,
  "water_cells": [
    {
      "id": "water_cell:2487",
      "numeric_id": 2487,

      "bbox": [
        3812.54,
        2944.21,
        3894.77,
        3028.92
      ],

      "rings": [
        [
          [3820.4, 2951.2],
          [3864.7, 2944.2],
```

```text

bbox

```

Полезные дополнительные поля:

```text
label_point
navigation_point
```

## 5.2. Что не хранить в геометрическом файле

Не хранить:

```text

neighbors
transition_ids

controller
resources
weather
depth

```

Геометрический файл должен содержать только форму и геометрически вычисляемые значения.

# 6. Три центра клетки

У сложной морской клетки один центр не всегда подходит для всех задач.

Рекомендуется разделить:

```text
center
label_point
navigation_point
```

## center

Математический центроид.

Используется для:

- статистики;
- отладки;
- примерного положения;
- анализа формы.

## label_point

Точка, гарантированно находящаяся внутри полигона.

Используется для:

- подписи;
- иконки;
- маркера;
- UI.

## navigation_point

Точка для:

- маршрутов;
- позиции флота;
- расчёта расстояния;
- визуальной линии движения;
- pathfinding.

Для простой клетки точки могут совпадать.

Для пролива, бухты или изогнутой прибрежной клетки они могут отличаться.

# 8. WaterArea и WaterCell

Каждая клетка принадлежит ровно одной WaterArea:

```json
{
  "id": "water_cell:2487",
  "water_area_id": "water_area:bay_of_biscay"
}
```

Тип клетки определяется через WaterArea:

```text
WaterCell.water_area_id
↓
WaterArea.type
```

Пример:

```text
WaterArea.type = ocean
→ клетка океанская

WaterArea.type = sea
→ клетка морская

WaterArea.type = strait
→ клетка пролива
```

Отдельные структуры:

```text
OceanCell
SeaCell
StraitCell
```

не нужны.

Нужна единая структура:

```text
WaterCell
```

---

# 9. Класс плотности клетки

Тип WaterArea и размер клетки — разные вещи.

Пример классов:

```text
strategic_narrow
coastal
dense_sea
regional_sea
ocean_transition
open_ocean
remote_ocean
polar_water
```

Пример:

```text
WaterArea.type = ocean
density_class = coastal
```

Это океанская клетка возле берега.

Другой пример:

```text
WaterArea.type = sea
density_class = regional_sea
```

Это крупная центральная клетка моря.

То есть:

```text
WaterArea.type отвечает:
что это за географическая территория.

density_class отвечает:
какого размера и формы должна быть клетка.
```

# 11. Не дублировать neighbors и transitions

Не хранить одновременно в WaterCell:

```json
{
  "neighbor_water_cell_ids": [],
  "transition_ids": []
}
```

Это одни и те же связи в двух формах.

Источник истины:

```text
water_transitions.json
```

Соседство строится из переходов:

```text
для каждого перехода:
cell_a сосед cell_b
cell_b сосед cell_a
```

Runtime создаёт:

```text
adjacency[cell_index] = transition_indices
```

---

# 12. Один переход — одна двусторонняя связь

Для обычной воды:

```text
один WaterTransition = одна двусторонняя связь
```

Не создавать два объекта:

```text
A → B
B → A
```

Правильно:

```json
{
  "cell_a_id": "water_cell:100",
  "cell_b_id": "water_cell:101"
}
```

Если когда-нибудь стоимость движения станет направленной, можно добавить:

```json
{
  "cost_a_to_b": 1.0,
  "cost_b_to_a": 1.2
}
```

Но геометрическая связь остаётся одной.

---

# 13. Минимальные типы переходов

На первом этапе достаточно:

```text
open_water
restricted_passage
```

Более подробный вариант:

```text
open_water
strait
channel
canal
```

Но не стоит заранее усложнять.

Можно начать с:

```json
{
  "transition_type": "water",
  "flags": {
    "is_narrow": true,
    "crosses_water_area_border": true
  }
}
```

# 14. Связь воды с сушей

Файл:

```text
assets/map_graph/water_land_links.json
```

Пример:

```json
{
  "schema_version": 1,
  "links": [
    {
      "id": "water_land_link:10542",

      "water_cell_id": "water_cell:2487",
      "land_area_id": "province:375",

      "shared_coast_km": 21.4
    }
  ]
}
```

Позже можно добавить геометрию береговых сегментов:

```json
{
  "coast_segments": [
    [
      [3832.5, 2981.1],
      [3836.8, 2984.2],
      [3840.7, 2987.9]
    ]
  ]
}
```

---

## 14.1. Почему не хранить neighbor_land_cell_ids в клетке

Список:

```text
neighbor_land_cell_ids
```

не содержит:

- длину общего берега;
- количество отдельных береговых сегментов;
- форму берегового контакта;
- тип связи;
- возможность будущих ограничений.

Поэтому источник истины должен быть отдельным объектом:

```text
WaterLandLink
```

Runtime строит:

```text
water_to_land_links
land_to_water_links
```

# 16. Флоты не хранятся в клетке

Не хранить:

```json
{
  "fleet_ids": []
}
```

Правильно:

```text
FleetState.current_water_cell_id
```

Runtime при необходимости создаёт индекс:

```text
fleets_by_water_cell
```

Клетка не должна быть владельцем списка объектов, которые находятся внутри неё.

---

# 17. Stable ID и runtime index

Не путать:

```text
stable numeric_id
runtime array index
```

Пример:

```text
ID:
water_cell:2487

runtime index:
1872
```

Это нормально.

ID клетки не обязан совпадать:

- с порядком в JSON;
- с индексом массива;
- с номером внутри WaterArea;
- с номером seed-точки.

---

# 18. Runtime-структура

После загрузки JSON рекомендуется собрать плотные массивы:

```text
water_cell_ids
water_area_indices
bbox
centers
navigation_points
areas_km2
flags
transition_offsets
transition_indices
land_link_offsets
land_link_indices
```

Граф можно хранить в CSR-подобной форме:

```text
adjacency_offsets
adjacency_transition_indices
```

Пример:

```text
offsets:
[0, 4, 9, 12...]

transition_indices:
[7618, 7621, 7624, 7630, ...]
```

Так соседства читаются без отдельных Dictionary и без тысяч Node.

# 19. Клик и выделение клетки

Существующий `SelectedCellOverlay` уже умеет:

- принимать rings;
- заливать полигон;
- рисовать контур;
- отображать выбранную территорию.

Его можно переиспользовать для морских клеток.

Лучше со временем переименовать:

```text
SelectedCellOverlay
```

в:

```text
SelectedMapAreaOverlay
```

Тогда один класс сможет выделять:

- сухопутную клетку;
- морскую клетку;
- провинцию;
- регион;
- WaterArea.

# 20. Черновые ручные границы

`CellBoundaryDraftLayer` полезен для:

- ручной разметки входов в моря;
- задания границ проливов;
- уточнения Бискайского залива;
- коррекции Ла-Манша;
- разделения спорных WaterArea.

Но сохранённые strokes — не готовая игровая геометрия.

Правильный процесс:

```text
ручные strokes
↓
constraints генератора
↓
разрезание водной маски
↓
генерация клеток
↓
валидация
↓
итоговые полигоны
```

Не использовать:

```text
stroke = runtime-граница
```

# 22. Что утверждается окончательно

```text
1. Используется единая структура WaterCell.

2. ID клетки имеет формат water_cell:<numeric_id>.

3. ID не зависит от WaterArea, названия или порядка в массиве.

4. Геометрия хранится отдельно от паспортных данных.

5. Переходы хранятся отдельно от клетки.

6. Связи с сушей хранятся отдельно.

7. В клетке не дублируются neighbors и transition_ids.

8. Источник истины соседства — WaterTransition.

9. Источник истины связи с сушей — WaterLandLink.

10. Сценарное состояние хранится отдельно.

11. Флоты не хранятся списком внутри клетки.

12. water_cell_numeric_id_registry.json не используется.

13. Будущее имя реестра — water_cell_ids.json.

14. water_cell_ids.json не создаётся на этапе активной генерации.

15. До стабилизации геометрии ID могут полностью пересоздаваться.

16. После стабилизации геометрии ID замораживаются через water_cell_ids.json.

17. Stable ID и runtime index — разные сущности.

18. JSON используется в разработке, плотные массивы/BIN — позже для runtime.
```

# 23. Пошаговый план внедрения

## Этап 1. Схемы

Создать пустые файлы:

```text
assets/map_geometry/water_cells.json
```

# 25. Площади морских клеток и генерация

## 25.1. Целевое количество клеток мира

Рабочий диапазон:

```text
6 000–7 000 водных клеток
```

Первый целевой бюджет генератора:

```text
около 6 500 клеток
```

Это даёт:

- достаточно подробные моря и побережья;
- стратегические проливы из отдельных клеток;
- нормальное движение флотов;
- не слишком плотную сетку в центре океанов;
- приемлемый объём JSON/BIN;
- быстрый pathfinding;
- удобный клик по клеткам.

При необходимости после тестовой генерации бюджет можно изменить:

```text
слишком крупные моря и побережья → увеличить до 7 000–7 500;
слишком дробные океаны → уменьшить до 5 500–6 000.
```

---

## 25.2. Классы размеров клеток

Все водные клетки не должны иметь одинаковую площадь.

Утверждаются следующие классы:

| Класс | Целевая площадь | Допустимый диапазон | Примерный диаметр |
|---|---:|---:|---:|
| `strategic_narrow` | 1 500 км² | 300–3 500 км² | около 44 км |
| `coastal` | 6 000 км² | 3 000–10 000 км² | около 87 км |
| `dense_sea` | 12 000 км² | 7 000–20 000 км² | около 124 км |
| `regional_sea` | 25 000 км² | 15 000–40 000 км² | около 178 км |
| `ocean_transition` | 50 000 км² | 30 000–80 000 км² | около 252 км |
| `open_ocean` | 100 000 км² | 65 000–150 000 км² | около 357 км |
| `remote_ocean` | 180 000 км² | 120 000–280 000 км² | около 479 км |
| `polar_water` | 100 000 км² | 60 000–180 000 км² | около 357 км |

Важно:

```text
целевая площадь — это ориентир генератора,
а не обязательное точное значение каждой клетки.
```

Клетка может быть меньше или больше, если этого требуют:

- береговая линия;
- остров;
- архипелаг;
- пролив;
- граница WaterArea;
- узкий вход в залив;
- сложная форма акватории.

---

## 25.3. Strategic narrow

Используется для:

- Босфора;
- Дарданелл;
- Гибралтара;
- Эресунна;
- Ормуза;
- Баб-эль-Мандеба;
- узких частей Малаккского пролива;
- Суэцкого канала;
- Панамского канала;
- других стратегических горлышек.

Обычная целевая площадь:

```text
1 500 км²
```

Допустимы особые исключения:

```text
200–800 км²
```

если реальная геометрия слишком узкая.

Такая клетка может быть значительно меньше обычной морской клетки, но должна:

- быть кликабельной;
- иметь устойчивый navigation_point;
- не пересекать сушу;
- не объединять две стороны острова;
- не допускать ложного обхода пролива.

---

## 25.4. Coastal

Прибрежные клетки нужны:

- у материкового берега;
- около портов;
- возле крупных островов;
- в архипелагах;
- у устьев рек;
- у входов в моря;
- возле мысов и бухт.

Целевая площадь:

```text
6 000 км²
```

Обычно это первые:

```text
50–150 км от значимого берега
```

Но расстояние не является единственным условием.

Клетки уменьшаются также:

- около важных портов;
- возле островных групп;
- рядом с узкими проходами;
- около входов в заливы;
- в сложных участках береговой линии.

---

## 25.5. Dense sea

Используется в насыщенных морях:

- Средиземном;
- Северном;
- Балтийском;
- Чёрном;
- Красном;
- Карибском;
- Японском;
- Южно-Китайском.

Целевая площадь:

```text
12 000 км²
```

У берегов этих морей всё равно используются `coastal`.

В проливах используется `strategic_narrow`.

---

## 25.6. Regional sea

Используется:

- в центральных частях крупных морей;
- в больших заливах;
- в акваториях, где детализация всё ещё важна, но берег уже далеко.

Целевая площадь:

```text
25 000 км²
```

Примеры:

- центральное Средиземноморье;
- центральное Карибское море;
- Мексиканский залив;
- Бенгальский залив;
- Гудзонов залив;
- крупные внутренние морские бассейны.

---

## 25.7. Ocean transition

Промежуточная зона между берегом и открытым океаном.

Целевая площадь:

```text
50 000 км²
```

Обычно используется примерно на расстоянии:

```text
150–700 км от значимой суши
```

Но рядом с архипелагами клетки должны оставаться меньше.

---

## 25.8. Open ocean

Основная сетка открытого океана.

Целевая площадь:

```text
100 000 км²
```

Примерный условный диаметр:

```text
около 350 км
```

Используется в:

- Атлантическом океане;
- Индийском океане;
- большей части Тихого океана;
- удалённых частях других океанских WaterArea.

---

## 25.9. Remote ocean

Самые удалённые и пустые части океанов.

Целевая площадь:

```text
180 000 км²
```

Обычный верхний предел:

```text
250 000–280 000 км²
```

Такие клетки нельзя использовать:

- возле островов;
- возле архипелагов;
- у входов в моря;
- у проливов;
- около сложного побережья.

---

## 25.10. Плавное изменение площади

Не использовать жёсткие ступени:

```text
149 км от берега → 6 000 км²
151 км от берега → 50 000 км²
```

Размер должен увеличиваться плавно.

Пример базовой функции:

```text
0–100 км:
6 000–10 000 км²

100–300 км:
10 000–30 000 км²

300–700 км:
30 000–70 000 км²

700–1 500 км:
70 000–130 000 км²

1 500+ км:
130 000–220 000 км²
```

После базовой функции применяются поправки.

---

## 25.11. Формула целевой площади

Для каждой точки воды генератор рассчитывает:

```text
target_area =
    base_area_by_distance_to_land
    × water_area_modifier
    × strategic_modifier
    × island_modifier
    × local_complexity_modifier
```

Пример:

```text
base_area_by_distance_to_land = 50 000 км²
water_area_modifier = 0.5
island_modifier = 0.6

target_area = 50 000 × 0.5 × 0.6
            = 15 000 км²
```

Это означает:

- точка может быть далеко от материка;
- но если она находится рядом с архипелагом;
- или внутри плотного моря;
- клетки остаются небольшими.

---

## 25.12. Модификаторы типа WaterArea

Примерные множители площади:

| Тип WaterArea | Множитель площади |
|---|---:|
| `strait` | 0.10–0.30 |
| `channel` | 0.30–0.60 |
| `lagoon` | 0.20–0.50 |
| `fjord` | 0.15–0.50 |
| `bay` | 0.50–0.80 |
| `gulf` | 0.70–1.00 |
| `sea` | 0.60–1.00 |
| `ocean` | 1.00 |

Но каждая WaterArea может иметь собственный профиль.

Пример Средиземного моря:

```json
{
  "id": "water_profile:mediterranean",
  "base_multiplier": 0.65,
  "minimum_area_km2": 3000,
  "maximum_area_km2": 35000
}
```

Пример Тихого океана:

```json
{
  "id": "water_profile:pacific_ocean",
  "base_multiplier": 1.15,
  "minimum_area_km2": 6000,
  "maximum_area_km2": 260000
}
```

Одного общего правила для всех `sea` или всех `ocean` недостаточно.

---

## 25.13. Утверждённый способ генерации

Использовать гибридный constrained Voronoi.

Правильный процесс:

```text
1. Подготовить единую водную маску мира.

2. Подготовить полигоны всех WaterArea.

3. Проверить отсутствие перекрытий WaterArea.

4. Превратить границы WaterArea в обязательные линии-ограничители.

5. Построить глобальное поле target_area.

6. Расставить seed-точки методом variable-radius Poisson disk sampling.

7. Добавить обязательные стратегические seed-точки:
   - в проливах;
   - в каналах;
   - между островами;
   - около входов в моря;
   - в бухтах;
   - у важных портовых акваторий.

8. Построить общую Voronoi-сетку.

9. Обрезать полигоны:
   - по водной маске;
   - по границам WaterArea;
   - по береговой линии.

10. Исправить:
   - слишком маленькие клетки;
   - тонкие щели;
   - несвязанные MultiPolygon;
   - слишком вытянутые формы;
   - ложные связи вокруг островов.

11. Рассчитать:
   - area_km2;
   - bbox;
   - center;
   - label_point;
   - navigation_point;
   - shared_border_km;
   - соседство;
   - связи с сушей.

12. Выполнить полную валидацию.

13. Экспортировать JSON/BIN.

14. Запечь визуальные тайлы и ID-карту.
```

---

## 25.14. Почему не генерировать WaterArea полностью отдельно

Если отдельно сгенерировать:

```text
Атлантику
Бискайский залив
Ла-Манш
Северное море
```

то пограничные клетки могут не состыковаться.

Пример проблемы:

```text
граница Атлантики имеет 7 сегментов;
граница Бискайского залива имеет 11 сегментов;
между ними появляются T-стыки, щели и несовпадающие рёбра.
```

Поэтому используется:

```text
единая глобальная генерация
+
жёсткие ограничения по границам WaterArea
```

Общее ребро создаётся один раз и используется обеими территориями.

---

## 25.15. Расстановка seed-точек

Расстояние между seed-точками выводится из целевой площади:

```text
seed_spacing_km ≈ 1.05–1.15 × sqrt(target_area_km2)
```

Пример:

| Целевая площадь | Расстояние между seeds |
|---:|---:|
| 1 500 км² | около 40–45 км |
| 6 000 км² | около 80–90 км |
| 12 000 км² | около 115–125 км |
| 25 000 км² | около 165–180 км |
| 50 000 км² | около 235–255 км |
| 100 000 км² | около 330–360 км |
| 180 000 км² | около 450–500 км |

---

## 25.16. Генерация у побережья

Обычный Voronoi, просто обрезанный берегом, создаёт:

- тонкие полосы;
- щепки;
- неудобные вогнутые клетки;
- MultiPolygon;
- клетки, охватывающие две стороны острова;
- клетки с плохим центром.

Поэтому у побережья используется отдельная подготовка:

```text
1. Построить направляющую линию примерно параллельно берегу.

2. Расставить coastal-seeds вдоль побережья.

3. Добавить seeds около:
   - бухт;
   - мысов;
   - устьев рек;
   - островов;
   - портов;
   - входов в проливы.

4. Только после этого заполнять остальную воду Poisson sampling.
```

---

## 25.17. Генерация проливов

Каждый стратегический пролив получает отдельный ручной профиль.

Пример Гибралтара:

```text
WaterArea:
Strait of Gibraltar

класс:
strategic_narrow

количество клеток:
2–3

площадь одной клетки:
примерно 500–2 000 км²
```

Возможная структура:

```text
западный вход;
центральное горлышко;
восточный выход.
```

Для MVP допустимы две клетки.

Босфор может быть одной стратегической клеткой.

Главное правило:

```text
стратегическая клетка может быть меньше обычной,
но не может пересекать сушу или создавать ложный путь.
```

---

## 25.18. Ограничения формы

### Площадь

```text
min_area ≤ area ≤ max_area
```

Исключение разрешается только явно:

```json
{
  "generation_exceptions": [
    "strategic_narrow_geometry"
  ]
}
```

### Вытянутость

Примерная проверка:

```text
elongation =
maximum_internal_length /
equivalent_diameter
```

Рекомендуемые пределы:

```text
обычная клетка:
не более 2.5

пролив или фьорд:
не более 5.0
```

### Разница соседних площадей

Обычно:

```text
max(area_a, area_b) / min(area_a, area_b) ≤ 2.2
```

На особых границах допустимо:

```text
до 3.0
```

Но клетка `1 000 км²` не должна напрямую соседствовать с клеткой `180 000 км²`.

Между ними должна появляться переходная клетка.

# 24. Финальный вывод

Морская клетка должна быть не Node и не монолитный JSON-объект, а элементом общей data-driven архитектуры карты.

Правильная формула:

```text
форма клетки
+
статический паспорт
+
граф переходов
+
связи с берегом
+
состояние сценария
```

Решение по ID:

```text
пока геометрия нестабильна:
ID можно пересоздавать;

после утверждения геометрии:
water_cell_ids.json замораживает numeric_id.
```
