# Архитектура морских клеток карты

## 0. Короткий вывод

Морские клетки лучше делать не через готовую базу морей и не руками, а через отдельный офлайн-генератор:

```text
водная маска мира
↓
центры будущих морских клеток
↓
Voronoi-разбиение
↓
обрезка по воде
↓
чистка геометрии
↓
соседство клеток
↓
sea_cells.json
↓
запекание визуального слоя в tile bundle
↓
быстрый показ в Godot через BakedTileProvider
```

Главное архитектурное правило:

```text
Морские клетки генерируются офлайн.
В игре они не строятся заново.
Godot в runtime только показывает запечённый слой и использует готовые данные для клика, движения и логики.
```

---

# 1. Что именно надо получить на выходе

На первом этапе не нужны типы морей, глубины, ресурсы, рыба, штормы и торговые маршруты. Сначала нужна только **геометрия морских клеток**.

Минимальный результат генерации:

```text
sea_cells.json
```

Внутри:

```text
SeaCell {
  id
  name
  rings
  brd_open
  bbox
  center
  area_km2
  neighbor_sea_ids
  neighbor_land_ids
}
```

Где:

```text
rings              // полный полигон морской клетки
brd_open           // только внутренние морские границы, без береговой линии
bbox               // ограничивающий прямоугольник для быстрого отбора
center             // центр клетки для UI/pathfinding
area_km2           // площадь
neighbor_sea_ids   // соседние морские клетки
neighbor_land_ids  // соседние береговые сухопутные клетки
```

Важно: `rings` нужны для логики и клика, а `brd_open` — для красивой отрисовки границ без дублирования береговой линии.

---

# 2. Почему не надо делать морские клетки через API морей

Готовые базы морей полезны для названий:

```text
Бискайский залив
Северное море
Средиземное море
Атлантический океан
Балтийское море
```

Но они плохо подходят для игровых клеток.

Проблема:

```text
Атлантический океан слишком огромный.
Северное море слишком важное, чтобы быть одной клеткой.
Ла-Манш слишком маленький, но стратегически очень важный.
Средиземное море нужно делить плотнее, чем центр Тихого океана.
```

Поэтому базы морей можно добавить потом как справочник для названий, но сами клетки надо генерировать самостоятельно.

Правильная формула:

```text
Реальные моря = названия и регионы.
Игровые морские клетки = результат генератора.
```

# 3. Главная архитектура

## 3.1. Нельзя строить морские клетки в runtime

Плохо:

```text
игрок запускает игру
Godot строит Voronoi
Godot режет полигоны
Godot считает соседство
Godot рисует клетки live
```

Так делать не надо.

Хорошо:

```text
Python tool генерирует sea_cells.json
Python/Godot tool запекает визуальные тайлы
Godot runtime читает готовый JSON и готовые картинки
```

Причина:

```text
генерация клеток — тяжёлая офлайн-задача;
показ карты — лёгкая runtime-задача.
```

---

## 3.2. Разделить данные и картинку

Нужно два слоя:

```text
1. Логические данные морских клеток
2. Визуальный запечённый слой морских границ
```

Логика:

```text
assets/generated/sea_cells.json
assets/generated/sea_cell_graph.json
```

Визуал:

```text
assets/tiles_bundle/sea_cells_baked/
```

В игре:

```text
BakedTileProvider показывает картинку.
SeaCellCatalog / SeaCellIndex отвечает за выбор клетки, соседей и движение.
```

Это важно: картинка не должна быть источником правды. Источник правды — JSON с полигонами и графом соседства.

# 4. Рекомендуемая структура файлов

Лучше сразу сделать файлы с короткими и точными названиями.

```text
scripts/tools/generate_sea_cells.py
scripts/tools/bake_sea_cells.py

assets/generated/sea_cells.json
assets/generated/sea_cell_graph.json
assets/tiles_bundle/sea_cells_baked/

scripts/map/SeaCellCatalog.gd
scripts/map/SeaCellIndex.gd
scripts/map/SeaCellSelection.gd
```

Не использовать названия:

```text
sea_v2.json
new_sea_cells.json
admin_sea.json
test_sea_final.json
better_ocean_cells.py
```

Нормальные названия:

```text
generate_sea_cells.py      // генерация морских клеток
bake_sea_cells.py          // запекание слоя морских клеток
sea_cells.json             // геометрия морских клеток
sea_cell_graph.json        // соседство морских клеток
SeaCellCatalog.gd          // загрузка данных клеток
SeaCellIndex.gd            // быстрый поиск клетки под курсором
SeaCellSelection.gd        // логика выбора клетки игроком
```

# 5. Алгоритм генерации морских клеток

## 5.1. Входные данные

Нужно взять:

```text
world_polygon      // прямоугольник всей игровой карты
land_polygons      // вся суша
lake_polygons      // озёра, если их надо исключить из морей
land_cells         // будущие сухопутные клетки, если надо строить neighbor_land_ids
```

На первом этапе достаточно:

```text
world_polygon
land_polygons
```

---

## 5.2. Получить водную маску

Базовая операция:

```text
sea_mask = world_polygon - land_polygons
```

Если озёра не должны быть морскими клетками:

```text
sea_mask = world_polygon - land_polygons - lake_polygons
```

Если озёра потом будут отдельными водными клетками, их лучше вынести в другой генератор:

```text
generate_lake_cells.py
```

---

## 5.3. Расставить seed-точки

Seed-точки — это будущие центры морских клеток.

Лучший вариант:

```text
Variable Poisson Disk Sampling
```

То есть точки не должны слипаться, но расстояние между ними может меняться.

Для MVP можно проще:

```text
jittered grid
```

Схема:

```text
1. Наложить сетку на море.
2. Каждую точку слегка случайно сдвинуть.
3. Оставить только точки внутри sea_mask.
4. Чем дальше от берега, тем больше шаг сетки.
```

---

# 6. Делать ли морские клетки одинаковыми

Не стоит делать все морские клетки строго одинаковыми.

Лучше:

```text
примерно одинаковые внутри своей зоны,
но крупнее по мере удаления от берега.
```

Причина:

```text
у берега нужны десанты, порты, блокады, рыба, проливы;
в центре океана нужны маршруты, дальность и перехват, но не мелкая детализация.
```

---

## 6.1. Самый простой стартовый вариант

Для первой версии лучше использовать две плотности:

```text
coastal:
  distance_to_land < 250 км
  target_cell_size = 80–110 км

ocean:
  distance_to_land >= 250 км
  target_cell_size = 240–320 км
```

Это проще всего реализовать и проверить.

---

## 6.2. Более хороший вариант

После первой генерации можно перейти на три зоны:

```text
coastal:
  0–200 км от берега
  70–100 км

transition:
  200–700 км от берега
  130–220 км

open_ocean:
  700+ км от берега
  250–380 км
```

Не рекомендуется делать 450+ км для обычного открытого океана в первой версии, потому что клетки могут стать слишком грубыми для Атлантики.

---

## 6.3. Важное правило плавности

Плохо:

```text
до 200 км клетки маленькие,
после 200 км сразу огромные.
```

Хорошо:

```text
размер клетки плавно растёт от берега к океану.
```

Пример:

```text
distance_to_land = 50 км   -> cell_size 80 км
distance_to_land = 300 км  -> cell_size 150 км
distance_to_land = 900 км  -> cell_size 300 км
```

Ограничение:

```text
соседние клетки не должны отличаться по размеру больше чем в 1.5–2 раза.
```

Иначе карта будет выглядеть рвано.

---

# 7. Построить Voronoi

После генерации seed-точек строится Voronoi:

```text
points -> Voronoi polygons
```

Каждая точка создаёт одну будущую морскую клетку.

Важно:

```text
Voronoi надо строить в плоских игровых координатах, а не напрямую в широте/долготе.
```

Лучше использовать:

```text
координаты твоей игровой карты в пикселях/world_px
```

или проекцию, в которой уже подготовлена карта.

Плохо:

```text
lon/lat напрямую
```

Потому что на севере размеры клеток будут искажаться.

---

# 8. Обрезать клетки по воде

Voronoi создаст полигоны везде. Поэтому каждый полигон нужно обрезать:

```text
sea_cell_polygon = voronoi_polygon ∩ sea_mask
```

После обрезки остаются только морские части.

---

# 9. Почистить геометрию

После обрезки появятся плохие куски:

```text
узкие щепки;
микро-полигоны;
клетки с крошечной площадью;
мультиполигоны;
битые self-intersection геометрии;
слишком тонкие клетки вдоль берега.
```

Нужно сделать чистку:

```text
1. Исправить геометрию через buffer(0) / make_valid.
2. Удалить или присоединить клетки меньше минимальной площади.
3. Убрать слишком узкие части.
4. Разбить MultiPolygon на основной полигон или несколько клеток.
5. Сгладить/упростить точки, если их слишком много.
```

Правило для MVP:

```text
если площадь клетки < 25% от целевой площади зоны,
присоединить её к соседу с самой длинной общей границей.
```

---

# 10. Границы: что рисовать, а что не рисовать

Очень важно не дублировать береговую линию.

У сухопутных клеток уже есть правильная идея:

```text
внутренние границы рисуются клеточным слоем;
внешняя граница области рисуется отдельным слоем.
```

Для моря нужно так же:

```text
морской клеточный слой рисует только границы между морскими клетками;
береговую линию рисует отдельный слой суша/море или coastline.
```

Поэтому в `sea_cells.json` лучше хранить:

```text
rings      // полный полигон клетки
brd_open   // только sea-sea границы, без coastline
```

Плохо:

```text
морская клетка рисует свой полный контур,
а слой суши тоже рисует берег.
```

Результат:

```text
двойная грязная береговая линия;
слишком толстый берег;
визуальный шум.
```

Хорошо:

```text
coastline layer рисует берег;
sea_cells layer рисует только внутреннюю сетку моря.
```

---

# 11. Волнистость границ

Для моря границы не должны выглядеть как идеальная математическая сетка.

Можно использовать тот же принцип, что и для сухопутных клеток:

```text
обычный Voronoi
↓
внутренние рёбра слегка искажаются
↓
получаются живые неровные границы
```

Но важно:

```text
искажение общего ребра должно быть одинаковым для обеих соседних клеток.
```

То есть нельзя отдельно волновать границу каждой клетки. Нужно волновать именно общее ребро по стабильному ключу:

```text
edge_key = min(cell_a, cell_b) + max(cell_a, cell_b)
```

Тогда две соседние клетки используют одну и ту же линию.

---

# 12. Соседство клеток

После генерации надо построить граф.

## 12.1. Морская клетка — морская клетка

Две морские клетки соседи, если:

```text
они имеют общую границу достаточной длины.
```

Не считать соседями, если они касаются только точкой.

Минимальное правило:

```text
shared_border_length > min_border_length
```

---

## 12.2. Морская клетка — сухопутная клетка

Морская клетка соседствует с сухопутной, если:

```text
морская клетка касается берега рядом с сухопутной клеткой.
```

Это нужно для:

```text
портов;
десантов;
блокад;
рыболовства;
городского экрана;
торговых путей.
```

На первом этапе можно хранить просто:

```text
neighbor_land_ids
```

Потом можно уточнить:

```text
landing_allowed
coast_length
nearest_port_id
```

Но это потом.

# 13. Формат sea_cells.json

Минимальный формат:

```json
{
  "version": 1,
  "world_px": 8192,
  "cells": [
    {
      "id": "sea_000001",
      "name": "Морская клетка 1",
      "surface": "sea",
      "rings": [
        [[1200.0, 3400.0], [1260.0, 3420.0], [1290.0, 3500.0]]
      ],
      "brd_open": [
        [[1210.0, 3410.0], [1250.0, 3440.0], [1280.0, 3490.0]]
      ],
      "bbox": [1200.0, 3400.0, 1290.0, 3500.0],
      "center": [1245.0, 3450.0],
      "area_km2": 8200.0,
      "neighbor_sea_ids": ["sea_000002", "sea_000003"],
      "neighbor_land_ids": ["land_001245"]
    }
  ]
}
```

Для первой версии можно не заполнять типы:

```text
water_type
region_name
depth
resource
danger
```

Их можно добавить позже без переделки геометрии.

# 14. Отрисовка в Godot

## 14.1. В dev/debug режиме

Можно подключить `sea_cells.json` через существующий `IrregularCellProvider`:

```gdscript
var sea_cells_provider := IrregularCellProvider.new(
    "res://assets/generated/sea_cells.json",
    MAX_Z,
    {
        "border_color": Color(0.05, 0.12, 0.18, 0.35),
        "border_width": 1.0,
        "fill_alpha": 0.0,
        "raster_px": 1024,
        "dash": false
    }
)
```

Но это только для разработки и проверки.

---

## 14.2. В нормальном runtime

В игре лучше использовать:

```gdscript
var sea_cells_layer := BakedTileProvider.new(
    "res://assets/tiles_bundle/sea_cells_baked",
    MAX_Z
)
```

То есть:

```text
IrregularCellProvider = посмотреть/проверить/сгенерировать.
BakedTileProvider = играть.
```

# 15. Визуальный стиль морских клеток

Для проверки можно заливать клетки разными цветами, как на debug-карте.

Но для игры лучше:

```text
заливка: почти прозрачная или отсутствует;
границы: тонкие сине-тёмные;
берег: отдельный более чёткий слой;
открытый океан: крупные спокойные клетки;
прибрежная зона: более мелкая сетка.
```

Пример стиля:

```text
sea_cell_border:
  color: тёмно-синий / сине-серый
  alpha: 0.25–0.45
  width: 1 px

sea_cell_fill:
  alpha: 0.0–0.08

coastline:
  color: почти чёрный / тёмный береговой
  width: толще морской сетки
```

Важно:

```text
морские клетки не должны визуально спорить с сушей.
Они должны быть читаемой сеткой навигации, а не главным цветным слоем.
```

---

# 16. Что делать с проливами и узкими местами

На первом этапе можно просто сгенерировать клетки по воде.

Но архитектурно надо сразу помнить:

```text
проливы нельзя потерять.
```

Проблемы могут быть здесь:

```text
Гибралтар;
Босфор;
Дарданеллы;
Ла-Манш;
Датские проливы;
Суэцкая зона;
Красное море;
Персидский залив;
Малаккский пролив;
Японские проливы.
```

Если генератор делает клетку слишком крупной, пролив может стать неуправляемым.

Решение для будущей версии:

```text
добавить forced seed points в проливах и важных узких местах.
```

Для MVP можно сделать вручную список точек:

```text
assets/source/sea_forced_points.json
```

И добавлять их к seed-точкам перед Voronoi.

---

# 17. Как не испортить берег

У берега Voronoi после clip часто создаёт узкие кривые куски.

Чтобы этого избежать:

```text
1. Делать у берега более частые seed-точки.
2. Не давать океанским крупным seed-точкам слишком близко подходить к берегу.
3. После clip удалять слишком узкие клетки.
4. Проверять минимальную площадь и компактность.
```

Хороший показатель качества:

```text
compactness = area / perimeter²
```

Если compactness слишком низкий, клетка слишком вытянутая.

# 18. Spatial index для клика

Визуальный слой будет запечён, но клик по морской клетке нельзя делать по картинке.

Нужен отдельный индекс:

```text
SeaCellIndex.gd
```

Он должен уметь:

```text
get_cell_at_world_pos(pos) -> sea_cell_id
```

Минимальная реализация:

```text
1. Сначала проверить bbox.
2. Потом point-in-polygon.
```

Для ускорения:

```text
spatial hash / grid index
```

Пример:

```text
world bin 256x256 px
в каждом bin список sea_cell_id
клик -> bin -> несколько кандидатов -> point-in-polygon
```

Это намного быстрее, чем проверять все морские клетки.

---

# 19. Что должно быть в runtime

В обычной игре должны работать только лёгкие вещи:

```text
BakedTileProvider показывает запечённые тайлы.
SeaCellCatalog держит данные клеток.
SeaCellIndex быстро находит клетку под курсором.
SeaCellGraph даёт соседей для движения флота.
```

В runtime не должно быть:

```text
Voronoi;
clip polygon;
генерация seed-точек;
массовое shapely-подобное вычисление;
live-render всех морских клеток;
Node2D на каждую морскую клетку.
```

# 20. Пошаговый план внедрения

## Шаг 1. Сделать генератор

```text
scripts/tools/generate_sea_cells.py
```

Задачи:

```text
прочитать land/world данные;
создать sea_mask;
сгенерировать seed-точки;
построить Voronoi;
обрезать по sea_mask;
почистить геометрию;
сохранить sea_cells.json.
```

---

## Шаг 2. Подключить как debug-слой

В Godot временно подключить:

```text
IrregularCellProvider -> sea_cells.json
```

Цель:

```text
посмотреть размер клеток;
найти мусорные полигоны;
проверить берег;
проверить проливы;
проверить визуальную читаемость.
```

---

coastal_cell_size;

# 21. Проверка качества генерации

После генерации проверить:

```text
1. Нет клеток на суше.
2. Нет дырок в море.
3. Нет микроскопических клеток.
4. Нет огромных клеток у берега.
5. Проливы не сломаны.
6. Острова окружены читаемыми клетками.
7. Морские клетки не дублируют береговую линию.
8. Соседство sea-sea построено правильно.
9. Соседство sea-land построено правильно.
10. Количество клеток не слишком большое.
```

Примерные цели:

```text
MVP:
  море: 3 000–8 000 клеток

более детальная версия:
  море: 8 000–15 000 клеток
```

# 22. Что не делать

Не делать:

```text
- не делать Node2D на каждую морскую клетку;
- не строить Voronoi в Godot runtime;
- не рисовать все морские клетки live во время игры;
- не делать клетки строго квадратными;
- не делать весь океан одинаково мелким;
- не делать весь океан одинаково крупным;
- не использовать базы морей как готовые игровые клетки;
- не дублировать береговую линию морским клеточным слоем;
- не хранить только картинку без JSON-геометрии;
- не смешивать генерацию, отрисовку и геймплейную логику в одном файле.
```

# 23. Итоговая архитектура

Финальная схема должна быть такой:

```text
Natural Earth / land polygons / world mask
↓
generate_sea_cells.py
↓
sea_cells.json
sea_cell_graph.json
↓
IrregularCellProvider для проверки
↓
bake_sea_cells.py
↓
assets/tiles_bundle/sea_cells_baked
↓
Godot runtime:
  BakedTileProvider — показывает морские клетки
  SeaCellCatalog — хранит данные
  SeaCellIndex — поиск клетки под курсором
  SeaCellGraph — движение флота и соседство
```

Главное правило:

```text
Геометрия морских клеток создаётся один раз офлайн.
В игре используется только готовый результат.
```

Так архитектура останется быстрой, понятной и совместимой с уже существующей системой irregular-клеток.
