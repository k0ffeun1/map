# Новая архитектура карты — подробные примеры для каждого уровня

**Проект:** глобальная историческая стратегия  
**Назначение:** показать улучшенную архитектуру данных на конкретных примерах  
**Основная идея:** геометрия, постоянный паспорт и состояние сценария должны быть разделены

---

# 1. Главный принцип

Одна и та же провинция существует сразу в нескольких слоях данных.

На примере Севильи:

```text
Геометрия:
где находится Севилья и какой у неё полигон

Паспорт:
что это за постоянная провинция, как она называется,
к какому региону и макрорегиону относится

Сценарий 1444:
кто ей владеет, кто контролирует,
какая культура, религия, население и здания

Сохранение:
что изменилось после начала партии
```

Эти данные нельзя складывать в один JSON-объект.

Правильная цепочка:

```text
assets/map_geometry/provinces.json
                    ↓
assets/game_data/provinces.json
                    ↓
assets/game_data/regions.json
                    ↓
assets/game_data/macroregions.json
                    ↓
assets/scenarios/1444/province_state.json
                    ↓
сохранение партии
```

# 2. Главное улучшение: постоянный ID провинции

Первоначально предлагался ID:

```text
province:iberia:andalusia:sevilla
```

Он читаемый, но зависит от классификации.

Если Севилью или другую провинцию позже перенести в другой регион,
придётся либо менять ID, либо оставлять в ID устаревшее название региона.

Поэтому для постоянной личности провинции надёжнее:

```text
province:<numeric_id>
```

Пример:

```text
province:2839
```

Тогда:

```text
province:2839
```

всегда остаётся одной и той же Севильей, даже если:

- исправили её название;
- изменили русский перевод;
- изменили region_id;
- переименовали регион;
- изменили владельца;
- создали другой сценарий;
- загрузили старое сохранение.

Человекочитаемое имя хранится отдельно:

```json
{
  "id": "province:2839",
  "slug": "sevilla",
  "name": "Sevilla",
  "display_name_ru": "Севилья"
}
```

# 3. Уровень 1 — геометрия провинции

Файл:

```text
assets/map_geometry/provinces.json
```

Этот файл отвечает только на вопрос:

```text
Где находится провинция?
```

Он не должен знать:

- владельца;
- культуру;
- религию;
- население;
- региональные бонусы;
- здания;
- сценарий;
- дату.

## 3.1. Рекомендуемая оболочка файла

```json
{
  "schema_version": 1,
  "geometry_version": "2026.07.13",
  "provinces": []
}
```

## 3.2. Пример Севильи

```json
{
  "id": "province:2839",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "bbox": [
    3920.15,
    3160.44,
    3982.71,
    3210.87
  ],
  "rings": [
    [
      [3950.42, 3182.31],
      [3961.15, 3180.88],
      [3972.54, 3187.19],
      [3970.20, 3199.45],
      [3956.10, 3206.81],
      [3941.57, 3197.62],
      [3950.42, 3182.31]
    ]
  ]
}
```

Координаты выше демонстрационные. Реальные `bbox` и `rings` берутся из текущей геометрии и не меняются вручную в рамках задачи регионов.

## 3.3. Что означает каждое поле

```text
id
Постоянная ссылка на провинцию во всей новой системе.

legacy_id
Ссылка на старую систему.
Нужна для миграции старых файлов и существующего кода.

numeric_id
Постоянный числовой идентификатор.
Удобен для ID-карты, индексов и бинарного экспорта.

bbox
Быстрая прямоугольная граница полигона.
Позволяет не проверять все rings при клике.

rings
Настоящая геометрия провинции.
```

## 3.4. Что здесь запрещено

Плохо:

```json
{
  "id": "province:2839",
  "owner_country_id": "country:castile",
  "culture_id": "culture:andalusian",
  "region_id": "region:iberia:andalusia",
  "population": 90000,
  "rings": []
}
```

Причина:

```text
геометрия превратилась в смесь карты, сценария и игрового состояния.
```

# 4. Уровень 2 — паспорт провинции

Файл:

```text
assets/game_data/provinces.json
```

Этот файл отвечает на вопрос:

```text
Что это за постоянная провинция?
```

Он не отвечает на вопрос:

```text
Кто владеет ей в 1444 году?
```

## 4.1. Рекомендуемая оболочка

```json
{
  "schema_version": 2,
  "content_version": "2026.07.13",
  "provinces": []
}
```

## 4.2. Пример Севильи

```json
{
  "id": "province:2839",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,

  "slug": "sevilla",
  "name": "Sevilla",
  "display_name_ru": "Севилья",
  "localization_key": "province.2839.name",

  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",

  "terrain_id": "",
  "climate_id": ""
}
```

## 4.3. Что здесь является постоянным

```text
numeric_id
Постоянная техническая личность.

legacy_id
Связь со старой системой.

slug
Читаемая техническая метка.

name
Базовое международное или исходное название.

display_name_ru
Текущий русский вариант.

region_id
Постоянная историко-географическая классификация.

macroregion_id
Крупная географическая классификация.

terrain_id
Базовый или доминирующий рельеф.

climate_id
Базовый климатический профиль.
```

## 4.4. Что здесь запрещено

```text
owner_country_id
controller_country_id
culture_id
religion_id
population
buildings
devastation
occupation
garrison
tax_income
```

Провинция не перестаёт быть Севильей, если:

```text
Кастилия потеряла её;
её захватили;
изменилась культура;
изменилась религия;
население сократилось;
построили крепость.
```

# 5. Почему region_id и macroregion_id можно оставить вместе

Строго нормализованный вариант:

```json
{
  "region_id": "region:iberia:andalusia"
}
```

Макрорегион вычисляется через регион:

```text
province
→ region
→ macroregion
```

Но для текущего проекта можно оставить и:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

При этом нужно считать:

```text
region_id — источник истины;

macroregion_id — денормализованный кэш
для удобства, фильтрации и отладки.
```

Валидатор обязан проверять:

```python
province["macroregion_id"] == regions[province["region_id"]]["macroregion_id"]
```

Ошибка:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:france"
}
```

Результат:

```text
VALIDATION ERROR:
province:2839 macroregion mismatch
```

# 6. Уровень 3 — регион

Файл:

```text
assets/game_data/regions.json
```

Регион отвечает на вопрос:

```text
К какой средней историко-географической области
относится провинция?
```

Примеры регионов:

```text
Галисия
Андалусия
Кастилия
Каталония
Бретань
Нормандия
Ломбардия
Тоскана
Бавария
Фландрия
```

## 6.1. Рекомендуемая оболочка

```json
{
  "schema_version": 1,
  "content_version": "2026.07.13",
  "regions": []
}
```

## 6.2. Пример Андалусии

```json
{
  "id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",

  "slug": "andalusia",
  "name": "Andalusia",
  "display_name_ru": "Андалусия",
  "localization_key": "region.iberia.andalusia.name"
}
```

## 6.3. Пример Галисии

```json
{
  "id": "region:iberia:galicia",
  "macroregion_id": "macroregion:iberia",

  "slug": "galicia",
  "name": "Galicia",
  "display_name_ru": "Галисия",
  "localization_key": "region.iberia.galicia.name"
}
```

## 6.4. Что не нужно хранить в регионе

Не рекомендуется:

```json
{
  "id": "region:iberia:andalusia",
  "province_ids": [
    "province:2839",
    "province:2840"
  ]
}
```

Причина:

```text
принадлежность уже хранится в паспортах провинций;
появляется второй источник истины.
```

Правильно при загрузке построить:

```text
provinces_by_region
```

из `provinces.json`.

Пример runtime-результата:

```text
region:iberia:andalusia
→ province:2839
→ province:2840
→ province:2841
→ ...
```

Этот список является вычисляемым индексом, а не редактируемым контентом.

# 7. Пример состава региона

Допустим, в карте есть следующие провинции:

```text
Севилья
Кадис
Кордова
Гранада
Малага
Хаэн
Альмерия
Уэльва
```

В каждой провинции хранится:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

Регион не обязан хранить их список.

При загрузке каталог строит:

```gdscript
provinces_by_region["region:iberia:andalusia"] = [
    "province:2839",
    "province:...",
    "province:...",
    "province:..."
]
```

# 8. Уровень 4 — макрорегион

Файл:

```text
assets/game_data/macroregions.json
```

Макрорегион отвечает на вопрос:

```text
К какой крупной статичной части мира относится регион?
```

Примеры:

```text
Иберия
Франция
Италия
Британские острова
Скандинавия
Балканы
Центральная Европа
Малая Азия
Магриб
Левант
```

## 8.1. Рекомендуемая оболочка

```json
{
  "schema_version": 1,
  "content_version": "2026.07.13",
  "macroregions": []
}
```

## 8.2. Пример Иберии

```json
{
  "id": "macroregion:iberia",

  "slug": "iberia",
  "name": "Iberia",
  "display_name_ru": "Иберия",
  "localization_key": "macroregion.iberia.name"
}
```

## 8.3. Пример Франции

```json
{
  "id": "macroregion:france",

  "slug": "france",
  "name": "France",
  "display_name_ru": "Франция",
  "localization_key": "macroregion.france.name"
}
```

Здесь `France` означает не государство-владельца, а крупную статичную географическую область.

Государство Франция должно иметь другой namespace:

```text
country:france
```

А макрорегион:

```text
macroregion:france
```

Это разные сущности.

# 10. Уровень 5 — состояние сценария 1444

Файл:

```text
assets/scenarios/1444/province_state.json
```

Он отвечает на вопрос:

```text
В каком состоянии провинция находится
в момент начала конкретного сценария?
```

## 10.1. Рекомендуемая оболочка

```json
{
  "schema_version": 1,
  "scenario_id": "scenario:1444",
  "map_content_version": "2026.07.13",
  "province_states": []
}
```

## 10.2. Демонстрационный пример Севильи

Числа и баланс ниже являются примером структуры, а не утверждением окончательных исторических значений.

```json
{
  "province_id": "province:2839",

  "owner_country_id": "country:castile",
  "controller_country_id": "country:castile",

  "culture_id": "culture:andalusian",
  "religion_id": "religion:catholic",

  "population": 90000,

  "province_buildings": {
    "building:provincial_administration": 1,
    "building:provincial_fort": 1
  }
}
```

## 10.3. Почему здесь нет rings

Потому что:

```text
сценарий не меняет геометрию;
геометрия уже находится в map_geometry.
```

## 10.4. Почему здесь нет region_id

Потому что:

```text
региональная принадлежность не меняется от сценария;
она находится в постоянном паспорте.
```

## 10.5. Почему здесь культура

Потому что культура может измениться:

```text
1444:
culture:andalusian

другой сценарий:
culture:castilian

альтернативная партия:
culture:portuguese
```

При этом ID провинции остаётся:

```text
province:2839
```

# 12. Уровень 6 — сохранение партии

Сценарий является стартовым шаблоном.

Сохранение хранит то, что изменилось после начала игры.

Пример:

```text
assets/scenarios/1444/province_state.json
```

содержит стартовое состояние.

После 40 лет игры сохранение может содержать:

```json
{
  "province_id": "province:2839",

  "owner_country_id": "country:portugal",
  "controller_country_id": "country:rebels",

  "culture_id": "culture:andalusian",
  "religion_id": "religion:reformed",

  "population": 73500,

  "province_buildings": {
    "building:provincial_administration": 1,
    "building:provincial_fort": 2
  },

  "devastation": 38,
  "occupation_progress": 100
}
```

Геометрия и паспорт всё равно не дублируются в сейве.

# 13. Разделение владельца и контролёра

## Юридический владелец

```text
owner_country_id
```

Показывает:

```text
кому провинция принадлежит по праву.
```

## Фактический контролёр

```text
controller_country_id
```

Показывает:

```text
кто контролирует её сейчас.
```

Пример оккупации:

```json
{
  "province_id": "province:2839",
  "owner_country_id": "country:castile",
  "controller_country_id": "country:portugal"
}
```

Это означает:

```text
Севилья юридически принадлежит Кастилии,
но оккупирована Португалией.
```

Паспорт провинции при этом не изменяется.

Исходный пример:

В улучшенной системе ID становится:

```text
province:3974
```

## 16.1. Вариант A — оставить Pays de la Loire

```json
{

  "legacy_id": "france__mayenne",

  "slug": "mayenne",
```

Это подходит, если выбран принцип:

```text
использовать устойчивые современные региональные контейнеры.
```

## 16.2. Вариант B — использовать историко-географический регион

```json
{
  "id": "province:3974",

  "slug": "mayenne",
```

# 17. Рекомендуемое правило классификации

## Регион

```text
Средняя историко-географическая область,
которая объединяет несколько провинций.
```

## Макрорегион

```text
Крупная статичная географическая область,
объединяющая несколько регионов.
```

## Не использовать как регионы

```text
текущие государства;
динамические владения;
торговые узлы;
военные театры;
зоны снабжения;
динамические культурные области;
временные оккупационные администрации.
```

## Обязательные правила

```text
каждая провинция имеет один основной region_id;

каждый регион имеет один macroregion_id;

регион не зависит от владельца;

макрорегион не зависит от страны;

региональные границы не меняются в сценарии;

zone полностью отсутствует.
```

# 20. Runtime-индексы

Строковые ID удобны в JSON, но не нужны в каждом игровом расчёте.

После загрузки строятся плотные индексы.

Пример:

```text
province:2839
→ province_index = 0

province:3974
→ province_index = 1

region:iberia:andalusia
→ region_index = 0

region:france:maine
→ region_index = 1

macroregion:iberia
→ macroregion_index = 0

macroregion:france
→ macroregion_index = 1
```

В памяти:

```gdscript
province_region_index[0] = 0
province_macroregion_index[0] = 0

province_region_index[1] = 1
province_macroregion_index[1] = 1
```

Сценарное состояние:

```gdscript
province_owner_index[0] = castile_index
province_population[0] = 90000
```

Это быстрее и компактнее, чем постоянный поиск по строкам.

# 21. Почему numeric_id не равен runtime_index

```text
numeric_id
постоянный и сохраняется между версиями.

runtime_index
плотный и создаётся заново при загрузке.
```

Пример:

```text
numeric_id:
2839
3974
8401
12552
```

Runtime:

```text
2839  → 0
3974  → 1
8401  → 2
12552 → 3
```

Не нужно создавать массив длиной 12553 ради четырёх провинций.

# 26. Валидация

Команда:

```text
python scripts\tools\validate_map_ids.py
```

Ожидаемый результат:

```text
ID VALIDATION OK
```

## 26.1. Проверка уникальности

```text
id провинций уникальны;
numeric_id уникальны;
legacy_id уникальны;
id регионов уникальны;
id макрорегионов уникальны.
```

## 26.2. Проверка геометрии и паспорта

Для каждой провинции должны совпасть:

```text
id;
numeric_id;
legacy_id.
```

Ошибка:

```text
geometry numeric_id = 2839
passport numeric_id = 2840
```

## 26.3. Проверка ссылок

```text
region_id существует;
macroregion_id существует;
region.macroregion_id существует;
province_id сценария существует.
```

## 26.4. Проверка иерархии

```text
province.macroregion_id
==
region.macroregion_id
```

## 26.5. Проверка запрещённых полей

В паспорте нельзя:

```text
owner_country_id;
controller_country_id;
culture_id;
religion_id;
population;
buildings;
zone_id;
parents.zone;
любое поле zone_*.
```

## 26.6. Проверка сценария

В сценарии нельзя:

```text
rings;
bbox;
region_id;
macroregion_id.
```

## 26.7. Проверка ID

Провинция:

```regex
^province:[0-9]+$
```

Регион:

```regex
^region:[a-z0-9_]+:[a-z0-9_]+$
```

Макрорегион:

```regex
^macroregion:[a-z0-9_]+$
```

# 31. Итоговая рекомендация

Использовать:

```text
province:<numeric_id>
```

вместо:

```text
province:<macroregion_slug>:<region_slug>:<province_slug>
```

Оставить:

```text
region:<macroregion_slug>:<region_slug>
macroregion:<macroregion_slug>
```

При этом после публикации ID регионов тоже не переименовывать напрямую,
а использовать aliases.

Сохранить основные правила:

```text
геометрия отдельно;

паспорт отдельно;

сценарий отдельно;

страна не входит в ID;

культура и религия не входят в паспорт;

владелец и контролёр не входят в паспорт;

zone отсутствует;

legacy_id сохраняется;

numeric_id не переиспользуется;

runtime использует плотные индексы;

JSON является редактируемым источником;

BIN можно добавить позже для релиза.
```

Это даёт стабильную архитектуру, в которой:

```text
карта может расширяться;

сценарии не дублируют геометрию;

сохранения переживают переименования;

регионы не зависят от государств;

владелец может меняться без изменения паспорта;

данные удобно проверять валидатором;

runtime можно оптимизировать без изменения контента.
```
