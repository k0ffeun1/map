# Правила для этого проекта

## Язык — всегда русский

Весь текст, который видит пользователь — ответы, сообщения, описания
инструментов (например, поле `description` у Bash-команд), — только на
русском. Пользователь явно указывал на это несколько раз (в том числе
описания вызовов Bash, которые тоже видны в интерфейсе) — не только
основной текст ответа.

## Документы проекта — что где искать

Этот файл (CLAUDE.md) и `TODO.md`/`done.md` — **текущий рабочий консенсус**:
что реально решено и что реально сделано прямо сейчас. Всё остальное — это
материалы-источники для конкретных будущих систем, ещё не в разработке.
При противоречии между CLAUDE.md и любым из документов ниже — побеждает

## Именование файлов — САМОЕ ВАЖНОЕ ПРАВИЛО

Файлов в проекте становится всё больше (JSON-датасеты, Python-скрипты
препроцессинга, GDScript-провайдеры). Пользователь **не будет помнить**, что
внутри файла, если имя — техническая аббревиатура из источника данных.

Плохой пример (реальная ошибка в этом проекте): `admin1_areas.json`.
"admin1" — это термин из Natural Earth / GIS (административный уровень 1:
штат/область/провинция), НЕ говорящий сам за себя без контекста. Через
месяц непонятно, что это за файл и почему не `admin2` и не `regions.json`.

Правило на будущее — **имя файла должно быть понятно человеку, который не
помнит, что происходило в прошлой сессии**, глядя ТОЛЬКО на список файлов в
папке, без чтения кода:

- называть по СМЫСЛУ игрового слоя, а не по внутреннему термину источника
  данных (не `admin1`, не `ne_10m_X`, не аббревиатуры GIS-датасетов);
- если файл — часть пары "генератор → результат", оба должны называться
  ОДИНАКОВО по смыслу (`build_<смысл>.py` → `<смысл>.json`), чтобы связь была
  видна по имени, без открытия кода;
- если это ТЕСТ/черновой прогон, а не финальная версия — явно писать `_test`
  или `_draft` в имени (как `build_cells_test.py` → `cells_test.json`), не
  оставлять голым именем, которое потом легко спутать с финальным слоем;
- избегать голых цифр/версий без пояснения смысла (`_v2` — плохо само по
  себе, `_v2_raster_voronoi` — лучше, если версия действительно нужна);
- предпочитать чуть более длинное, но однозначное имя короткому и
  двусмысленному;
- **при заведении НОВОГО файла — на секунду остановиться и спросить себя:
  "если я забуду весь контекст этой сессии, пойму ли я по одному имени
  файла, что здесь лежит?"** Если нет — переименовать, прежде чем писать код.

Существующие не переименовываю без явной просьбы пользователя (задевает
пути в `TileMapViewer.gd`/других скриптах). Пример доведённого до конца
переименования: `admin1_areas.json` → `assets/provinces.json`,
`build_admin1_areas.py` → `scripts/tools/build_provinces.py` (2026-07-09,
см. done.md) — все ссылки в коде и документах поправлены вместе с
переименованием файла, а не оставлены висеть.

## Архитектура карты — согласовано с пользователем (см. optim_map_godot_strategy.md)

Пользователь принёс отдельный документ с рекомендациями по архитектуре карты
для Godot-стратегии — прочитан и одобрен, следовать этим принципам по мере
роста проекта:

- **Клетка = запись в данных, а не Node2D/Area2D.** Ни один игровой объект
  клетки не должен быть отдельной нодой сцены — так уже сделано
  (`IrregularCellProvider` рисует клетки полигонами в тайлах, `Cell.gd` —
  чистый Resource без ноды) и дальше делать так же.
- **Данные и рендер — раздельно.** `MapData`-подобный слой (у нас —
  `Cell.gd`/`CellCatalog.gd`) не должен знать о рендере; рендер
  (`IrregularCellProvider` и т.п.) не должен быть источником истины по
  игровым данным. Уже разведено, держать разведённым и дальше.
- **Тяжёлая генерация географии — офлайн, не в Godot.** GIS-очистка,
  Voronoi-нарезка клеток, упрощение полигонов — в Python
  (`scripts/tools/*.py`), результат — готовый JSON, который Godot просто
  грузит и рисует. Уже так и есть (весь пайплайн `scripts/tools/`), продолжать
  в том же духе, не переносить генерацию в рантайм GDScript.
- **Реальные регионы — контейнеры, а не сама игровая клетка.** Область
  (напр. Галисия/Мордовия) НЕ должна быть одной игровой клеткой — слишком
  разный размер по миру ломает баланс. Внутри каждой области нарезаются
  игровые клетки помельче (см. пример с Ла-Коруньей — 4 клетки внутри одной
  провинции). Это уже согласованное направление, не обсуждается заново.
- **TileMapLayer — только для настоящей сетки** (квадратные клетки, туман
  войны, фон). Неровные/административные полигоны — всегда через свой
  полигональный рендер (`IrregularCellProvider`/аналоги), не через тайлы.
  Уже так и сделано.
- **dirty-обновления, чанки, spatial-index для клика, LOD по зуму** —
  правильные техники, но НЕ внедрять заранее "про запас". Использовать
  строго когда появится реальный повод (клик по клетке ещё не реализован,
  количество клеток ещё мало) — документ сам называет пороги (>5000 клеток
  для чанков, >10-20 тыс. для mesh-кэша, см. §32 документа), ориентироваться
  на них, а не тащить инфраструктуру заранее.
- Конкретную предложенную в документе иерархию нод (`WorldMap/Data/
  Renderers/Entities/Systems`) и предложенные имена скриптов (`MapData.gd`,
  `MapRenderer.gd` и т.п.) буквально не копировать — в проекте уже
  сложившаяся своя структура (`TileMapViewer.gd` как оркестратор слоёв),
  переименовывать/перестраивать её только по отдельной явной просьбе
  пользователя, не просто чтобы совпасть с документом.

## Стек проекта — согласовано с пользователем (обсуждение документов
АРХИТЕКТУРА_ПРОЕКТА_СТРАТЕГИИ_ОПТИМИЗИРОВАННАЯ.md и
СТЕК_ПРОЕКТА_СТРАТЕГИИ_ПЛЮСЫ_МИНУСЫ.md)

Архитектурный документ (АРХИТЕКТУРА_ПРОЕКТА...) одобрен целиком как
долгосрочный ориентир — совпадает с принципами выше в этом файле (данные/
рендер раздельно, движение по графу переходов, запечённый визуал +
динамический overlay, ID-карта для кликов, кэш вместо пересчёта каждый
кадр, dirty flags, версии сейвов).

Стек-документ (СТЕК_ПРОЕКТА...) — **предложение "C# = всё игровое ядро,
GDScript только UI" ОТКЛОНЕНО.** Вместо него принят вариант пользователя:
граница между языками проходит **по типу вычисления, а не по
архитектурному слою**.

- **Сейчас (текущий стек, не менять)**: Godot 4 + GDScript — вся игра
  целиком (UI, карта, камера, клики, панели, визуализация, сейвы,
  редакторские инструменты). Python — офлайн-генерация данных
  (`scripts/tools/*.py`), уже так и работает. JSON/Resource — каталоги и
  предрасчёты (SQLite не вводить, пока нет конкретного кейса, где
  JSON/Resource реально не хватает).
- **Потом, ЕСЛИ понадобится (не заранее, только по факту профилирования)**:
  GDScript остаётся тем же (UI/карта/камера/клики/панели/визуализация/
  сейвы/инструменты), в C#. C++/GDExtension выносятся **только** тяжёлые
  батчевые расчёты: pathfinding, AI-оценка целей, торговые маршруты,
  годовой симулятор, массовый пересчёт экономики.

Ключевое правило границы (чтобы не получить плохой гибрид): граница между
GDScript и C#/C++ должна быть **редкой и толстой** (один батч-вызов на весь
массив клеток раз в год/ход), а не **частой и тонкой** (вызов на клетку,
вызов на клик). Плохой пример, которого избегаем: `Cell` как объект в C#,
UI в GDScript, тысячи вызовов туда-обратно на каждый клик или каждый
игровой год.

Почему не "C# как ядро" сейчас: весь текущий код (2868 строк на момент
решения) уже на GDScript и уже реализует нужное разделение данные/рендер
(`Cell.gd`/`CellCatalog.gd`) — переход на C# сейчас означает переписывание
уже работающего кода без нового функционала. Механики пока простые,
тяжёлых вычислений (экономика на тысячах клеток, pathfinding армий, AI) в
проекте физически ещё нет — оптимизировать раньше измеренной проблемы
производительности — то самое "внедрять инфраструктуру про запас", чего
проект избегает (см. правило про dirty-обновления/чанки/LOD выше).
Установленный движок (`Godot_v4.7-stable_win64.exe`) — не .NET-сборка,
переход на C# потребует отдельной установки mono/.NET редактора.

## Проверка в игре — только пользователь, но запускать игру обязательно

После КАЖДОГО изменения, которое влияет на то, что видно в игре (новый
слой, правка генератора, правка рендера и т.п.) — Клод **обязан сам
запустить Godot** (перезапустить, если уже был запущен), чтобы у
пользователя под рукой была свежая версия. Это не опционально и не требует
отдельной просьбы каждый раз.

Но САМУ проверку — смотреть глазами, скриншотить, кликать по карте,
оценивать результат — делает **только пользователь**, не Клод. Клод не
пытается сам "посмотреть", не описывает то, чего не видел, не делает
скриншотов ради собственной проверки. Разница: запуск игры — обязанность
Клода каждый раз; оценка того, что получилось — всегда пользователь.

## Новые слои в TileMapViewer.gd — добавлять СТРОГО в конец `_ready()`

Реальная ошибка этой сессии (2026-07-12): добавление нового слоя "V" вторым
элементом массива `_layers` (сразу после "Спутник") сдвинуло индексы ВСЕХ
слоёв после него на +1 — клавиша `8` вместо "Провинции" неожиданно стала
открывать "Реки".

Причина: часть клавиш в `_unhandled_input` (`1`, `6`, `0`, `-`, `=`, `8`,
`C`) сопоставлена с **жёсткими числовыми индексами** в `_layers`
(`KEY_8: idx = 5` и т.п.), а не с переменными — это исторически сложившийся
способ для самых старых/базовых слоёв (остальные, добавленные позже, уже
используют переменные вроде `_ocean_layer_idx`, `_regions_iberia_layer_idx`
и не ломаются от порядка).

**Правило**: новый слой-провайдер в `_ready()` — всегда `_layers.append()`
СТРОГО в самом конце функции (после всех существующих блоков), никогда не
вставлять в середину, даже если по смыслу он логически ближе к другому
слою. Позиция в массиве почти никогда не влияет на видимый порядок
отрисовки (для этого есть явный `"z_index"` в записи слоя, см. `_make_tile`)
— значит вставка в конец ничего не портит визуально, а вставка в середину
рискует сломать чужую клавишу без единой ошибки компиляции (баг тихий,
находится только руками пользователя в игре). Индекс нового слоя — всегда
через отдельную переменную (`var _my_layer_idx := -1`, как у большинства
существующих слоёв), никогда не новый хардкод в `match event.physical_keycode`.

## Структура файлов провинций/регионов (новая архитектура, с 2026-07-13)

Игровые слои в Godot по-прежнему читают легаси `assets/provinces.json`
(геометрия+имя одним файлом) — это НЕ заменено. Новая архитектура рядом —
отдельный "паспортный" слой данных для будущих систем (владение, культура,
сценарии), который генератор [build_map_architecture_v1.py](scripts/tools/build_map_architecture_v1.py)
собирает ИЗ `assets/provinces.json`, ничего в нём не меняя:

```text
assets/
├── provinces.json                       — легаси: геометрия + имя одним
│                                            файлом, слои Godot читают его
│
├── map_geometry/
│   └── provinces.json                   — только форма: id, legacy_id,
│                                            numeric_id, bbox, rings
│                                            (4027 провинций)
│
├── game_data/
│   ├── provinces.json                   — постоянный паспорт: id, slug,
│   │                                        name, display_name_ru,
│   │                                        region_id, macroregion_id,
│   │                                        terrain_id/climate_id (пустые
│   │                                        пока не нужны). Заполнен
│   │                                        region_id только у 9 из 4027
│   │                                        (Андалусия + Mayenne) — массовое
│   │                                        заполнение остальных ЕЩЁ НЕ
│   │                                        начато, это следующий большой шаг.
│   ├── regions.json                     — средняя историко-геог. область
│   │                                        (сейчас только 2: Андалусия,
│   │                                        Pays de la Loire)
│   └── macroregions.json                — крупная область (сейчас только 2:
│                                            Иберия, Франция)
│
├── scenarios/1444/
│   └── province_state.json              — сценарное состояние: owner/
│                                            controller_country_id,
│                                            culture_id, religion_id,
│                                            population, province_buildings
│                                            (все поля пока пустые — сценарий
│                                            ещё не начали населять)
│
└── migrations/
    ├── province_numeric_id_registry.json — legacy_id -> numeric_id,
    │                                         постоянный, номера НИКОГДА не
    │                                         переиспользуются (next_numeric_id
    │                                         монотонно растёт)
    └── map_id_aliases.json               — старый id -> новый
                                              province:<numeric_id> (4029
                                              записей), только дописывается
```

Каждый JSON-файл новой архитектуры несёт `schema_version` (+`content_version`/
`geometry_version`/`map_content_version`) в обёртке — см. пример выше.

**Как продолжать заполнение** (когда дойдут руки до массовой разметки
регионов): дописывать `region_id` в `game_data/provinces.json` и новые
записи в `regions.json`/`macroregions.json` по образцу уже заполненной
Андалусии — генератор (`CANONICAL_OVERRIDES` в `build_map_architecture_v1.py`)
и есть точка, куда добавлять новые провинции с известной классификацией.
После каждого прогона генератора — обязательно
`python scripts/tools/validate_map_ids.py`, ожидаемый результат
`ID VALIDATION OK` (проверяет уникальность/ссылки/иерархию/запрещённые поля —
см. done.md, раздел "Новая архитектура регионов/провинций").

## Ручные "патч"-скрипты (`patch_*.py`) легко потерять при перегенерации

Реальная ошибка (найдена и исправлена 2026-07-13, см. done.md): скрипты вида
`patch_sevilla_coastal_access.py`, которые модифицируют УЖЕ сгенерированный
файл (`assets/provinces.json`) ПОСЛЕ основного генератора (`build_provinces.py`),
незаметно теряются, если кто-то (человек или Клод) перегенерирует тот же
выходной файл заново и не помнит запустить патч повторно. Правка при этом не
видна нигде в самих данных — только в существовании скрипта и его
докстринге, поэтому пропажу находит только пользователь глазами в игре
(в этом случае — Севилья снова оказалась без выхода к морю на карте).

**Правило**: перед тем как перегенерировать `assets/provinces.json` (или
любой другой файл, который редактируется несколькими шагами пайплайна) —
проверить `ls scripts/tools/patch_*.py` и прогнать КАЖДЫЙ найденный патч
заново, в том порядке, что указан в его докстринге (там же обычно написано,
какие шаги идут ДО и ПОСЛЕ патча — см. `patch_sevilla_coastal_access.py`).
Если правка визуальная — обязательно сверить результат (bbox/число точек
контура) с последним коммитом, где патч точно был применён, а не полагаться
на память.
