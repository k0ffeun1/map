# Что сделано (Global Strategy Prototype)

## Базовая карта
- Тайловая карта мира (slippy map, схема z/x/y), стриминг по видимым тайлам,
  LOD-уровни `MIN_Z..MAX_Z` (сейчас `MAX_Z = 7`).
- Базовый слой — онлайн-тайлы реальной Земли: [OnlineTileProvider.gd](scripts/OnlineTileProvider.gd)
  (сервер ESRI, сейчас стиль `World_Physical_Map` — стилизованный атлас без подписей).
- Камера: [CameraController.gd](scripts/CameraController.gd)
  - WASD / стрелки — плавное перемещение (lerp);
  - колесо мыши — зум к курсору;
  - ПКМ / СКМ (зажать) — перетаскивание карты;
  - `R` — сброс (вписать всю карту в экран);
  - `Esc` — выход;
  - ограничение камеры по границам карты.
- Движок стриминга/слоёв: [TileMapViewer.gd](scripts/TileMapViewer.gd)
  — рендерит несколько слоёв поверх друг друга, переключение клавишами `1`–`6`.

## Слои (клавиши 1–6)
1. **Спутник/атлас** — реальная карта Земли (онлайн).
2. **Политический** — оверлей-заглушка (процедурный шум по регионам).
3. **Экономический** — оверлей-заглушка (процедурный тепловой градиент).
4. **Религиозный** — оверлей-заглушка (процедурный шум по регионам).
5. **Клетки** — глобальный слой клеток-провинций по всему миру
   ([CellTileProvider.gd](scripts/CellTileProvider.gd)):
   - только границы (скруглённые квадраты линиями), без цветной заливки суши —
     заливку убрали по просьбе (было промежуточным цветным шумом-заглушкой);
   - реальная береговая линия — маска суши строится из данных высот
     (Terrarium elevation tiles), а не из спутниковой картинки;
   - маска сглажена majority-фильтром 3×3, чтобы убрать шумовые "дыры"
     в низинных регионах (Нидерланды, дельта По, дельта Нила, низины у Каспия) —
     порог "суша/море" сдвинут до `-8 м`, чтобы польдеры и т.п. не резались как море;
   - клетки не рисуются за полярными порогами (`NORTH_CUTOFF_Y`/
     `SOUTH_CUTOFF_Y`, ~76°N/~58°S) — убрана вся Антарктида и дальняя
     необитаемая Арктика (Гренландия выше поселений, Шпицберген, арктические
     острова); пороги подобраны по скриншоту, не облётаны по всему миру.
6. **Моря** — контуры морей/заливов/проливов/звуков/каналов/лагун/фьордов
   ([SeaBorderTileProvider.gd](scripts/SeaBorderTileProvider.gd)), только линии,
   без заливки:
   - геоданные — Natural Earth `ne_10m_geography_marine_polys` (общественное
     достояние), 301 объект после фильтрации по типу;
   - офлайн-препроцессинг (не в Godot, один раз):
     [build_sea_borders.py](scripts/tools/build_sea_borders.py) — проецирует
     полигоны в Web Mercator (та же система координат `WORLD_PX`, что и
     остальные слои), упрощает Douglas-Peucker (117k → ~35k точек), сохраняет
     в [assets/sea_borders.json](assets/sea_borders.json) (672 КБ);
   - рендер синхронный, без сети: данные грузятся один раз в память при
     старте, каждый тайл клипует и рисует линии из колец, чьи bbox
     пересекают тайл (ручная растеризация отрезков с антиалиасингом по краю,
     без встроенного polyline-API у `Image`);
   - слой НЕ участвует в `TilePreloader` (не нужно — данные уже локальные).

## Загрузка тайлов
- Кэш на диске: `user://tilecache` (карта) и `user://elevcache` (высоты) —
  повторный запуск игры использует уже скачанное без сети.
- **Bundle-кэш в проекте**: `assets/tiles_bundle/tilecache` и
  `assets/tiles_bundle/elevcache` — то, что "запечено" прямо в проект/игру
  (проверяется провайдерами ПЕРВЫМ, до сети и до `user://`).
  Перенесён ПОЛНЫЙ мир (весь `MAX_Z`): 22 719 файлов (~166 МБ) карты +
  21 795 файлов (~996 МБ) высот — предзагрузка завершена, перенос из
  `user://` сделан вручную (см. "На будущее" — процесс ещё не автоматизирован).
  Билд/установщик с этого момента полностью офлайн.
- Фоновая предзагрузка всех тайлов мира при старте:
  [TilePreloader.gd](scripts/TilePreloader.gd) — качает весь мир до `MAX_Z`
  для карты и высот параллельно (пул HTTPRequest), пишет прогресс внизу экрана.
  Использовать игру можно и во время предзагрузки.

## Производительность (эта сессия)
Карта заметно фризила/мигала при зуме. Причины и фиксы:
- **LOD дребезжал во время анимации зума** — считался от промежуточного
  сглаженного `zoom` каждый кадр, а не от целевого. Теперь
  [TileMapViewer.gd](scripts/TileMapViewer.gd) берёт `camera.get_target_zoom()`
  (новый метод в [CameraController.gd](scripts/CameraController.gd)) и
  переключает уровень один раз за жест, с гистерезисом `LOD_HYSTERESIS`.
- **Старый LOD выгружался мгновенно, до готовности нового** — при смене
  уровня видимого слоя тайлы старого LOD теперь держатся, пока не готовы
  все нужные тайлы нового (см. `_process` в `TileMapViewer.gd`) — мигание
  пустотой при зуме исчезло.
- **Декодирование тайлов и рендер клеток блокировали кадр** —
  [OnlineTileProvider.gd](scripts/OnlineTileProvider.gd) (чтение файла +
  JPEG/PNG-декодирование) и [CellTileProvider.gd](scripts/CellTileProvider.gd)
  (маска суши + отрисовка клеток, ~600 тыс. итераций на тайл) теперь
  выполняются в `WorkerThreadPool`, главный поток только создаёт текстуру из
  готового `Image`. Оба провайдера дожидаются своих фоновых задач в
  `_exit_tree()` — иначе поток мог дёрнуть уже уничтоженный объект при выходе.
- **`TilePreloader` фризил старт и отжирал сеть** — теперь стартует с
  задержкой `START_DELAY = 10s`, качает меньшим пулом (3 вместо 10) и
  сканирует уже скачанный кэш порциями (`SCAN_BUDGET_PER_FRAME`), а не всё за
  один кадр.

## Слой подписей морей
[SeaLabelsLayer.gd](scripts/SeaLabelsLayer.gd) + [SeaLabelNode.gd](scripts/SeaLabelNode.gd) —
не тайловый слой (подписей мало, ~300), создаются один раз, показываются
вместе со слоем "Моря". Имя/координата центроида берутся из
`SeaBorderTileProvider.get_labels()` (area-weighted центроид самого крупного
кольца объекта). Масштаб каждой подписи выставляется каждый кадр
`= 1/zoom камеры`, чтобы текст был константного размера на экране при любом
зуме, а не съезжал/не раздувался.

## Убраны Антарктида и Крайний Север — везде, не только у клеток
Раньше обрезка по широте (`NORTH_CUTOFF_Y`/`SOUTH_CUTOFF_Y`, ~76°N/~58°S)
работала только в слое "Клетки". Теперь:
- границы ВСЕЙ карты (`camera.set_map_bounds`) обрезаны по этим широтам —
  камера физически не может провернуться туда ни на одном слое;
- **дополнительно** поверх всех слоёв рисуется закрашенный
  прямоугольник-маска (`_add_polar_mask` в `TileMapViewer.gd`) — при сильном
  отдалении ("вписать всю карту", `R`) несовпадение соотношения сторон окна и
  обрезанной карты давало полоску полюса по краю экрана даже при
  ограниченной камере; маска гарантированно перекрывает её независимо от
  того, что нарисовано снизу.

## Неровные (Voronoi) клетки суши — слой "Клетки суши (неровные)" (клавиша 7)
Офлайн-препроцессинг (не в Godot, один раз, как `build_sea_borders.py`):
[build_land_cells.py](scripts/tools/build_land_cells.py) →
[assets/land_cells.json](assets/land_cells.json), рендерится
[IrregularCellProvider.gd](scripts/IrregularCellProvider.gd) (заливка +
тонкая граница, рендер в `WorkerThreadPool`, как остальные тяжёлые провайдеры).

- **Данные** — Natural Earth `ne_10m_land` (полигоны суши), 6837 отдельных
  кусков после разбора `MultiPolygon` (остров/материк = один кусок).
- **Число клеток на кусок суши** зависит от площади (км², считается по
  исходным lon/lat ДО проекции):
  - < 300 км² — клеток нет (слишком мелкий остров, не показываем);
  - 300–3000 км² — 1 клетка (весь остров);
  - 3000–15000 км² — 2 клетки;
  - 15000–50000 км² — 3–4 (линейная интерполяция);
  - > 50000 км² (материки, крупные острова) — `площадь / TARGET_CELL_AREA_KM2`
    (сейчас `10000`, даёт плавную стыковку на границе 50000 км²).
- **Плотность по регионам** (`SPARSE_ZONES`/`BOOST_ZONES` в скрипте) — не
  общий множитель, а прямоугольники lon/lat с локальным весом, применяются
  при расстановке точек-семян Voronoi (не только к общему числу клеток):
  - реже (крупнее клетки): Сибирь, Сахара, Амазония, внутренняя Австралия,
    тайга/тундра Канады, Патагония, Конго, Аравия (Руб-эль-Хали),
    Центр. Азия/Гоби, Тибет, Калахари/Намиб;
  - гуще (мельче клетки): Европа, вес `5.0` относительно базового `1.0`
    (нормализуется по `GLOBAL_MAX_WEIGHT`, иначе вес ≥1 всегда проходил бы
    проверку и буст не работал бы).
- **Гренландия — особый случай**: не обычный остров (обитаемо только
  побережье), клетки строятся ТОЛЬКО в прибрежной полосе (`poly.boundary.buffer`),
  центр — ледник без клеток вообще (см. `GREENLAND_BBOX`/`GREENLAND_COASTAL_BUFFER_KM`).
- **Волнистые (изрезанные) границы** — не Voronoi-прямые: каждое РЕБРО
  Voronoi (не весь контур клетки) сглажено рекурсивным смещением середины
  отрезка (как рисуют реки в генераторах карт), см. `_displace_segment`.
  Кэшировано по ключу (индекс вершины A, индекс вершины Б) — у двух соседних
  клеток одно и то же ребро получает ИДЕНТИЧНУЮ волнистую линию (без щелей на
  стыке). Пробовали сначала сглаживание Чайкина (скругление углов
  многоугольника целиком) — оно смягчает только вершины, рёбра между ними
  остаются идеально прямыми; это не то, что нужно ("изрезанные линии, как
  реки"), поэтому заменили на подход с общим кэшем волнистых рёбер.
- **Меркатор-коррекция расстояния между семенами** — без неё север
  (Сибирь/Канада) искажён проекцией и получал систематически меньше клеток,
  чем должен был (расстояние между точками считалось в "мировых пикселях"
  без поправки на то, что 1 км на экваторе ≠ 1 км у полюса в Меркаторе).
- **Проверка на разрыв по антимеридиану** изначально ошибочно выбрасывала
  Афро-Евразию целиком (bbox шире половины мира — но это НЕ разрыв, а просто
  очень широкий континент от Португалии до Чукотки); исправлено на проверку
  скачка между СОСЕДНИМИ точками кольца, а не общей ширины bbox.
- **Пространственная сетка для min-distance проверки** между семенами —
  наивная O(n²) проверка (сравнение с каждой уже поставленной точкой) заняла
  бы часы для материков с тысячами семян; заменена на бакет-сетку с
  окном 3×3 (или шире у полюсов, где Меркатор-масштаб больше).
- Итог на момент предыдущей генерации: **15 061 клетка**, ~1.23 млн точек
  (файл `land_cells.json` ~23 МБ — заметно вырос из-за возросшей плотности и
  изрезанности, разово влияет на время загрузки при старте, см. TODO).

## Волнистая береговая линия (эта сессия)
Запрос пользователя по скриншотам: часть побережий выглядела "прямой рваной"
(реальные точки Natural Earth без сглаживания) — внутренние границы между
клетками уже были волнистые, а сама береговая линия нет.
- **Береговая линия теперь тоже волнистая**: в
  [build_land_cells.py](scripts/tools/build_land_cells.py) добавлена
  `_wavify_geom`/`_wavify_ring` — тот же приём рекурсивного смещения
  середины отрезка (`_displace_segment`), что и у внутренних Voronoi-рёбер,
  но применяется ОДИН РАЗ ко всему контуру суши (внешнее кольцо + дыры)
  сразу после `simplify(1.5)`, ДО разбиения на клетки. Слабее внутренних
  границ (`COAST_JAGGED_DEPTH=3`/`COAST_JAGGED_AMPLITUDE=0.16` против
  `4`/`0.28` у внутренних), чтобы не взорвать число точек на материках.
  Старое сглаживание Чайкина (`chaikin_smooth_closed`) и `_add_cell`
  (с `rdp`-упрощением поверх волнистого контура, что сводило волну обратно
  к прямым линиям) убраны — везде используется `_add_wavy_cell` без
  повторного упрощения.
- Итог новой генерации: **14 497 клеток**, ~1.37 млн точек контуров клеток
  (файл `land_cells.json` ~26 МБ).
- **Пробовали и откатили**: закрашивать мелкие острова (< 300 км²) сплошным
  цветом моря вместо прозрачной клетки (чтобы не просвечивал спутниковый
  слой) — пользователь попросил НЕ делать так, потому что позже спутниковый
  слой всё равно уберут и останутся только клетки, так что временный
  "мусор" от мелких островов не имеет смысла чинить сейчас. Код (`erase_cells`
  в JSON, `ERASE_COLOR`/рендер в `IrregularCellProvider.gd`) добавлялся и
  удалён обратно в эту же сессию.
- **Баг волнистого берега нашёлся и исправлен той же сессией**: смещение
  середины отрезка было СИММЕТРИЧНЫМ (в обе стороны), поэтому контур клетки
  местами уходил внутрь настоящей суши — снаружи клетки оставался виден
  кусок настоящей земли спутникового слоя (дыра). Исправлено —
  `_displace_segment_outward`/`_ring_signed_area` смещают береговую линию
  ТОЛЬКО наружу (в море), контур клетки может только расти, никогда не
  теряет исходную сушу.

## Мелкие острова у берега материка, плотность регионов, Гренландия (эта сессия)
- **Мелкие "прилипшие" острова убираются, а не мержатся**: острова тира
  "1 клетка" (300..3000 км²) в пределах `NEARSHORE_KM` (12 км) от куска суши
  крупнее `NEARSHORE_MAINLAND_KM2` (50 000 км²) теперь НЕ получают клетку
  вообще (`_is_nearshore_of_mainland`, STRtree-индекс материков
  `_build_mainland_index`) — раньше давало визуальный хаос (куча
  перекрывающихся волнистых мелких клеток рядом с берегом материка, видно
  в дельте Амазонки и у восточного побережья США). Есть список исключений
  `ISLAND_EXCEPTION_ZONES` (Карибский бассейн, Япония, Корея) — там мелкие
  острова рядом с материком/друг с другом остаются отдельными клетками
  (настоящие архипелаги), список расширяемый.
- **Плотность регионов**: добавлены `BOOST_ZONES` — Карибский бассейн,
  Япония, Корея, Нижние земли (Нидерланды/Бельгия — гуще, чем остальная
  Европа). Патагония убрана из `SPARSE_ZONES` (была лишней/сломанной на
  вид) — обычная плотность.
- **Гренландия ослаблена**: `GREENLAND_COASTAL_BUFFER_KM` 180→110, своя
  целевая площадь клетки `GREENLAND_TARGET_CELL_AREA_KM2=45000` (было
  пропорционально общей `TARGET_CELL_AREA_KM2=10000` острова — слишком
  много клеток в глубину узкой полосы) — теперь в среднем ~1-2 клетки
  вглубь от берега. Плюс `GREENLAND_NORTH_CUTOFF_LAT=72.0` — севернее клеток
  вообще нет (практически необитаемо).
- Итог: **15 649 клеток**, ~1.47 млн точек (файл `land_cells.json` ~27.6 МБ).

## Правки по скриншотам с красными квадратами (эта сессия)
- **Баг: Исландия/Баффинова Земля/Элсмир/Виктория/Девон получали "гренландский"
  режим** (только берег + отсечка севера) из-за слишком широкого порога
  `area > 100000` км² в проверке `is_arctic_island` — все они выше этого
  порога и центроид у всех попадает в `GREENLAND_BBOX`. Отсюда: Исландия
  одной большой клеткой, и большие куски суши на севере Канады вообще без
  клеток (их "гренландский" центр оказался ВЫШЕ `GREENLAND_NORTH_CUTOFF_LAT`,
  а прибрежная полоса у них не подразумевалась). Порог поднят до 1.5 млн
  км² (реальная Гренландия ~2.17 млн, следующий по размеру арктический
  остров Баффинова Земля ~507 тыс) — теперь ТОЛЬКО настоящая Гренландия
  получает урезанный режим, остальные — обычный Voronoi по всей площади.
- **`MIN_ISLAND_AREA_KM2` снижен с 300 до 15 км²** — при 300 пропадали
  вообще (без клетки) многие настоящие именованные острова (Средиземноморье,
  Дания, Британия/Ирландия, Фареры, часть Карибов).
- **`NEARSHORE_KM` уменьшен с 12 до 5 км`**, список `ISLAND_EXCEPTION_ZONES`
  расширен (добавлены Филиппины, Средиземноморье, Британия/Ирландия/Бретань,
  Дания/Фареры/промежуток Исландия-Британия) — при 12 км и коротком списке
  исключений под "удалить как мусор у берега" ошибочно попадали настоящие
  прибрежные острова (о. Уайт, Англси и т.п.), не только наносные островки
  дельт/заливов.
- **Филиппины "наезжали" друг на друга**: волнистость берега смещает контур
  только наружу (см. предыдущий фикс дыр), но БЕЗ ограничения по абсолютной
  величине — в тесном архипелаге соседние ОТДЕЛЬНЫЕ острова могли распухнуть

  смещения поверх относительной доли от длины сегмента.
- Итог: **16 368 клеток**, ~1.47 млн точек (файл `land_cells.json` ~27.6 МБ).

### Найденные и исправленные баги
- **`IrregularCellProvider.gd` не поддерживал дырки в полигонах** — рисовал
  только внешний контур клетки, дырки (озёра) игнорировал полностью, поэтому
  Каспий/Байкал/Великие озёра/Виктория закрашивались как суша. Добавлена
  поддержка множественных колец (`rings[0]` внешний контур, `rings[1..]`
  дырки) — заливка чётно-нечётным правилом в `_fill_polygon`, границы рисуются
  по всем кольцам. Обновлены `build_land_sea.py`/`build_continents.py`, чтобы
  писать дырки (`p.interiors`) в JSON, а не только внешний контур.
- **Острова внутри озёр вылезали оторванными чёрными кляксами** — по ДВУМ
  независимым причинам, обе исправлены в `build_land_sea.py`/`build_continents.py`:
  1. Вычитание озера из суши делалось полигоном озера С его дырками-островами
     — острова физически не входили в вычитаемую область и оставались
     отдельными кусками суши посреди озера. Фикс: вычитать СПЛОШНОЙ контур
     озера (без дырок).
  2. Некоторые озёра (рифтовые озёра Африки, как Каспий) — не отдельная
     запись в `ne_10m_lakes`, а дырка, уже встроенная прямо в
     `ne_10m_land` — острова внутри такой дырки вообще не участвуют в
     вычитании озера. Общий фикс: любой кусок суши, ЦЕЛИКОМ лежащий внутри
     дырки ДРУГОГО куска (через `STRtree`/`contains` по центроиду) —
     остров в озере, выбрасывается целиком, независимо от источника.
- **Самопересекающиеся "бабочки"-полигоны после округления координат** —
  добавлена защита (`_emit_cell` в обоих скриптах: строим `Polygon(ext,
  holes)` из УЖЕ округлённых координат, если невалиден — `buffer(0)` и
  разбор на несколько простых клеток), та же схема, что и в
  `build_land_cells.py`/`_add_wavy_cell`.
- **Клавиши-символы слоёв (`=`, `-` и т.п.) не всегда читались из-за
  раскладки клавиатуры** — `event.keycode` зависит от раскладки, переключили
  `TileMapViewer.gd` на `event.physical_keycode` (та же категория бага, что
  раньше был с WASD).
- **Устаревший кэш классов Godot** — после добавления новых файлов со
  `class_name` (`RiverTileProvider.gd`, `BakedTileProvider.gd`) движок не
  сразу их подхватывал ("Identifier ... not declared", вся игра зависала на
  "Загрузка карты...") — чинится пересканированием проекта
  (`godot --headless --editor --quit-after N`).

## Мерцание при зуме и шов на слое "Континенты" (эта сессия)

### Мерцание/потемнение полупрозрачных слоёв при смене LOD
Раньше при смене уровня детализации старый тайл слоя держался как подложка,
пока НЕ ДОГРУЗИТСЯ ВЕСЬ видимый слой на экране целиком (проверка `missing[li]
> 0` по всему слою). Из-за этого старый и новый тайл полупрозрачного слоя
(континенты, альфа ~0.55) несколько кадров лежали друг на друге — альфа
складывалась (0.55 поверх 0.55 ≈ 0.8), слой заметно темнел на долю секунды
при каждом зуме.
- **Фикс**: в [TileMapViewer.gd](scripts/TileMapViewer.gd) добавлена
  `_replacement_ready(li, kz, kx, ky, lod, x0, y0, x1, y1)` — точная проверка
  "готова ли ЗАМЕНА именно ЭТОГО старого тайла" (для более мелкого LOD —
  все дочерние тайлы новой сетки в этой области; для более крупного —
  один родительский тайл нового LOD). Старый тайл снимается сразу, как
  только его конкретная замена готова, а не когда весь экран целиком.
  Убрана старая грубая `missing`-логика.
- Непрозрачные слои (спутник) это не задевало — там наложение старого/нового
  тайла незаметно, проблема была специфична для полупрозрачных оверлеев.

### Шов/полоса на слое "Континенты", "прыгающая" по широте при зуме
Пользователь заметил тонкую полосу через континент (видна на нескольких
широтах одновременно — Сибирь, Африка, и т.д.), которая обрывалась ровно на
границе континента (в океан не заходила) и перескакивала на другую широту
при смене уровня зума (напр. с Африки — на Сардинию).
- **Причина**: [bake_continents_tiles.py](scripts/tools/bake_continents_tiles.py)
  рендерит каждый тайл независимо в суперсэмплинге (x2), потом сжимает
  LANCZOS до 256×256 — но у фильтра НЕТ доступа к реальным пикселям ЗА
  краем тайла (тайл рендерится изолированно), поэтому у самого верхнего и
  нижнего ряда каждого тайла получается едва другой оттенок, чем у
  соседнего тайла того же ряда. На сплошной прозрачности (океан) незаметно,
  а рядом с любым внутренним краем (изгиб берега, озеро) — видна тонкая
  полоса через весь ряд тайлов. Разная тайловая сетка на разных `z` →
  разная широта шва на разных уровнях зума → "прыгает" при смене зума.
- **Фикс**: тайл теперь рендерится с запасом `MARGIN_PX=4` (в итоговых px)
  за каждым краем, сжимается ВМЕСТЕ с запасом (то же соотношение
  суперсэмплинга), затем обрезается ровно до нужных 256×256 — LANCZOS видит
  настоящих соседей, шов пропадает.
- Заодно, по просьбе пользователя, границы континентов сделаны тоньше/чётче:
  `BORDER_WIDTH: 0.7 → 0.45`, `MAX_BORDER_PX: 3 → 2`.
- **Важно**: правки внесены в `bake_continents_tiles.py`, но тайлы **ещё не
  перезапечены** — перезапечка отложена, чтобы сделать её один раз вместе
  со сглаживанием контуров континентов (см. TODO.md), а не дважды.

  подмешивание цвета соседнего тайла на стыке при билинейной фильтрации.

  выше, `_replacement_ready`.)

- **Найден и исправлен артефакт**: на низком зуме (z1–z3) появлялась ложная
  горизонтальная линия через весь тайл (обнаружено на стыке Дании/Швеции и
  на Босфоре) — причина: у гигантских слитых полигонов (Европа/Азия после
  Чайкина — 17–23 тыс. точек) на низком зуме не хватало пикселей на
  мировую единицу, тонкая деталь контура схлопывалась в суб-пиксельную
  полоску и PIL scanline-заливка протягивала сплошную линию через весь
  тайл. Фикс: `MIN_SCALE` — держим минимум px/мировая-единица на всех
  уровнях, поднимая supersample только для низких z (там тайлов мало,
  z0–z3 = 85 шт., дёшево).
- Тайлы перезапечены дважды (первый раз без фикса линии, обнаружен и
  исправлен, перезапечено снова) — **важный урок**: перед повторным запуском
  долгой печи ВСЕГДА проверять, что предыдущий процесс дейстительно
  остановлен (`ps aux`), а не полагаться на то, что `TaskStop`/новый запуск
  сам разберётся — был случай, когда старый и новый процесс печи работали
  ОДНОВРЕМЕННО в одну и ту же папку, портя результат.
- Итог: 8104 тайлов, 35.57 МБ.

  цепочка кластеров мелких соседей схлопывается сама постепенно.
  Итог: 8503 → 5892 кусков.
- **Удаление мелких островов** (не слияние — полное исключение из вывода,

  - `PROTECTED_ISLAND_NAMES` — исторически значимые острова по имени (Иона,

    Гори, Роббен-Айленд, Иводзима, Пасхи и т.д.);

    просто часть MultiPolygon у более крупной провинции) — Ваддензе/

    провинции "Friesland"/"Groningen"/"Niedersachsen";
  - `PROTECTED_ISLAND_COUNTRIES` — защита по стране целиком: у Мальты датасет
    делит территорию на муниципалитеты (Валлетта, Слима и т.п.), даже слитые
    ПОЛНОСТЬЮ в естественные куски (остров Мальта/Гозо) всё равно мельче

    подходит вообще (имена — случайные "выжившие" после цепочки слияний,
    напр. "Xewkija"/"Birgu", а не "Malta");
  - `TOP_N_ISLANDS` + `color_key` — для Мальдив (все атоллы мельче даже

    порядкового индекса клетки, если поле есть).
  Итог: 5892 → 3436 кусков (2456 мелких островов удалено), финально

### Найден и исправлен реальный баг: бесконечный цикл в фоновом потоке
При добавлении пунктирных границ (`_dash_segments_world` в
[IrregularCellProvider.gd](scripts/IrregularCellProvider.gd)) пользователь
столкнулся с зависанием игры и даже уходом компьютера в сон под нагрузкой.
Причина — классический баг off-by-epsilon: на границе штрих/промежуток
`remaining` из-за погрешности плавающей точки могло округлиться до ~0,
`seg_end == pos`, цикл `while pos < seg_len: ... pos = seg_end` не
продвигался — 100% одного ядра НАВСЕГДА в фоновом `WorkerThreadPool`-потоке,
причём на КАЖДЫЙ рендерящийся тайл слоя. Исправлено: `EPS`-защита
гарантированного шага + отдельный жёсткий потолок `MAX_DASH_SEGMENTS` про
запас. Написан регресс-тест
[scripts/tools/test_dash_no_hang.gd](scripts/tools/test_dash_no_hang.gd)
(автономный `SceneTree`-скрипт, `godot --headless --script ...`) — гоняется
после каждой правки этой области кода, показывает "OK: N штрихов посчитано
за M мс" вместо зависания.

### Стиль границ — толщина, чёткость, волнистость (эта сессия, несколько итераций по скриншотам)
Пользователь несколько раз присылал скриншоты и уточнял: итоговое решение —
`IrregularCellProvider.gd` получил набор НОВЫХ опциональных параметров стиля
(старые слои не задеты, дефолты = прежнее поведение):
- **Пунктир** — `border_dashed`/`dash_len`/`dash_gap`, фаза считается по
  накопленной длине в МИРОВЫХ координатах (не по локальным px тайла) — иначе
  на стыке двух тайлов штрихи не совпадают.
- **Мягкость сглаживания края** — `border_feather` (было жёстко 1.0 px).
- **Минимальная полутолщина** — `border_min_half_w` (было жёстко 1.0 px) —
  нашёлся баг: этот "пол" перебивал `border_width` на любом зуме ниже
  максимального, из-за чего изменение толщины визуально не давало эффекта
  ("граница не изменилась" — жалоба пользователя, разобрана и исправлена).
- **Разрешение растра тайла** — `raster_px` (было жёстко 256 для всех слоёв)
  — реальная причина "видны пиксели" на сильном приближении: тайл рисуется в
  фиксированное разрешение независимо от зума, `TileMapViewer._make_tile`
  сам подгоняет масштаб спрайта под `tile_world / texture.get_width()`, так
  что подъём `raster_px` работает "бесплатно" для рендера, но НЕ бесплатно
  по CPU/памяти — обсуждали с пользователем: для крошечного тестового слоя
  клеток (1-2 тайла) это несущественно, для слоя "Области" (весь мир) это
  реально 16× работы на КАЖДЫЙ тайл; пользователь осознанно попросил
  `raster_px=1024` для обоих слоёв, зная цену (см. TODO.md).
- **Волнистые внутренние рёбра** — `build_cells_test.py`: тот же приём
  рекурсивного смещения середины отрезка, что уже применялся для береговой
  линии (`build_land_cells.py`), но детерминированный по хэшу КЛЮЧА РЕБРА
  (отсортированные округлённые концы, не зависит от направления обхода) —
  волна применяется к СЫРЫМ Voronoi-регионам ДО обрезки провинцией, поэтому
  внешний контур области остаётся прямым (как в исходных данных), волнистые
  только внутренние рёбра между клетками.
- **Именованный стиль вместо позиционных чисел** — по прямому запросу
  пользователя (принёс пример формата `const BORDER_STYLE := {...}`),
  признано ЛУЧШЕ прежнего подхода (позиционные аргументы с комментариями) —
  заведён `const BORDER_STYLE` в `TileMapViewer.gd` с записями `"cell"` и
  `"province"` (только для того, что реально отрисовано — `"region"`/
  `"country"` не заводить заранее без геометрии).
- Итоговые числа (подобраны под ~1.5px/alpha 0.30 для клеток и ~2.5px/alpha
  0.55 для областей НА БЛИЗКОМ ЗУМЕ z7, см. формулу в комментарии
  `BORDER_STYLE`): `cell.width=0.375`, `province.width=0.625`.

### Убрано "мыло" на стыке границы клетки и границы области
Пользователь заметил по скриншоту: там, где контур клетки совпадает с
границей самой провинции, линия выглядит размытой — причина: ДВЕ почти
совпадающие полупрозрачные сглаженные линии рисуются друг на друге (своя у
слоя клеток + своя у слоя области), с независимым сглаживанием и чуть
разными округлениями координат. Исправлено на уровне данных, не рендера:
- `build_cells_test.py`: `_split_open_border_chains()` — для каждого ребра
  клетки считает расстояние от его середины до ИСХОДНОГО (ещё не порезанного
  на клетки) контура провинции; рёбра ближе `BOUNDARY_TOL=0.05` мировых px
  классифицируются как "внешние" (совпадают с границей области, её и так
  рисует слой "8") и выбрасываются из отрисовки; остальные — "внутренние"
  (волнистые Voronoi-рёбра) — идут в новое поле JSON `brd_open` списком
  ОТКРЫТЫХ (не замкнутых) цепочек точек.
- `IrregularCellProvider.gd`: новое поле `border_open_rings` (парсится из
  `brd_open`) — когда непусто, ПОЛНОСТЬЮ заменяет `border_rings`/`rings` как
  источник линии для конкретной клетки, рёбра рисуются БЕЗ замыкания
  последней точки на первую (в отличие от `border_rings`/`rings`, которые
  всегда кольца). `_dash_segments_world()` получил параметр `is_open` для
  того же (не заворачивать пунктир через несуществующее последнее ребро).
  Важно: `rings` (заливка/площадь/будущий клик) НЕ меняется — это чисто

## Бюджет создания текстур за кадр (2026-07-09)
Пользователь принёс отдельный внешний отчёт по оптимизации кода карты —
разобран, большинство пунктов совпало с уже сделанным/уже решённым (не

выше). Из реальных пунктов сделан один — остальные (лимит/LRU кэша тайлов,

ключи, `Cell.gd` → packed-массивы для будущей симуляции) сознательно
отложены: лимит кэша — по прежнему решению пользователя (не трогать, пока
мир не докачан), запекание — "потом", остальное — не горит.

**`MAX_TEXTURE_CREATES_PER_FRAME := 16`** добавлен в четыре провайдера,
которые пачкой создают `ImageTexture.create_from_image()` из результатов
фоновых потоков: `OnlineTileProvider.gd`, `BakedTileProvider.gd`,
`IrregularCellProvider.gd`, `RiverTileProvider.gd`. Раньше `_process()`
забирал ВСЕ готовые `Image` из `_done_images` и создавал текстуры для всех
разом — если резкий разворот камеры/смена слоя "дозревал" сразу много
фоновых задач одним кадром, это могло дать микрофриз. Теперь обрабатывается
не больше 16 штук за кадр, остаток (`done.slice(i)`) кладётся обратно в
`_done_images` (с тем же мьютексом, что и у фоновых потоков) и доделывается
в следующих кадрах — спрайт просто появляется на кадр-два позже, без
видимого рывка. `_decoding`/`_rendering` для необработанных элементов не
трогается, поэтому `request_tile()` для них корректно продолжает
возвращать `null` ("ещё не готово"), повторный запуск декодирования/рендера
не запускается.

### `scripts/tools/generate_sea_cells.py` — генератор игровых морских клеток
Пайплайн по документу: водная маска → адаптивные seed-точки через
квадродерево (гуще у берега, реже в океане, целевой размер по кривой
расстояния до берега) → Voronoi → обрезка по морю → чистка/слияние мелких
кусков → граф соседства → [assets/generated/sea_cells.json](assets/generated/sea_cells.json)
+ `sea_cell_graph.json`. Рендерится debug-слоем `IrregularCellProvider` на
клавише `9` ("Клетки моря (тест)").

- **Источник суши — `assets/provinces.json`, НЕ `land_sea.json`** — явное
  решение пользователя: "слой провинций это основополагающий слой, на
  котором будет строиться вся карта дальнейшая" (см. память проекта
  `project_provinces_foundation_layer`). Все новые офлайн-генераторы суши
  по умолчанию берут `provinces.json`.
- **Найдены и исправлены ДВЕ квадратичные по стоимости "зависалки"**
  (первый прогон висел 10+ минут без результата на маленьком тестовом
  регионе, второй раз — 5+ минут на полном мире без единого прогресс-принта):
  1. `clip_and_explode` пересекал КАЖДУЮ Voronoi-клетку с ОДНИМ гигантским
     `sea_mask` (весь мир минус вся суша). Исправлено: STRtree по кускам
     суши, вычитаются только БЛИЗКИЕ куски (обычно 0-3), не вся геометрия.
  2. `compute_brd_open` считал `distance()` до ГЛОБАЛЬНОГО
     `land_union.boundary` на каждое ребро каждой клетки — тот же класс
     бага. Исправлено аналогично, через STRtree.
  3. **Реинкарнация бага при переходе на полный мир**: `load_land_union()`
     делал `unary_union()` всех провинций — соседние провинции Евразии
     склеивались в ОДИН полигон на 28216 точек с bbox почти во весь мир,
     и STRtree переставал быть локальным (для любой клетки рядом с
     Евразией индекс находил именно эту громадину). Исправлено —
     `load_land_pieces()` возвращает НЕсклеенные куски (по одной провинции),
     STRtree строится по ним; `unary_union` делается только ОТДЕЛЬНО, для
     растровой маски (где склейка не мешает).
- **Волнистые границы / скруглённые углы — попробованы и ОТКАЧЕНЫ**:
  сначала добавили волнение рёбер (тот же приём, что у
  `build_cells_test.py` — рекурсивное смещение середины ребра по хэшу),
  понравилось, но было слишком "мелко-пильчато" (depth 4→2). Дальше
  попробовали "круглые квадраты" (регулярная сетка seed-точек + `buffer(-r)
  .buffer(+r)` скругление углов) — пользователь забраковал ("ужасно"),
  попросил вернуть ПЕРВУЮ версию: хаотичные seed-точки (jitter=0.35), БЕЗ
  волнения, прямые линии Voronoi. Код волнения/скругления удалён (не
  оставлен мёртвым/закомментированным, см. CLAUDE.md).
- **Статус "потенциальный центр провинции"** — `Cell.gd` получил новое поле
  `province_center_status` ("" / "potential" / зарезервировано "actual").
  В `build_cells_test.py` помечена клетка `lacoruna_3` (розовая на карте,
  индекс 3 → hue≈307° по золотому сечению в `IrregularCellProvider._load_data`).
  В генераторе морских клеток — `merge_capital_coastal_cells()`: все морские
  клетки, касающиеся берега такой клетки, сливаются в ОДНУ (чтобы столичная
  клетка была со всех сторон окружена одной морской клеткой, а не
  разрезана внутренним sea-sea ребром). Пока связка ТЕСТОВАЯ (источник —
  `cells_test.json`, единственный файл с этим полем сейчас) — когда
  появится настоящий слой клеток суши, брать оттуда.
- **Кривая размера клетки от расстояния до берега** — несколько раз

### `scripts/tools/build_world_ocean.py` + слой "Мировой океан" (клавиша `2`)
Отдельная, более простая задача (по прямой просьбе пользователя) — ЕДИНАЯ
маска "вода/не вода" на весь мир, БЕЗ деления на клетки, перед тем как
резать клетки на всём мире. Результат — [assets/world_ocean.json](assets/world_ocean.json)
(тот же формат rings/bbox, что у `land_sea.json`), вычислено как
`world_box - union(provinces.json)`.

- **Щели между провинциями → мнимое "море" внутри материков** — соседние
  провинции в `provinces.json` не всегда идеально стыкуются (обычное дело
  для реальных административных векторных данных). Без исправления —
  сотни мелких дырок-крапинок мнимой воды на стыках (найдено визуально на
  побережье Ла-Манша/Бретани/Португалии, сотни клеток < 5 км² с нулём
  соседей в `generate_sea_cells.py` тоже были тем же багом на побережье
  Франции/Испании).
- **Простой `buffer(+gap)` на каждый кусок ДО объединения — тоже
  попробован и заменён**: закрывал щели, но раздувал контур ~500
  фейковыми точками-скруглениями на каждый залив, которые `simplify` потом
  СХЛОПЫВАЛ, теряя реальную детализацию берега (111 точек на Ла-Корунью
  вместо 232 у provinces.json). Заменено на **морфологическое ЗАМЫКАНИЕ**
  (`buffer(+CLOSE_PX)` → `unary_union` → `buffer(-CLOSE_PX)`, CLOSE_PX=0.15) —
  щели заклеиваются, берег возвращается почти на исходное место, точек
  берега получилось БОЛЬШЕ, чем у простого buffer (1137 против 679 в
  тестовом окне). Плюс отдельная чистка результата: мелкие дырки-крапинки
  (`MIN_HOLE_AREA_PX2=4.0`) и лужи-щепки (`MIN_WATER_PIECE_AREA_PX2=4.0`)
  выброшены явно (208 дырок и 614 щепок в тестовом прогоне).
- **Реки не слиты с океаном в один полигон** — сознательное решение после
  обсуждения с пользователем: реки (`rivers.json`) — полилинии с уровнями
  значимости (`tier` 0/1/2 крупная/средняя/малая, уже готово в данных из

### Пиксельность берега на слое "Мировой океан" — причина и решение (bake)
Пользователь заметил, что берег у слоя "Мировой океан" заметно "лесенкой"
по сравнению со слоем провинций при одинаковом `raster_px=1024`. Разобрано
по шагам, ложные версии по пути:
1. Проверили детализацию геометрии самого контура (124 точки у Ла-Коруньи
   в `world_ocean.json` против 232 у `provinces.json`) — НЕ причина, этого
   достаточно для гладкого контура.
2. **Настоящая причина**: `_fill_polygon` в `IrregularCellProvider.gd`
   рисует заливку БЕЗ сглаживания (скан-линия, `ceil`/`floor` до целого
   пикселя) — у провинций это незаметно, потому что поверх рисуется
   ОТДЕЛЬНАЯ обводка контура с настоящим феатером/градиентом
   (`border_feather`), которая визуально маскирует грубый край заливки.
   Обводка океана изначально была `alpha=0.0` (задумывалась "просто
   заливка без рамки") — поэтому был виден голый пиксельный край. Добавлена
   видимая (но мягкая, `border_feather=2.0`) обводка — помогло частично.
3. **Настоящая-настоящая причина мыла/зависания на близком зуме**: океан —
   ОДИН полигон на 34155 точек с bbox почти во весь мир, каждый тайл
   вынужден пересчитывать все точки (build-line заливка на чистом
   GDScript — то же самое, из-за чего "Континенты"/"Суша-Море" уже раньше
   переведены на запечённые тайлы, см. записи выше в этом файле). Пока
   тяжёлый живой рендер не досчитался — виден растянутый тайл с дальнего
   зума (мыло/пиксели).
- **Решение — запекание**: [scripts/tools/bake_world_ocean_tiles.py](scripts/tools/bake_world_ocean_tiles.py)
  (по образцу `bake_land_sea_tiles.py`/`bake_continents_tiles.py`,
  supersample 4x + LANCZOS даунскейл). ТЕСТОВЫЙ прогон печёт только регион
  (Северо-Запад Иберии, `REGION_LONLAT`), не весь мир — 66 тайлов за 78
  секунд. `TileMapViewer.gd` подключает `BakedTileProvider`, если папка
  `assets/tiles_bundle/world_ocean_baked` существует (тот же паттерн, что у
  континентов/суши-моря), иначе падает обратно на живой `IrregularCellProvider`.
  Пользователь подтвердил результат ("все норм! четко"). **Полный мир НЕ
  запечён** — сознательно отложено до конца доработки слоя (следующая
  сессия начнётся с механики глубин, см. TODO.md).

### Тестовый запечённый слой провинций — Галисия (клавиша `4`)
Пользователь попросил проверить более высокое разрешение (`SUPERSAMPLE=8`,
`TILE_PX=1024`) для запекания слоя "Области" (живой слой `8` не трогать).
Несколько итераций, каждая находила и чинила реальную проблему:

1. **Первая версия — весь Иберийский полуостров** (`bake_provinces_iberia_tiles.py`)
   — позже полностью удалена и заменена версией **только для Галисии**
   (`scripts/tools/bake_provinces_galicia_tiles.py`, тот же тестовый регион,
   что у "Мирового океана"/превью глубин) — по прямой просьбе пользователя,
   когда встал вопрос отдельного тестового слоя.
2. **Баг: тёмный "ободок"/кляксы на границе заливка↔прозрачность** —
   классический баг непремультиплицированной альфы при LANCZOS-ресайзе
   (прозрачный фон хранится как чёрный `(0,0,0,0)`, чёрный подмешивается в
   цвет соседних полупрозрачных пикселей). Фикс — `_resize_premultiplied()`
   (домножение RGB на альфу перед сжатием, обратное деление — ПОСЛЕ, на уже
   маленькой итоговой картинке, не на исходном супersample-холсте — иначе
   на дальнем зуме, где `MIN_SCALE` поднимает supersample очень высоко,
   float-массив на весь холст не влезает в память, ловили `numpy.
   _core._exceptions._ArrayMemoryError`).
3. **По просьбе пользователя границы сначала полностью убраны** (`alpha=0`,
   как у живого слоя `8` в этот момент) — оказалось, что "ложная граница",
   которую видел пользователь, была не отрисовкой, а щелями между
   провинциями (см. диагностику `world_ocean.json` выше) — исправлено
   раздутием (`GAP_FIX_PX=0.15`) каждой провинции индивидуально перед
   заливкой (только для картинки, не меняет `provinces.json`).
4. **Разрешение тайла поднято 256→1024** (`TILE_PX`, не просто `SUPERSAMPLE`)
   — по просьбе пользователя, когда края провинций выглядели "пиксельными"
   при близком зуме. Объяснено пользователю на пальцах: тайл — квадратный
   кусок ГОТОВОЙ картинки (как в Google Maps), не провинция; итоговый размер
   тайла у всех старых bake-скриптов жёстко зашит в 256×256, `SUPERSAMPLE`
   влияет только на чёткость ДО сжатия обратно в этот размер — увеличение
   именно `TILE_PX` даёт реально больше пикселей на тот же кусок мира.
5. **Граница возвращена** по прямой просьбе — тонкая (`width=0.15` мировых
   px), резкая (`feather=0.1`, минимум без деления на ноль), непрозрачная
   (`alpha=1.0`) — синхронно и в bake-скрипте, и в `BORDER_STYLE["province"]`
   живого слоя `8` в [TileMapViewer.gd](scripts/TileMapViewer.gd).
6. **Баг: граница на стыке двух провинций двоилась** — рисовалась НЕЗАВИСИМО
   по контуру каждой провинции; после раздутия (шаг 3) контуры соседей стали
   слегка отличаться → две разъехавшиеся линии на одном стыке. Пробовали
   рисовать границу по ИСХОДНОМУ (нераздутому) контуру — помогло не везде
   (у меньшинства провинций сам исходный контур соседей не совпадает
   координата-в-координату — реальная неточность реальных
   административных векторных данных, не баг).
7. **Механика границы переписана целиком** (предложение пользователя) — НЕ
   векторные линии по контуру вообще, а поиск границы ПРЯМО в уже залитой
   (раздутой, без щелей) картинке: где сосед другого цвета/прозрачности —
   там граница. Двоение линии физически невозможно по построению (один и
   тот же пиксельный переход). Толщина — сначала жёсткий `binary_dilation`
   (быстро оказалось плохо — см. ниже), потом заменено на плавное затухание
   по расстоянию (`scipy.ndimage.distance_transform_edt` + формула ТОЧНО как
   в `IrregularCellProvider._draw_segment`: `alpha=clamp((half_w+half_feather
   -dist)/feather, 0, 1)`), чтобы совпадать с живым слоем `8` визуально, а не
   просто жёстко перезаписывать пиксели.
8. **Ловушка с памятью (дважды)** — на дальнем зуме (`MIN_SCALE` задирает
   supersample) холст огромный (до ~16-17 тыс. px), но реальный контент —
   маленький уголок. `numpy`-обработка (int32/float маски) на ВСЁМ холсте
   падала по памяти (`ArrayMemoryError`, и отдельно — незаметное повышение
   до `float64` при смешивании с python-`float`, тоже удвоило память).
   Исправлено: работа numpy'ем только в обрезке по `img.getbbox()` (реальный
   контент), explicit `float32` везде.
9. **Известное НЕ РЕШЁННОЕ ограничение** (см. TODO.md) — реальные детали
   берега у́же самой линии границы (найдено: крошечный залив у Ла-Коруньи —
   та же точка нестыковки, что чинили в `world_ocean.json` выше; и заметнее —
   гавань у Лиссабона) отрисовываются сплошной чёрной кляксой, потому что
   линия границы физически шире самой детали. Обсуждали закрашивать мелкие
   детали цветом соседа — остановились, когда пользователь указал, что
   Лиссабонская гавань РЕАЛЬНАЯ и исторически значимая, закрашивать её
   нельзя не проверив размер. Более аккуратное решение (предложено
   пользователем) — детектировать такие "запечатанные" точки и локально
   раздвигать сушу до нужной ширины пролива (морфологическая операция по
   distance transform, наподобие conditional dilation/reconstruction) —
   сложнее всего, что делали в этой сессии, не начато.

Итог на тот момент: `assets/tiles_bundle/provinces_galicia_baked` — 22 тайла,

## Узкие гавани решены, слой `4` расширен на всю Иберию, диск почищен (2026-07-10/11, продолжение)

### Механика границы в bake-скрипте дозрела ещё на шаг дальше пункта 8 выше
Между предыдущей записью и этой сессией плавное затухание по
`distance_transform_edt` (пункт 7 выше) заменено на бинарную дилатацию диском
(`scipy.ndimage.binary_dilation` по маске-диску радиуса `half_w+half_feather`)
— дешевле по памяти на полном тайле (EDT на float64/int64 требовал сотни МБ),
а само сглаживание края всё равно даёт downscale LANCZOS при сжатии
supersample-холста, так что визуальной разницы не видно. Плюс сам холст на
дальнем зуме больше не аллоцируется на весь тайл (было до ~17К px, падало по
памяти `MemoryError`/`ArrayMemoryError`) — теперь под каждый тайл берётся
только прямоугольник вокруг реального контента (bbox по всем `hits`,
выровненный на сетку supersample), а не весь холст целиком.

### Узкие гавани (Ла-Корунья и т.п.) — решены двумя мерами
1. **Раздутие `GAP_FIX_PX` (закрывает щели между соседними провинциями)
   перестало вылезать в море**: после `poly.buffer(GAP_FIX_PX)` из результата
   вычитается точный полигон мирового океана (`assets/world_ocean.json`,
   покрывает весь мир, не только тестовый регион — проверено по
   `build_world_ocean.py`, там нет региональных ограничений). Раньше раздутие
   без разбора грызло и сушу, и узкие заливы — теперь щели между соседями по
   суше закрываются как раньше, а к морю провинция возвращается к точному
   контуру.
2. **Граница на berегу теперь рисуется только внутрь суши**: маска
   `opaque` (непрозрачные исходные пиксели) накладывается на результат
   дилатации границы (`border &= opaque`) — чёрный пиксель границы физически
   не может лечь на воду. Раньше "полутолщины" границы с двух берегов узкого
   пролива смыкались и заливали его целиком сплошной чёрной кляксой.

Проверено пользователем визуально на клавише `4` в игре — залив у
Ла-Коруньи, который раньше был чёрной кляксой, теперь открыт. При разборе
скриншота с ложной тревогой про Лиссабон (он на самом деле открыт и не
пострадал — вне текущего региона на момент проверки) найден **один** остаточный

## Механика "3 уровня моря" (мелководье/шельф/глубины) — клавиша `5`, плюс мелководье насовсем в слое `2` (2026-07-10/11, продолжение)

### Батиметрия (клавиша `5`): найден и исправлен реальный баг с пропусками данных
Пользователь заметил белые крапинки на суше и чёрные точки на воде на
превью батиметрии. Причина — исходный GMRT-грид (склейка GEBCO+доп. съёмок)
реально содержит пропуски (NaN, ~0.09% сетки, дыры на стыках отдельных
съёмок), а `reproject()` в
[_preview_sea_depth.py](scripts/tools/_preview_sea_depth.py) не получал
`src_nodata`/`dst_nodata` — пропуски либо портили соседние пиксели мусорными
значениями от билинейного смешивания с NaN (чёрные точки), либо (раз `dst`
изначально нулевой) оставались как `elevation=0` (белые крапинки, ложно
классифицируется как мелководье). Исправлено: `src_nodata=np.nan`/
`dst_nodata=np.nan` в `reproject()`, оставшиеся NaN-пропуски заполняются

### Найден и исправлен реальный баг: щели между провинциями считались морем

### Найден и исправлен баг фильтрации текстуры (зубцы вдоль всего берега)
Расстояние до берега кодируется как 16 бит на пиксель, разбитые на 2
отдельных 8-битных канала текстуры (R/G — GPU не умеет упаковывать больше
8 бит в канал без специальных форматов). `LINEAR`-фильтрация спрайта
интерполирует R и G НЕЗАВИСИМО друг от друга, а не как единое число — там,
где младший байт (G) перескакивает через 255→0 (происходит каждые ~4 км
расстояния), интерполяция даёт мусорные комбинации, видимые как мелкие
зубцы/вздутия вдоль всего берега. Исправлено — `TEXTURE_FILTER_NEAREST`
вместо `LINEAR` на спрайте мелководья (та же настройка уже была у спрайта
батиметрии с самого начала).

### Отрисовка маркера — векторные узлы, НЕ тайлы (перепройдено дважды)

Первая версия ([ProvinceCityMarkerProvider.gd](scripts/ProvinceCityMarkerProvider.gd),
УДАЛЁН) рисовала маркер растром прямо в тайлы 256×256, как границы
провинций. Оказалось плохой идеей для ~100 РЕДКИХ точек: на стыке двух
тайлов круг иногда проваливался (половина рисовалась в одном тайле, половина
в другом — если решение "попадает ли маркер в тайл" на границе давало разный
результат для соседних тайлов), из-за чего часть городов выглядела
"пустыми", а сквозь непрорисованную половину круга просвечивала заливка
провинции под ним ("розовый цвет заходит на круг").

Исправлено переходом на векторные `Node2D` (тот же приём, что уже был у
подписей морей, `SeaLabelsLayer`/`SeaLabelNode` — подписей/маркеров мало, не
нужен тайловый механизм):
- [ProvinceCityMarkerNode.gd](scripts/ProvinceCityMarkerNode.gd) — один
  узел = один город, круг через `draw_circle(..., antialiased=true)` +
  подпись `draw_string` с отступом `LABEL_GAP=8.0` px ПОД кругом (не
  слитно), `z_index=100` (гарантированно выше всех тайловых слоёв).
- [ProvinceCityMarkersLayer.gd](scripts/ProvinceCityMarkersLayer.gd) —
  контейнер, грузит `province_cities_iberia.json` один раз, создаёт узлы,
  каждый кадр выставляет `scale = 1/zoom` (постоянный размер на экране при
  любом зуме, тот же приём, что `SeaLabelsLayer._process`). Видимость
  синхронизирована со слоем "Провинции (Иберия)" в `TileMapViewer._process`.
- `SeaLabelNode.gd`/`SeaLabelsLayer.gd` попутно получили необязательный
  `offset_y` (по умолчанию 0, подписи морей не тронуты) — использовался в
  промежуточной версии, когда подписи городов ещё были через переиспользование
  `SeaLabelsLayer`; после перехода на `ProvinceCityMarkerNode` подписи городов
  рисуются им же самим, но параметр `offset_y` оставлен в `SeaLabelNode` как
  общая возможность (не удалён — рабочий, может пригодиться).

### Найдено и исправлено по пути: две независимые причины MemoryError

На выросшем до всей Атлантики bbox (~10900×10300 px при x4, точная память
машины ~16 ГБ, но реально свободно 3-4 ГБ из-за фоновых приложений)
`scipy.ndimage.distance_transform_edt` в `build_coast_distance_field.py`
стабильно падал с `MemoryError` — внутри себя считает промежуточные
int32-индексы (2,H,W) + их float64-версию, пиковая память ~2.7 ГБ **на один
вызов**, а вызывается дважды (суша→море и море→суша) без явного
освобождения между вызовами.

- **Первый фикс (частичный)**: кастинг результата в `float32` сразу после
  каждого вызова + явный `gc.collect()` между вызовами — снизил пиковую
  память вдвое, хватило для x4, но x8 всё равно падал (сам вызов scipy всё
  ещё требовал ~4x больше при удвоении разрешения).
- **Настоящий фикс** — переход с `scipy.ndimage.distance_transform_edt` на
  `cv2.distanceTransform(..., cv2.DIST_L2, cv2.DIST_MASK_PRECISE)`: тот же
  ТОЧНЫЙ (не аппроксимированный) евклидов результат, но компилированная
  реализация без гигантских промежуточных Python/numpy-массивов индексов —
  на порядок меньше пиковой памяти, сразу float32. `opencv-python` уже был
  в зависимостях проекта (использовался для `build_land_cells_v2.py`).
- **Вторая независимая утечка**: `signed_km` неявно повышался до `float64`
  при умножении `float32`-массива на `km_per_world_px_row` (получался
  через `np.array(..., dtype=object)` по умолчанию float64) — на x8
  (450 Мpx) это отдельно требовало лишние ~3.3 ГБ. Исправлено явным
  `dtype=np.float32` на всей цепочке вычисления км/строка.
- **`wsl --shutdown`** — по ходу отладки свободная память на машине падала
  сама по себе независимо от python-скриптов (до ~0.9 ГБ) из-за `vmmem`
  (VM для WSL2/Docker Desktop, копится память, не отдаёт обратно активно).
  `wsl --shutdown` безопасно освобождает её (WSL сам поднимается заново при
  следующей надобности) — вернуло ~8.6 ГБ свободных, без него часть
  перезапусков скриптов падала не по вине самого кода.

### Найдено: x8 упирается не в память, а в лимит Godot на `Image`

После обоих фиксов x8 (21845×20546 px = ~449 млн пикселей) успешно
СЧИТАЛСЯ в питоне (~1-3 минуты на файл), но при загрузке в Godot падал с
`ERROR: Too many pixels for Image. Maximum is ... = 268435456 pixels`
(`scene/resources/image_texture.cpp`) — это архитектурный потолок движка на
ОДИН `Image`/текстуру (соответствует примерно 16384×16384), не связан с
доступной оперативной/видеопамятью. x4 (10923×10273 = ~112 млн px)
укладывается с запасом — **зафиксировано как рабочее значение** для обоих
живых оверлеев слоя 2 на этом bbox.

**На будущее, если понадобится x8+**: живые Sprite2D-оверлеи мелководья/
глубины сейчас грузят ВЕСЬ регион одной текстурой — чтобы поднять
разрешение выше лимита, нужен тот же тайловый подход, что уже есть у слоя
"Мировой океан" (`bake_world_ocean_tiles.py` + `BakedTileProvider.gd`):
нарезать растр на мелкие тайлы, грузить по требованию. Не сделано — ждёт
отдельного решения пользователя, сейчас x4 устраивает.

## Фикс маски суша/море у растра глубины: польдеры Нидерландов (2026-07-12)

Пользователь заметил на скриншоте тёмные пятна-острова посреди суши в
Нидерландах на слое глубины/мелководья. Причина отличалась от прошлого бага

высоты GEBCO (`is_sea = elevation <= 0.0`) — а значительная часть Нидерландов
(польдеры) физически НИЖЕ уровня моря (реальная высота отрицательная,
местами до -6.7 м), хотя это осушенная суша под дамбами, а не море. GEBCO
честно репортит физическую высоту — по наивному правилу польдеры ошибочно
считались морем.

- **Фикс**: маска море/суша теперь берётся из ВЕКТОРА (`assets/world_ocean.json`,

  вектор уже сказал "это море", не для самого решения "суша это или море".
  Новая функция `_rasterize_ocean_mask()` растеризует `world_ocean.json` на
  ту же сетку, что и растр GEBCO.
- Побочный эффект — заодно устранён рассинхрон береговой линии между
  `sea_depth_west_europe.png` и `coast_distance_field_west_europe.png` (оба
  теперь от одного источника).
- **Развитие темы**: у слоя "Мировой океан" (клавиша `2`, живые
  оверлеи глубины/мелководья поверх запечённых тайлов) остров, которого нет
  в `provinces.json` (удалён как мусор ещё в старой чистке), после этого
  фикса перестал визуально "проступать призраком" — раньше несовпадение двух
  разных источников истины (GEBCO vs вектор) давало плоское пятно без
  градиента глубины именно в форме острова, которого физически нет в данных;
  после унификации источника оба слоя стали рисовать это место одинаково
  (обычным морем), контур пропал.

## Слой "V" — подложка "океан снизу + провинции сверху" (2026-07-12)

### Идея и почему до неё дошли не сразу
Пользователь заметил на слое 2/B тёмные силуэты крупных островов (см. выше
про баг мирового океана) и предложил несколько вариантов чинить это через
перекраску/цветовой ключ между слоями — все были признаны нерабочими или
хуже текущего векторного подхода (антиалиасинг на границе полигона ломает
точное сравнение цвета, см. обсуждение в чате). Рабочая идея нашлась в
итоге: не вычитать геометрию суши из моря вообще, а нарисовать **сплошную
заливку на весь мир НИЖЕ провинций** (painter's algorithm) — тогда провинции
сами перекрывают её сверху везде, где есть суша, никакого вычитания и
никаких дырок не нужно. Побочный эффект (принят сознательно): слой должен
показываться ВМЕСТЕ с провинциями — сам по себе, без них, он просто
сплошной цвет без формы суши.

### Реализация — [SolidColorTileProvider.gd](scripts/SolidColorTileProvider.gd)
Новый минимальный `TileProvider`: одна текстура 1×1px на весь слой (все
тайлы любого z/x/y возвращают одну и ту же текстуру) — красить каждый пиксель
мира по отдельности не нужно, один пиксель растягивается на любой размер
тайла. `set_color()` обновляет цвет ЖИВЬЮ (`_tex.update(_img)`) — все уже
созданные спрайты сразу видят новый цвет, т.к. делят один и тот же `_tex`,
без пересоздания спрайтов.

### Найденные по пути баги
- **`_make_tile` не поддерживал отрицательный `z_index`** — сигнатура
  использовала sentinel `z_index_override: int = -1` ("не задан"), поэтому
  первая попытка дать слою V явный `z_index = -10` (заведомо ниже всех)
  тихо игнорировалась (проверка `>= 0` считала -10 "не заданным" и подставляла
  `layer_idx`). Sentinel заменён на `1000000000` — отрицательные z_index
  явно поддерживаются.
- **Вставка нового слоя в середину `_ready()` сломала клавишу `8`** —
  добавление слоя V вторым элементом массива `_layers` (сразу после
  "Спутник") сдвинуло числовые индексы всех слоёв после него на +1; часть
  клавиш (`1`/`6`/`0`/`-`/`=`/`8`/`C`) завязана на ЖЁСТКИЕ индексы в массиве
  (исторически, для самых старых слоёв), а не на переменные — `8` вместо
  "Провинции" стала открывать "Реки". Исправлено (слой V перенесён в САМЫЙ
  КОНЕЦ `_ready()`) и задокументировано отдельным правилом в CLAUDE.md
  ("Новые слои в TileMapViewer.gd — добавлять СТРОГО в конец `_ready()`") —
  чтобы больше не повторилось ни с одним будущим слоем.

### Этап 1 — плоский цвет
Слой V, `z_index = -10` (константа `OCEAN_V_Z_INDEX`, заведомо ниже любого
существующего слоя в проекте) — гарантированно самый нижний независимо от
порядка создания. Цвет заливки — тот же, что у мелководья (`#36b2dc`,
`OCEAN_V_COLOR`), по прямой просьбе пользователя, чтобы дыры в данных не
выглядели чёрным провалом.

### Этап 2 — глубина/мелководье поверх V
Изначально пробовали НОВЫЙ подход — глубина ДИСКРЕТНЫМИ уровнями (8 полос,
каждая со своим цветом и переключателем вкл/выкл, отдельный шейдер
`sea_depth_levels.gdshader` с `level_bounds[7]`/`level_colors[8]`/
`level_enabled[8]`) вместо непрерывного градиента слоя 2. По прямой просьбе
пользователя ОТКАЧЕНО обратно — вместо этого сделана **точная копия** того,
что уже есть у слоя 2 (тот же `sea_depth_zones.gdshader`, те же
`OCEAN_DEPTH_DEFAULT_*`/`OCEAN_SHALLOW_DEFAULT_*` дефолты, та же панель
1-в-1, просто на СВОИХ независимых материалах/спрайтах). Файл
`sea_depth_levels.gdshader` удалён как мёртвый код.
- **Панель слоя V** — независимая от слоя 2, размещена в свободном месте
  справа (x:960-1416), не пересекается ни с одной другой панелью (учтён
  прошлый баг сессии: пересекающиеся `Control`-панели в `$UI` блокируют клики
  по нижней панели — см. более раннюю запись про слой "C").
- **Справка "Управление"/"Слои" убрана из [Main.tscn](scenes/Main.tscn)
  полностью** (узел `Hints`) — по прямой просьбе пользователя, устарела
  (список клавиш давно не совпадал с реальным набором слоёв).
- **z_index мелководья слоя V поднят до `21`** (явное число, не
  `OCEAN_V_Z_INDEX + N`) — по прямой просьбе пользователя ТОЛЬКО полоса
  мелководья (не глубина) должна рисоваться ПОВЕРХ провинций (`z_index=20`,
  слой "Области", клавиша `8`), а не под ними, как остальная часть V.
- **Базовая заливка V синхронизирована с цветом мелководья ЖИВЬЮ** — по
  прямой просьбе пользователя, ползунок цвета мелководья в панели V теперь
  одновременно двигает и `SolidColorTileProvider.set_color()` (через
  чекбокс-переключатель этой связки, можно отключить не трогая сам
  ползунок).
- **Пипетка** — кнопка `🖉` рядом с каждым из 4 цветовых полей панели V
  (мелководье/шельф/склон/глубины). Жмём — следующий клик по карте берёт
  РЕАЛЬНО ОТРИСОВАННЫЙ цвет пикселя под курсором
  (`get_viewport().get_texture().get_image().get_pixel()`) и подставляет в
  этот `ColorPickerButton`, эмитируя `color_changed` вручную (программная
  установка `.color` сама сигнал не шлёт). Только у панели слоя V, не у
  слоя 2.

## Мелководье и глубина: x8 на всю Атлантику через тайлы (2026-07-12/13)

Продолжение темы "x8 упирается в лимит Godot Image" (см. выше) — пользователь
попросил всё-таки досчитать x8 для обоих живых оверлеев ("мелководье" и
"глубина"), способом "тайлы вместо одного файла", который раньше обсуждался
как решение на будущее.

### Почему это НЕ то же самое тайлирование, что у "Мирового океана"
У [bake_world_ocean_tiles.py](scripts/tools/bake_world_ocean_tiles.py) тайлы
— это ГОТОВЫЙ ЦВЕТ, супersample там означает "отрендерить крупнее, потом
LANCZOS-сжать до фиксированного `TILE_PX`". У мелководья/глубины файл хранит
не цвет, а ЧИСЛО (расстояние в км / глубину в метрах), закодированное как
16 бит в каналах R/G — сжимать/интерполировать такой "растр" любым фильтром
(LANCZOS и т.п.) нельзя, это испортит закодированное значение (R и G не
смешиваются как цвет). Поэтому тайлы здесь — это просто НАРЕЗКА уже
посчитанного при x8 растра на куски, без пересжатия; супersample и итоговое
разрешение — одно и то же (нет отдельного шага рендер-крупнее+сжать).

### `build_coast_distance_field.py` — SUPERSAMPLE=8 + нарезка
- Новая логика в `main()`: если `out_w*out_h > TILE_MAX_PX*TILE_MAX_PX`
  (`TILE_MAX_PX=8000`, т.е. лимит 64 млн px на тайл — с большим запасом
  от потолка Godot в 268 млн) — вместо одного PNG сохраняется папка
  `..._tiles/` с кусками `tile_{row}_{col}.png` + `manifest.json`
  (координаты каждого куска в мировых px, диапазон кодирования). Меньшие
  регионы/supersample по-прежнему сохраняются одним файлом (обратная
  совместимость).
- **Найдены и исправлены ДВЕ независимые причины MemoryError на x8**
  (450 Mpx), сверх уже сделанных фиксов из прошлой записи:
  1. После сборки `rgba` в памяти оставались НЕудалёнными все промежуточные
     массивы (`signed_km`, `norm16`, `r`/`g`/`b`/`a`) — лишние ~3 ГБ, не
     нужные на этапе нарезки на тайлы, валили MemoryError на первом же
     `PIL.Image.save()` (внутренняя копия PIL перед записью).
  2. `norm16` был `uint32` без необходимости (значения 0..65535 влезают в
     `uint16`) — лишние ~360 МБ. Кроме того, цепочка
     `clip()`/`subtract()`/`multiply()`/`round()` через промежуточные
     переменные (`signed_km_clamped = ...`) создавала СВОЙ временный
     717-МБ буфер на каждую операцию — переписано на in-place (`out=`
     параметр, переиспользование одного буфера `signed_km` на всех шагах).
- Итог: 21845×20546 px → **9 тайлов** (3×3) в
  `assets/generated/coast_distance_field_west_europe_tiles/`, ~95 МБ
  суммарно, компьютер требует закрывать Godot перед прогоном (см. про
  `vmmem`/WSL выше — тот же класс проблемы с памятью на этой машине).

### `build_sea_depth_west_europe.py` — тот же фикс, ещё более нужный
Этот скрипт держал ЕЩЁ БОЛЬШЕ лишних копий массивов, чем coast_distance_field
до своего фикса (`nan_to_num` без `copy=False`, явный `.copy()`, `uint32`) —
переписан той же техникой (in-place `nan_to_num`/`negative`/`clip`, единый
буфер `combined` на всех шагах, `uint16`, `del` после каждого шага,
`gc.collect()`), плюс та же нарезка на тайлы (переиспользован тот же
`TILE_MAX_PX=8000`). Итог: тоже 9 тайлов в
`assets/generated/sea_depth_west_europe_tiles/`.

### Godot: тайловая загрузка вместо одного Sprite2D
- Новая функция `_load_depth_sprites(material, z_index) -> Array` — грузит
  ЛИБО тайлы по `manifest.json` (если есть), ЛИБО старый одиночный файл
  (фолбэк, обратная совместимость), создаёт по Sprite2D на каждый кусок с
  ОБЩИМ `ShaderMaterial` (шейдер и уравнения одни на все тайлы, общий
  материал безопасен и дёшев — Godot поддерживает шаринг материалов между
  много `CanvasItem`). Аналогичная функция уже была для мелководья
  (`_load_shallow_water_sprites`, тот же паттерн, добавлена в этой же сессии
  чуть раньше при первом переходе мелководья на тайлы).
- Переменные-одиночные спрайты (`_ocean_depth_sprite`, `_ocean_v_depth_sprite`,
  `_ocean_shallow_sprite`, `_ocean_v_shallow_sprite`) заменены на массивы
  (`_ocean_depth_sprites` и т.п.) — синхронизация видимости в `_process`
  теперь через `for spr in массив: spr.visible = ...`.
- Используется и слоем "2", и слоем "V" — оба зовут одну и ту же

### 1. Битая кодировка имён — найдена и починена в источнике
`assets/provinces.json` содержал сотни имён с "двойной UTF-8" порчей
(`Entre RÃ­os` вместо `Entre Ríos`, `SÃ¸r-TrÃ¸ndelag` вместо `Sør-Trøndelag`)
— баг тянулся из промежуточного `_work/ne_10m_admin_1_states_provinces.geojson`
(сам `.dbf`/`.cpg` корректны, UTF-8; порча возникла при разовой конвертации
shapefile → geojson вне репозитория). Раньше это считалось "не багом, а
особенностью" — в `patch_sevilla_coastal_access.py`/`build_province_cities_iberia.py`/
`build_regions_iberia.py` были прямые комментарии "не опечатка, так и должно
быть" и сами строковые константы содержали битые имена (`"CÃ¡diz"`,
`"La CoruÃ±a"`).
- Фикс — `_fix_mojibake()` в
  [build_provinces.py](scripts/tools/build_provinces.py): при чтении имени
  пробует `s.encode("latin-1").decode("utf-8")`, при неудаче возвращает
  строку как есть (безопасно для нормального ASCII).
- Все строковые константы в трёх скриптах, которые ссылались на провинции по
  битому имени, приведены к нормальным именам (`"Cádiz"`, `"La Coruña"`,
  `"Bragança"`, `"Córdoba"` и т.д.), комментарии-пояснения "не опечатка"
  переписаны на актуальные.
- Починка имён НЕ меняет `legacy_id` (он строится из ASCII-slug, который и
  раньше отбрасывал не-ASCII символы одинаково для битого и нормального
  варианта) — значит перегенерация не ломает существующие ссылки на
  legacy_id нигде в проекте.

### 2. Стабильный ID провинции: `province:<numeric_id>`
Раньше ID провинции зависел от классификации родителя
(`province:world:entre_r_os`, `province:iberia:andalusia:sevilla`) — если
регион переклассифицировать, по логике документа пришлось бы либо ломать
ID, либо жить с устаревшим путём в идентификаторе. Заменено на
`province:<numeric_id>` (Севилья = `province:2839`), который никогда не
меняется:
- [scripts/tools/build_map_architecture_v1.py](scripts/tools/build_map_architecture_v1.py)
  переписан: генерирует `assets/map_geometry/provinces.json` (только
  геометрия), `assets/game_data/provinces.json` (паспорт),
  `assets/game_data/regions.json`/`macroregions.json` (статичная
  классификация), `assets/scenarios/1444/province_state.json` (сценарное
  состояние: владелец/контролёр/культура/религия/население/
  `province_buildings`).
- Новый постоянный реестр номеров
  [assets/migrations/province_numeric_id_registry.json](assets/migrations/province_numeric_id_registry.json) —
  `legacy_id -> numeric_id`, номер выдаётся один раз навсегда и не
  переиспользуется даже после удаления провинции (`next_numeric_id`
  монотонно растёт). При перегенерации существующие провинции сохраняют
  тот же номер (`new=0` в выводе скрипта, если состав клеток не менялся).
- Новый файл миграций
  [assets/migrations/map_id_aliases.json](assets/migrations/map_id_aliases.json) —
  4029 записей старый ID → новый (`province:iberia:andalusia:sevilla` →
  `province:2839` и т.п.), только дописывается, ничего не удаляется.
- `region_id` в паспорте — источник истины; `macroregion_id` — вычисляемый
  кэш (берётся из `regions.json`), проверяется валидатором на
  рассинхронизацию.
- Во все JSON-обёртки добавлен `schema_version`/`content_version`
  (`geometry_version` у геометрии, `map_content_version` у сценария).
- В паспорт добавлено поле `slug` — ASCII-транслитерация имени с реальной
  разбивкой диакритики (`unicodedata.normalize("NFKD")`, а не простое
  отбрасывание не-ASCII символов, как раньше в `fallback_province_id`) —
  `Entre Ríos` → `entre_rios`, `Sør-Trøndelag` → `sortrondelag`.
- В сценарии `"buildings": []` заменено на `"province_buildings": {}` — по
  документу здания разных уровней (клетка/город/провинция) не должны
  смешиваться в одном плоском списке; провинциальный уровень заведён,
  городской/клеточный — не заведены (нет ещё соответствующих механик).

### 3. `validate_map_ids.py` расширен по чек-листу документа (§24)
Раньше проверял только уникальность id и существование родителей по
`parent`-полям. Теперь дополнительно:
- уникальность `numeric_id`/`legacy_id` (не только `id`);
- формат ID по уровням через регулярки (`^province:[0-9]+$`,
  `^region:[a-z0-9_]+:[a-z0-9_]+$`, `^macroregion:[a-z0-9_]+$`);
- совпадение набора провинций и полей (`numeric_id`/`legacy_id`) между
  геометрией и паспортом;
- иерархия: `macroregion_id` провинции обязан совпадать с `macroregion_id`
  её `region_id` (а не быть независимым полем);
- запрещённые динамические поля в паспорте/геометрии (`owner_country_id`,
  `culture_id`, `population`, `buildings`, `zone_id` и т.п.) и запрещённые
  статические поля в сценарии (`rings`, `bbox`, `region_id`);
- целостность реестра numeric_id (номер не выдан дважды, `next_numeric_id`
  больше любого выданного, паспорт не расходится с реестром);
- aliases не указывают в никуда и не совпадают с ныне существующим id.
Итог прогона на реальных данных — `ID VALIDATION OK`.

Первый квадратный MVP-прогон был заменён на Voronoi-нарезку после визуальной
проверки слоя `9`: клетки больше не обязаны быть квадратами. Следующим
визуальным проходом к Voronoi-рёбрам добавлено детерминированное искривление:
рёбра уплотняются и проходят через общее поле смещения, поэтому соседние клетки

заливки у морских клеток нет, при клике выделяется только граница. Береговые
границы морских клеток не рисуются: генератор пишет `brd_open` только для
внутренних water-water рёбер, чтобы чёрная линия не наслаивалась на сушу.
Маска морских клеток синхронизирована с видимой водой слоя `2`: геометрия
строится по `world_ocean + 2 км в сторону суши`, профиль генерации
`water_profile:jittered_voronoi_coast_margin_2km_mvp`. Для слоя `9` добавлена
сворачиваемая панель настроек, видимая только при включённом слое: цвет/альфа
заливки, цвет/альфа/толщина/размытие контура, а также отдельные цвет/толщина/
размытие контура выделенной морской клетки.

Текущий тестовый прогон: 62 морские клетки, 128 переходов, 159 связей с берегом.
`assets/migrations/water_cell_ids.json` намеренно НЕ создан:
документ прямо говорит заводить реестр только после стабилизации геометрии.
