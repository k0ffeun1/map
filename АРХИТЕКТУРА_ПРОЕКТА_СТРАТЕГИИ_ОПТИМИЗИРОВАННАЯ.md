# Архитектура проекта глобальной стратегии

## Максимально оптимизированная архитектура карты, симуляции и интерфейса

Документ фиксирует архитектуру проекта для глобальной пошаговой стратегии с физической картой, клетками, провинциями, регионами, городами, морскими зонами, движением юнитов, логистикой, экономикой и запечёнными визуальными слоями карты.

Главная цель архитектуры — не просто «чтобы работало», а чтобы проект можно было расширять годами без превращения кода в хаос.

---

# 1. Главная идея архитектуры

Игра должна быть разделена на несколько независимых слоёв:

```text
Визуал карты
Данные карты
Состояние партии
Системы симуляции
AI
UI
Сохранения
```

Главный принцип:

```text
Godot показывает игру.
Логика игры живёт отдельно от сцен, кнопок, картинок и анимаций.
```

То есть Godot отвечает за:

```text
отрисовку карты
клики мышкой
окна интерфейса
анимации юнитов
подсветку клеток
визуальные эффекты
```

А игровое ядро отвечает за:

```text
клетки
провинции
города
площадь
население
экономику
движение
логистику
войну
события
AI
```

Нельзя смешивать эти вещи в одном `GameManager`.

# 2. Общая схема проекта

```text
Content / Balance Data
        ↓
Static World Data
        ↓
Runtime World State
        ↓
Simulation Systems
        ↓
Events / Results
        ↓
UI + Map Renderer + Animations
```

## 2.1 Content / Balance Data

Это таблицы баланса и правила:

```text
рельефы
покровы
почвы
климаты
ресурсы
освоения
инфраструктура
модификаторы движения
модификаторы еды
модификаторы населения
модификаторы торговли
модификаторы снабжения
```

Пример:

```json
{
  "hills": {
    "defense_value": 20,
    "movement_cost": 1.25,
    "pasture_potential": 20,
    "vineyard_potential": 15,
    "road_cost": 1.25
  }
}
```

Важно: модификаторы должны лежать в таблицах, а не быть зашитыми в код.

## 2.4 Cache

Кэш — это заранее посчитанные значения, чтобы игра не пересчитывала всё каждый кадр.

```gdscript
CellCache {
  cell_id

  food_potential
  pasture_potential
  forest_potential
  mining_potential
  settlement_potential

  current_food_output
  current_resource_output
  trade_value
  economic_value

  defense_value
  supply_limit
  attrition_risk
  movement_base_cost
}
```

Кэш пересчитывается только когда что-то изменилось:

```text
построили дорогу
сменили освоение
изменилась власть
появилось разорение
город подключил клетку
клетка попала в засуху
появился мост
изменилась инфраструктура
```

Главное правило оптимизации:

```text
Не пересчитывать всю карту, если изменилась одна клетка.
```

# 3. Карта как граф

Визуально карта выглядит как набор полигонов, но логически это граф:

```text
клетки = узлы
переходы между клетками = рёбра
```

Это фундамент для движения, снабжения, торговли, AI и войны.

```gdscript
MapGraph {
  cells[]
  transitions[]
  adjacency[cell_id] = transition_ids[]
}
```

Переход между клетками:

```gdscript
TransitionStatic {
  id
  from_cell_id
  to_cell_id

  distance_km
  border_length_km

  transition_type
  allowed_unit_types

  has_river_crossing
  has_bridge
  has_mountain_pass
  has_sea_lane
  has_road_connection

  base_land_cost
  base_sea_cost
}
```

Главная идея:

```text
Движение считается не по клетке, а по переходу между клетками.
```

Это решает проблему огромных клеток, гор, Сибири, пустынь и океанов.

# 4. Площадь клеток

Площадь надо считать и для суши, и для моря.

## 4.1 Сухопутная клетка

Площадь влияет на:

```text
потенциал населения
пашню
пастбища
лес
рудники
контроль территории
локальную экономику
```

Но площадь нельзя использовать линейно.

Правильнее:

```text
area_factor = sqrt(area_km2 / 1000)
area_factor = clamp(area_factor, 0.4, 4.0)
```

То есть большая клетка даёт больше потенциала, но не становится автоматически в 30 раз сильнее.

---

## 4.2 Морская клетка

Площадь морской клетки влияет на:

```text
рыболовный потенциал
масштаб морской зоны
сложность патрулирования
шанс встречи флотов
пиратство
штормовой риск
морское снабжение
торговые маршруты
```

Но для движения флота главное:

```text
distance_km между центрами морских клеток
```

Пример морской клетки:

```gdscript
SeaCellStatic {
  id
  area_km2
  area_factor
  centroid

  water_type
  depth_type
  sea_zone_id

  coast_adjacency
  port_access
  fish_potential
  storm_risk
  piracy_risk
  trade_route_value
  naval_supply_value
}
```

Типы морских клеток:

```text
coastal_sea       // прибрежное море
open_sea          // открытое море
deep_ocean        // глубокий океан
inland_sea        // внутреннее море
strait            // пролив
lake              // озеро
river_estuary     // устье реки
```

# 5. Движение юнитов

Юнит не должен просто «прыгать» из клетки в клетку.

У него должно быть два состояния:

```text
стоит в клетке
находится в пути между клетками
```

```gdscript
UnitState {
  id
  unit_type
  owner_id

  location_type // cell или transition

  current_cell_id

  from_cell_id
  to_cell_id
  transition_id
  travel_progress
  travel_cost_total
  travel_cost_remaining

  movement_points_per_turn
  current_movement_points

  status // idle, marching, fighting, retreating, sieging
}
```

Если переход стоит 12 очков движения, а у армии 4 очка движения за ход:

```text
Ход 1: 4 / 12
Ход 2: 8 / 12
Ход 3: 12 / 12 — армия прибыла
```

На карте это выглядит так:

```text
Ход 0:
[ Горная клетка A ]        [ Горная клетка B ]
        ⚔

Ход 1:
[ Горная клетка A ] ---⚔---- [ Горная клетка B ]
Прогресс: 4/12

Ход 2:
[ Горная клетка A ] ------⚔- [ Горная клетка B ]
Прогресс: 8/12

Ход 3:
[ Горная клетка A ] -------- [ Горная клетка B ]
                                      ⚔
```

# 6. Формулы движения

## 6.1 Суша

```text
land_cost =
  clamp(
    distance_km / 30
    × relief_modifier
    × cover_modifier
    × road_modifier
    × weather_modifier
    × state_modifier,
    0.5,
    12
  )
```

Пример для огромной горной клетки:

```text
distance_km = 120
base = 120 / 30 = 4
mountains_modifier = 2.2
forest_modifier = 1.3
winter_modifier = 1.25

transition_cost = 4 × 2.2 × 1.3 × 1.25 = 14.3
```

Можно ограничить:

```text
max_land_transition_cost = 12 или 16
```

---

## 6.2 Горы и перевалы

Горы не должны быть просто «дорогими равнинами».

У переходов должны быть типы:

```text
обычный горный переход
перевал
дорога через перевал
непроходимые высокие горы
```

Пример:

```text
Горы без перевала: transition_cost = 14
Горный перевал: transition_cost = 7
Дорога через перевал: transition_cost = 4
Высокие горы без прохода: transition_allowed = false
```

---

## 6.3 Море

```text
sea_cost =
  clamp(
    distance_km / 80
    × water_type_modifier
    × weather_modifier
    × navigation_modifier
    × current_modifier,
    0.3,
    15
  )
```

Пример океанского перехода:

```text
distance_km = 500
base = 500 / 80 = 6.25
deep_ocean_modifier = 1.3
storm_modifier = 1.4
early_navigation_modifier = 1.3

sea_transition_cost = 6.25 × 1.3 × 1.4 × 1.3 ≈ 14.8
```

Флот с 5 очками движения будет идти 3 хода.

# 7. Запечённая карта

Для производительности статичные визуальные слои карты правильно запекать картинками.

Но важно:

```text
Запекать можно визуал.
Нельзя запекать игровую логику.
```

Правильная схема:

```text
Картинка карты = внешний вид
Данные карты = настоящая игровая логика
```

## 7.3 Не одна огромная картинка, а тайлы

```text

```

```text

```


# 8. ID-карта для кликов

Если визуальная карта запечена картинкой, Godot сам не знает, где какая клетка.

Лучшее решение для MVP — невидимая ID-карта.

ID-карта — это специальная картинка, где каждая клетка закрашена уникальным цветом.

```text
клик мыши
↓
координата карты
↓
пиксель ID-карты
↓
цвет
↓
cell_id
```

Пример:

```text
клетка 1523 = RGB(0, 5, 243)
```

Файлы:

```text
visual_map_tiles/
  terrain_0_0.png

id_map_tiles/
  id_0_0.png
```

Плюсы:

```text
очень быстро
не нужны тысячи CollisionPolygon
легко определить клетку под мышью
хорошо работает с запечённой картой
```

Минусы:

```text
нужно аккуратно генерировать ID-карту
координаты visual map и id map должны идеально совпадать
```

Для проекта это оптимальное решение.

# 9. Визуальная архитектура карты в Godot

Не надо делать каждую клетку отдельной сценой.

Плохой вариант:

```text
20 000 клеток = 20 000 Node2D
каждый Node сам считает, сам рисует, сам ловит мышку
```

Правильный вариант:

```text
MapRenderer
  рисует карту тайлами
  отдельно рисует overlay
  отдельно рисует границы
  отдельно рисует юниты
  отдельно рисует маршруты
```

Структура:

```text
MapRoot
  TerrainTiles
  ReliefTiles
  WaterTiles
  StaticBorderLayer
  DynamicOverlayLayer
  RouteLayer
  CityMarkers
  UnitMarkers
  SelectionLayer
```

Скрипты:

```text
MapRenderer.gd
MapTileLoader.gd
MapSelectionController.gd
IdMapPicker.gd
OverlayRenderer.gd
RouteRenderer.gd
UnitRenderer.gd
CityMarkerRenderer.gd
```

```text
↓

↓
```

# 12. Политика отдельно от географии

Нельзя смешивать регион и владельца региона.

```text
Галисия как регион = география
Кастилия контролирует Галисию = политика
```

Географический регион остаётся Галисией независимо от того, кто им владеет.

Для политического объекта лучше использовать нейтральный термин:

```text
Polity
```

```gdscript
PolityState {
  id
  name
  capital_city_id

  treasury
  manpower
  legitimacy
  stability

  owned_cell_ids
  controlled_cell_ids

  diplomacy_state
  laws
  institutions
}
```

Клетка хранит:

```text
owner_polity_id
controller_polity_id
```

## 13.1 TurnManager

Отвечает за порядок хода.

```gdscript
TurnManager {
  start_turn()
  collect_player_orders()
  collect_ai_orders()
  resolve_orders()
  process_world_tick()
  end_turn()
}
```

Пример порядка хода:

```text
1. Игрок отдаёт приказы
2. AI отдаёт приказы
3. Движение
4. Бои / столкновения
5. Осады
6. Производство еды и ресурсов
7. Население
8. Торговля
9. События
10. Обновление кэшей
11. UI получает результат
```

---

## 13.2 MovementSystem

Отвечает за движение.

```gdscript
MovementSystem {
  calculate_transition_cost(unit, transition)
  start_movement(unit, target_cell)
  advance_travel(unit)
  finish_travel(unit)
  cancel_travel(unit)
}
```

Работает с:

```text
MapGraph
TransitionStatic
UnitState
```

# 30. Godot: `class_name` и `preload` для скриптовых слоёв

Дата заметки: 2026-07-13.

Для зрелых, постоянных систем проекта нужно предпочитать `class_name`.

Примеры таких систем:

```text
ProvinceCityMarkersLayer
SeaLabelsLayer
CellCatalog
будущий полноценный редактор клеток
будущий слой юнитов
будущая система маршрутов
```

Причина: `class_name` делает скрипт нормальным типом проекта. Это даёт читаемость, типизацию, автодополнение, удобный поиск и меньше неявных `preload`-констант.

```gdscript
class_name ProvinceCityMarkersLayer
extends Node2D
```

Для временных, экспериментальных или локальных helper-инструментов допустим `preload` без `class_name`.

Пример: черновой карандаш границ клеток слоя `C`, пока это только инструмент разметки, а не зрелая часть редактора.

```gdscript
const CELL_BOUNDARY_DRAFT_LAYER_SCRIPT := preload("res://scripts/CellBoundaryDraftLayer.gd")
var layer: Node2D = CELL_BOUNDARY_DRAFT_LAYER_SCRIPT.new()
```

Важно не забыть: когда инструмент становится постоянной частью архитектуры, его нужно перевести на `class_name`, проверить уникальность имени, `.uid`, запуск Godot и отсутствие зависаний загрузки карты.

По скорости игры разница между `class_name` и `preload` почти не является узким местом. На FPS карты это практически не влияет. На запуск проекта влияние обычно тоже небольшое: `class_name` добавляет регистрацию глобального класса в Godot, `preload` загружает конкретный скрипт там, где он явно нужен. Существенные задержки запуска чаще дают большие JSON/PNG/тайлы, генерация, кэш, шейдеры и создание множества узлов, а не сам факт `class_name`.

Архитектурное правило:

```text
Зрелая система = class_name.
Локальный черновик/эксперимент = preload.
После стабилизации черновик переводится в class_name.
```

Дата заметки: 2026-07-13.

Уровень `zone` не используется. Он удаляется из данных и кода, поэтому новые
системы не должны добавлять `zone_id`, `parents.zone`, `zone_*` и отдельные
проверки под зоны.

Постоянные игровые сущности карты должны иметь стабильный id, уникальный не
только внутри файла, но и глобально между уровнями. Не полагаться на позицию
объекта в JSON-массиве.

Рекомендуемые префиксы:

```text
cell_*         — клетка, минимальная физическая земля
province_*     — провинция / область
region_*       — историко-географический регион
macroregion_*  — крупный надрегион
city_*         — город
sea_*          — море / крупный водный объект
route_*        — маршрут / переход
unit_*         — юнит
```

Текущий слой `assets/provinces.json` уже использует стабильные id вида
`spain__sevilla`, `netherlands__groningen`. Это допустимое переходное состояние:
id стабильные и не позиционные. При следующей большой миграции можно привести
их к явному префиксу уровня, например `province_spain_sevilla`, через таблицу
миграции/алиасов, а не молча переименовывать в сохранениях.

Правило связей:

```json
{
  "id": "cell_iberia_000123",
  "level": "cell",
  "parents": {
    "province": "province_spain_sevilla",
    "region": "region_iberia_andalucia",
    "macroregion": "macroregion_iberia_south"
  }
}
```

Если используется старое поле `parent_id`, оно допустимо только как временное
поле рядом с более явным `parents`. Для зрелой системы лучше хранить родителей
по уровням.

Проверка контракта:

```text
scripts/tools/validate_map_ids.py
```

Валидатор должен проверять:

```text
нет пустых id
нет дублей там, где они не разрешены явно
нет глобальных конфликтов id между уровнями
все parent-ссылки указывают на существующие id
нет ссылок на удалённый уровень zone
```

Архитектурное правило:

```text
id — это стабильный контракт сохранений, кликов, алиасов и связей.
геометрия может меняться, смысл id не должен меняться молча.
```

# 32. Целевая архитектура данных карты: геометрия, паспорт, сценарий

Дата заметки: 2026-07-13.

Заложена первая версия зрелой структуры данных карты. Старые игровые слои пока
остаются совместимыми и продолжают читать прежние файлы, но новая архитектура
уже создана рядом с ними.

Главное правило: постоянный id провинции не должен зависеть от текущего
владельца. Испания, Португалия, Франция, оккупация, культура, религия,
население и здания являются состоянием сценария или партии, а не личностью
провинции.

Целевой пример id:

```text
province:iberia:andalusia:sevilla
```

Это значит:

```text
province   — уровень сущности
iberia     — статичная большая география
andalusia  — историко-географический регион
sevilla    — сама провинция
```

## Файлы новой структуры

```text
assets/map_geometry/provinces.json
```

Только форма провинций: `id`, `legacy_id`, `numeric_id`, `bbox`, `rings`.
Это тяжелый слой. Он нужен карте, кликам и рендеру.

```text
assets/game_data/provinces.json
```

Паспорт провинции: `id`, `legacy_id`, `numeric_id`, имя, регион, макрорегион,
рельеф, климат. Здесь не должно быть текущего владельца, текущей культуры,
текущей религии, зданий или населения партии.

```text
assets/game_data/regions.json
assets/game_data/macroregions.json
```

Справочники историко-географических уровней. Уровень `zone` не возвращать:
он удаляется из архитектуры.

```text
assets/scenarios/1444/province_state.json
```

Стартовое состояние сценария: владелец, контролер, культура, религия,
население, здания. Эти данные могут меняться во время игры и в сохранениях.

## Пример: Севилья

Геометрия:

```json
{
  "id": "province:iberia:andalusia:sevilla",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "bbox": [3947.37, 3154.45, 3990.1, 3193.07],
  "rings": []
}
```

Паспорт:

```json
{
  "id": "province:iberia:andalusia:sevilla",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "name": "Sevilla",
  "display_name_ru": "Севилья",
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",
  "terrain_id": "",
  "climate_id": ""
}
```

Состояние сценария:

```json
{
  "province_id": "province:iberia:andalusia:sevilla",
  "owner_country_id": "",
  "controller_country_id": "",
  "culture_id": "",
  "religion_id": "",
  "population": null,
  "buildings": []
}
```

Культура и религия намеренно находятся в сценарии/сейве, а не в паспорте:
они могут меняться во время партии.

## Миграционный принцип

`legacy_id` хранится для связи со старой системой, кликами, слоями и уже
созданными правками. Старые файлы не переименовываются молча.

Новая генерация выполняется скриптом:

```text
scripts/tools/build_map_architecture_v1.py
```

Проверка выполняется скриптом:

```text
scripts/tools/validate_map_ids.py
```

Архитектурное правило:

```text
Старые слои = совместимость.
Новые файлы map_geometry/game_data/scenarios = целевая модель.
Массовый перевод рантайма делается отдельным шагом, после проверки данных.
```

## Инструкция для заполнения регионов

Эту инструкцию можно передать в другой чат или использовать как чеклист для
ручного заполнения JSON.

Задача: заполнить и расширить JSON регионов для новой архитектуры карты.

Целевая структура:

```text
assets/map_geometry/provinces.json
```

Геометрия провинций. Здесь лежат `id`, `legacy_id`, `numeric_id`, `bbox`,
`rings`. `rings` и `bbox` без отдельной задачи не трогать.

```text
assets/game_data/provinces.json
```

Паспорт провинций. Здесь лежат `id`, `legacy_id`, `numeric_id`, `name`,
`display_name_ru`, `region_id`, `macroregion_id`, `terrain_id`, `climate_id`.

```text
assets/game_data/regions.json
```

Историко-географические регионы.

```text
assets/game_data/macroregions.json
```

Крупные статичные макрорегионы.

```text
assets/scenarios/1444/province_state.json
```

Изменяемое стартовое состояние сценария: `owner_country_id`,
`controller_country_id`, `culture_id`, `religion_id`, `population`,
`buildings`.

Важные правила:

```text
уровень zone удалён, его не использовать
не добавлять zone_id, parents.zone, zone_*
страна-владелец не должна быть частью id провинции
культура и религия не должны быть в паспорте провинции
текущий владелец и контролёр не должны быть в паспорте провинции
legacy_id не удалять, он нужен для связи со старой системой
```

Формат id:

```text
province:<macroregion_slug>:<region_slug>:<province_slug>
region:<macroregion_slug>:<region_slug>
macroregion:<macroregion_slug>
```

Примеры:

```text
province:iberia:andalusia:sevilla
region:iberia:andalusia
macroregion:iberia
```

Пример региона:

```json
{
  "id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",
  "name": "Andalusia",
  "display_name_ru": "Андалусия"
}
```

Пример макрорегиона:

```json
{
  "id": "macroregion:iberia",
  "name": "Iberia",
  "display_name_ru": "Иберия"
}
```

Что нужно делать при заполнении:

```text
1. Добавлять нормальные историко-географические регионы в assets/game_data/regions.json.
2. Добавлять крупные статичные макрорегионы в assets/game_data/macroregions.json.
3. В assets/game_data/provinces.json проставлять region_id, macroregion_id и display_name_ru.
4. Не менять rings/bbox в assets/map_geometry/provinces.json без отдельной задачи.
5. Не ломать legacy_id.
6. После правок запускать python scripts\tools\validate_map_ids.py.
```

Ожидаемый результат проверки:

```text
ID VALIDATION OK
```

Главная идея:

```text
Провинция имеет постоянную личность и геометрию.
Регион и макрорегион — статичная историко-географическая принадлежность.
Страна-владелец, культура, религия, население, здания — состояние сценария или сохранения.
```
