# Архитектура регионов, макрорегионов и паспортов провинций

**Проект:** глобальная историческая стратегия  
**Назначение документа:** оценка новой архитектуры карты, выявление рисков и фиксация рекомендуемой структуры данных  
**Статус:** архитектурная рекомендация перед массовым заполнением регионов и провинций

---

# 1. Краткий вывод

Предложенная архитектура в целом правильная.

Главное разделение проведено хорошо:

```text
Геометрия провинции
≠
Постоянный паспорт провинции
≠
Состояние конкретного сценария или сохранения
```

Правильная логика:

```text
Провинция имеет постоянную личность и геометрию.

Регион и макрорегион являются постоянной
историко-географической принадлежностью.

Страна-владелец, контролёр, культура, религия,
население, здания и разорение являются состоянием
конкретного сценария или сохранения.
```

Такой подход подходит для:

- нескольких стартовых дат;
- альтернативных сценариев;
- модификаций;
- сохранений;
- смены владельцев;
- оккупации;
- культурных изменений;
- религиозных изменений;
- миграции населения;
- строительства и разрушения зданий.

Текущую архитектуру можно оценить примерно на:

```text
8/10
```

Главные проблемы находятся не в производительности, а в:

1. стабильности ID;
2. дублировании принадлежности к макрорегиону;
3. отсутствии версий схемы и миграций;
4. не до конца определённой системе владения;
5. смешивании зданий разных территориальных уровней.

После исправления этих пунктов архитектура станет практически окончательной и сможет расширяться годами.

# 2. Текущая целевая структура

## 2.1. Геометрия провинций

```text
assets/map_geometry/provinces.json
```

В файле находятся:

```text
id
legacy_id
numeric_id
bbox
rings
```

Пример:

```json
{
  "id": "province:iberia:andalusia:sevilla",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "bbox": [],
  "rings": []
}
```

Назначение файла:

- хранение полигонов;
- определение границ;
- пространственный поиск;
- обработка кликов;
- построение ID-карты;
- расчёт пересечений;
- подготовка визуального слоя;
- генерация пространственного индекса.

Геометрия не должна зависеть от:

- владельца;
- культуры;
- религии;
- населения;
- сценария;
- даты начала партии.

## 2.2. Паспорт провинций

```text
assets/game_data/provinces.json
```

В файле находятся:

```text
id
legacy_id
numeric_id
name
display_name_ru
region_id
macroregion_id
terrain_id
climate_id
```

Пример:

```json
{
  "id": "province:iberia:andalusia:sevilla",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "name": "Sevilla",
  "display_name_ru": "Севилья",
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",
  "terrain_id": "",
  "climate_id": ""
}
```

Паспорт должен содержать только постоянные свойства провинции.

Паспорт не должен содержать:

```text
owner_country_id
controller_country_id
culture_id
religion_id
population
buildings
devastation
occupation
army_id
city_state
```

---

## 2.3. Регионы

```text
assets/game_data/regions.json
```

Регион — постоянная историко-географическая область.

Пример:

```json
{
  "id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia",
  "name": "Andalusia",
  "display_name_ru": "Андалусия"
}
```

Регион:

- не является страной;
- не зависит от текущего владельца;
- не меняется при войне;
- не меняется при смене династии;
- не должен быть торговым узлом;
- не должен быть военным театром;
- не должен быть временной административной единицей.

---

## 2.4. Макрорегионы

```text
assets/game_data/macroregions.json
```

Макрорегион — крупная статичная географическая область.

Пример:

```json
{
  "id": "macroregion:iberia",
  "name": "Iberia",
  "display_name_ru": "Иберия"
}
```

Макрорегион объединяет несколько соседних регионов.

Он нужен для:

- крупных режимов карты;
- группировки данных;
- UI;
- статистики;
- регионального AI;
- фильтрации событий;
- загрузки частей мира;
- крупных географических модификаторов.

---

## 2.5. Сценарное состояние провинций

```text
assets/scenarios/1444/province_state.json
```

Здесь находятся изменяемые данные:

```text
owner_country_id
controller_country_id
culture_id
religion_id
population
buildings
```

Пример:

```json
{
  "province_id": "province:iberia:andalusia:sevilla",
  "owner_country_id": "country:castile",
  "controller_country_id": "country:castile",
  "culture_id": "culture:andalusian",
  "religion_id": "religion:catholic",
  "population": 42000,
  "buildings": []
}
```

При запуске другого сценария паспорт Севильи остаётся тем же, а состояние загружается другое.

# 3. Что в архитектуре сделано правильно

## 3.1. Геометрия отделена от игровых данных

Это одно из самых важных решений.

Геометрический файл:

```text
assets/map_geometry/provinces.json
```

может быть:

- тяжёлым;
- большим;
- с тысячами точек;
- редко изменяемым;
- подготовленным офлайн;
- позже переведённым в бинарный формат.

Игровой паспорт при этом остаётся лёгким.

Плюсы:

```text
геометрия не загружается системами,
которым нужны только названия и принадлежность;

редактор сценариев не трогает полигоны;

смена владельца не требует изменения карты;

сейвы не содержат rings и bbox;

геометрию можно оптимизировать отдельно.
```

---

## 3.2. Паспорт отделён от состояния партии

Это правильный data-driven подход.

Одна и та же провинция может существовать в сценариях:

```text
1066
1204
1444
1700
1800
альтернативная история
пользовательский мод
```

При этом неизменными остаются:

```text
id
numeric_id
legacy_id
геометрия
название
регион
макрорегион
базовый географический профиль
```

А изменяются:

```text
владелец
контролёр
культура
религия
население
здания
разорение
гарнизон
экономическое состояние
```

---

## 3.3. Страна не входит в ID провинции

Это правильное решение.

Плохо:

```text
province:spain:sevilla
```

Потому что Севилья может:

- сменить владельца;
- стать независимой;
- войти в другое государство;
- оказаться оккупированной;
- существовать в сценарии до появления Испании.

Правильно:

```text
province:iberia:andalusia:sevilla
```

или ещё более стабильно:

```text
province:2839
```

---

## 3.4. Культура и религия вынесены в сценарий

Это тоже правильно.

Культура и религия могут меняться:

```text
ассимиляция
миграция
колонизация
обращение
реформация
изгнание
переселение
война
государственная политика
```

Поэтому они не являются паспортными свойствами провинции.

---

## 3.5. Уровень zone удалён

Удаление `zone` упрощает архитектуру.

Старая длинная лестница:

```text
Province
→ Region
→ Zone
→ Macroregion
→ Superregion
→ Continent
```

создаёт слишком много промежуточных сущностей.

Текущая схема:

```text
Province
→ Region
→ Macroregion
```

намного понятнее.

Если позже понадобятся:

- военные театры;
- торговые области;
- морские бассейны;
- зоны снабжения;
- климатические пояса;
- культурные области;

их лучше делать отдельными независимыми системами.

Пример:

```text
province_region_membership
province_trade_area_membership
province_supply_area_membership
province_military_theater_membership
province_climate_area_membership
```

Не нужно возвращать универсальный `zone`, который пытается решать все задачи одновременно.

# 4. Главный риск: ID провинции зависит от её родителей

Текущий формат:

```text
province:<macroregion_slug>:<region_slug>:<province_slug>
```

Пример:

```text
province:france:pays_de_la_loire:mayenne
```

выглядит удобно, но имеет архитектурную проблему.

Если позже изменится классификация Mayenne:

```text
region:france:pays_de_la_loire
```

на:

```text
region:france:maine
```

то логически придётся изменить и ID провинции:

```text
province:france:pays_de_la_loire:mayenne
```

на:

```text
province:france:maine:mayenne
```

Это может сломать ссылки из:

- сценариев;
- сохранений;
- событий;
- зданий;
- армий;
- торговых маршрутов;
- локализации;
- модов;
- дипломатических систем;
- AI;
- миграций;
- тестов.

Получается противоречие:

```text
Провинция должна иметь постоянную личность,
но её ID зависит от изменяемой классификации.
```

# 5. Рекомендуемый формат ID провинций

## 5.1. Самый надёжный вариант

```text
province:<numeric_id>
```

Пример:

```text
province:2839
```

Паспорт:

```json
{
  "id": "province:2839",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839,
  "slug": "sevilla",
  "name": "Sevilla",
  "display_name_ru": "Севилья",
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

Плюсы:

- ID никогда не меняется;
- не зависит от региона;
- не зависит от макрорегиона;
- не зависит от языка;
- не зависит от владельца;
- не зависит от названия;
- удобен для сейвов;
- удобен для миграций;
- удобен для бинарных данных.

Минус:

```text
province:2839
```

хуже читается глазами, чем полный путь.

Это компенсируется полями:

```text
slug
name
debug_path
display_name_ru
```

---

## 5.2. Компромиссный вариант

```text
province:sevilla_2839
```

Пример:

```json
{
  "id": "province:sevilla_2839",
  "numeric_id": 2839,
  "slug": "sevilla",
  "region_id": "region:iberia:andalusia"
}
```

Плюсы:

- читаемо;
- почти не зависит от родителей;
- ID остаётся уникальным;
- пригодно для ручной отладки.

Минус:

- при переименовании всё равно возникает вопрос, менять ли slug;
- название может иметь несколько вариантов;
- историческое название может измениться.

---

## 5.3. Если текущий формат уже решено оставить

Тогда нужно ввести жёсткое правило:

```text
ID провинции никогда не меняется,
даже если изменился region_id или macroregion_id.
```

Пример:

```json
{
  "id": "province:france:pays_de_la_loire:mayenne",
  "region_id": "region:france:maine",
  "macroregion_id": "macroregion:france"
}
```

Технически это работает, но ID становится семантически устаревшим.

Поэтому, пока карта ещё не заполнена полностью, лучше отвязать ID провинции от родителей.

# 6. ID регионов и макрорегионов

Для регионов текущая схема приемлема:

```text
region:<macroregion_slug>:<region_slug>
```

Пример:

```text
region:iberia:andalusia
```

Для макрорегионов:

```text
macroregion:<macroregion_slug>
```

Пример:

```text
macroregion:iberia
```

Но для них тоже нужно правило:

```text
после публикации сценариев и сейвов ID не переименовываются напрямую;
переименование делается через таблицу aliases и миграцию.
```

---

# 7. Дублирование macroregion_id

Сейчас провинция содержит:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

А регион содержит:

```json
{
  "id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

Таким образом, макрорегион можно получить двумя путями:

```text
Province → Macroregion
```

и:

```text
Province → Region → Macroregion
```

Это создаёт риск рассинхронизации.

Ошибочный пример:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:france"
}
```

---

# 8. Как лучше хранить macroregion_id

## Вариант A — нормализованный источник

В `provinces.json` хранится только:

```json
{
  "region_id": "region:iberia:andalusia"
}
```

Макрорегион вычисляется:

```text
province.region_id
→
region.macroregion_id
```

Плюсы:

- один источник истины;
- невозможно рассинхронизировать;
- проще редактировать;
- проще мигрировать.

Минус:

- нужен дополнительный lookup.

Для нескольких тысяч провинций этот lookup не является проблемой.

---

## Вариант B — оставить macroregion_id как кэш

Можно оставить оба поля:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

Но считать `macroregion_id` не самостоятельной информацией, а денормализованным кэшем.

Валидатор обязан проверять:

```python
province.macroregion_id == regions[province.region_id].macroregion_id
```

При сборке `macroregion_id` можно генерировать автоматически.

---

## Рекомендация

Для редактируемых исходников:

```text
region_id — источник истины.
```

Для runtime-данных:

```text
region_index
macroregion_index
```

Оба числовых индекса можно хранить для скорости.

---

# 9. Numeric ID и runtime index

`numeric_id` нужно сохранить.

Но нельзя использовать его как индекс плотного массива.

Пример разреженных ID:

```text
2839
3974
8401
12552
```

Плохо:

```csharp
var provinces = new Province[12553];
```

если реально провинций только несколько тысяч.

Лучше:

```text
numeric_id 2839  → runtime_index 0
numeric_id 3974  → runtime_index 1
numeric_id 8401  → runtime_index 2
```

---

## 9.1. Назначение numeric_id

```text
numeric_id:
- постоянный;
- уникальный;
- хранится в контенте;
- используется для миграций;
- используется в ID-карте;
- не переиспользуется после удаления провинции.
```

---

## 9.2. Назначение runtime_index

```text
runtime_index:
- создаётся при сборке или загрузке;
- плотный;
- начинается с 0;
- используется в массивах;
- может меняться между версиями;
- не является единственным идентификатором в сейве.
```

Пример runtime-массивов:

```csharp
int[] provinceRegionIndex;
int[] provinceMacroregionIndex;
int[] provinceOwnerIndex;
int[] provinceControllerIndex;
int[] provincePopulation;
```

Для производительности это важнее, чем формат строкового ID.

---

# 10. Legacy ID

`legacy_id` нельзя ломать.

Он нужен для связи:

```text
новая архитектура
↔
старая система
```

Пример:

```json
{
  "id": "province:2839",
  "legacy_id": "spain__sevilla",
  "numeric_id": 2839
}
```

Правила:

```text
legacy_id не переименовывается;
legacy_id не переиспользуется;
legacy_id должен быть уникальным;
legacy_id должен совпадать в геометрии и паспорте;
legacy_id не является основным runtime-ID.
```

Но `legacy_id` не заменяет будущую систему миграций новой архитектуры.

# 11. Версии схемы

Каждый крупный файл должен содержать версию структуры.

Не рекомендуется хранить только массив:

```json
[

  {}
]
```

Лучше:

```json
{
  "schema_version": 1,
  "content_version": "2026.07.13",
  "provinces": []

```

# 12. Миграции и aliases

Нужно заранее создать:

```text
assets/migrations/map_id_aliases.json
```

Пример:

```json
{
  "province:iberia:andalusia:seville": "province:2839",
  "province:spain:andalusia:sevilla": "province:2839",
  "region:spain:andalusia": "region:iberia:andalusia"
}
```

При загрузке старого сейва:

```text
старый ID
↓
поиск в aliases
↓
актуальный ID
```

Aliases нужны для:

- исправления опечаток;
- переименования региона;
- смены формата ID;
- совместимости модов;
- загрузки старых сценариев;
- загрузки старых сохранений.

# 13. Локализация

На текущем этапе поле:

```json
"display_name_ru": "Севилья"
```

допустимо.

Но при появлении нескольких языков паспорт начнёт разрастаться:

```json
{
  "display_name_ru": "Севилья",
  "display_name_en": "Seville",
  "display_name_es": "Sevilla",
  "display_name_fr": "Séville"
}
```

Лучше постепенно перейти к ключу локализации:

```json
{
  "name": "Sevilla",
  "localization_key": "province.2839.name"
}
```

Файлы:

```text
assets/localization/ru/provinces.json
assets/localization/en/provinces.json
assets/localization/es/provinces.json
```

Пример:

```json
{
  "province.2839.name": "Севилья"
}
```

Для текущего этапа можно оставить `display_name_ru`, но архитектурно лучше предусмотреть `localization_key`.

# 14. Правила историко-географической классификации

Перед массовым заполнением нужно создать документ:

```text
REGION_TAXONOMY.md
```

В нём зафиксировать единые правила.

---

## 14.1. Определение региона

```text
Регион — средняя историко-географическая область,
состоящая из нескольких игровых провинций.

Регион не зависит от текущих государственных границ.
Регион не меняется в сценарии.
Регион не является временной административной единицей.
```

Примеры:

```text
Галисия
Андалусия
Бретань
Нормандия
Ломбардия
Тоскана
Бавария
Фландрия
```

---

## 14.2. Определение макрорегиона

```text
Макрорегион — крупная статичная географическая область,
объединяющая несколько соседних регионов.
```

Примеры:

```text
Иберия
Франция
Британские острова
Италия
Балканы
Скандинавия
Центральная Европа
Малая Азия
```

---

## 14.3. Обязательные правила

```text
1. Каждая провинция имеет ровно один основной region_id.

2. Каждый регион имеет ровно один macroregion_id.

3. Регионы не перекрываются.

4. Макрорегионы не перекрываются.

5. Государственная принадлежность не влияет на классификацию.

6. Текущий владелец не влияет на ID.

7. Культура и религия не определяют принадлежность напрямую.

8. Спорные случаи решаются единым редакторским правилом.

9. Торговые и военные области не смешиваются с регионами.

10. Временные административные единицы не являются регионами карты.
```

# 15. Дополнительные связи и теги

Иногда провинция может одновременно относиться к нескольким смысловым областям:

```text
атлантическое побережье
Средиземноморье
горная дуга
торговый бассейн
историческая марка
речная система
```

Не нужно для этого вводить несколько `region_id`.

Лучше использовать отдельные теги или каталоги:

```json
{
  "tags": [
    "atlantic_coast",
    "historical_march",
    "mediterranean_trade"
  ]
}
```

Но добавлять такие теги нужно только тогда, когда появилась реальная механика, которая их использует.

# 16. Terrain и climate

Текущие поля:

```text
terrain_id
climate_id
```

подходят только в том случае, если провинция является минимальной физической единицей.

Если внутри провинции существуют отдельные клетки с разным рельефом, один `terrain_id` будет слишком грубым.

Пример одной провинции:

```text
побережье
равнины
холмы
горы
лес
река
```

В этом случае лучше:

```json
{
  "dominant_terrain_id": "terrain:hills",
  "climate_profile_id": "climate:mediterranean"
}
```

Разделение:

```text
Cell:
точный рельеф;
точный покров;
точный климат;
точная влажность.

Province:
доминирующий рельеф;
общий климатический профиль;
агрегированные значения для UI и AI.

Region:
широкий историко-географический профиль.
```

Если провинция и есть минимальная клетка, поля можно оставить без переименования.

# 18. Источник истины для владельца и контролёра

Нужно заранее определить, где хранится юридический владелец.

Возможны два варианта.

---

## Вариант A — владение на уровне провинции

```text
ProvinceState является источником истины.

Все клетки внутри провинции наследуют owner_country_id.
```

Подходит, если провинция передаётся целиком.

---

## Вариант B — владение на уровне клетки

```text
CellState является источником истины.

Владелец провинции вычисляется как агрегат
или хранится как административная принадлежность.
```

Подходит для очень детальной системы контроля.

---

## Рекомендуемый гибрид

```text
Юридический владелец:
ProvinceState.owner_country_id

Фактический военный контроль:
ProvinceState.controller_country_id
или CellOccupationState для детальной оккупации.
```

Например:

```text
Севилья юридически принадлежит Кастилии,
но фактически контролируется Арагоном.
```

```json
{
  "province_id": "province:2839",
  "owner_country_id": "country:castile",
  "controller_country_id": "country:aragon"
}
```

Если нужна частичная оккупация клеток, она должна быть отдельным состоянием, а не вторым независимым юридическим владельцем.

# 20. JSON как источник, BIN как runtime-формат

Для разработки JSON подходит хорошо:

```text
читается человеком;
удобно редактировать;
удобно хранить в Git;
удобно проверять diff;
удобно использовать в скриптах;
удобно делать моддинг.
```

Но в релизе тяжёлые файлы лучше компилировать:

```text
JSON source
↓
validation
↓
runtime indices
↓
binary export
↓
Godot/C# loading
```

Пример:

```text
assets/game_data/provinces.json
↓
assets/generated/world_catalog.bin
```

```text
assets/map_geometry/provinces.json
↓
assets/generated/province_geometry.bin
```

---

# 21. Что реально влияет на оптимизацию

Само разделение на:

```text
regions.json
macroregions.json
provinces.json
```

почти не влияет на FPS.

Оно улучшает:

- архитектуру;
- поддержку сценариев;
- редактирование;
- тестирование;
- моддинг;
- отсутствие дублирования;
- надёжность ссылок.

Для производительности важнее:

```text
строки преобразуются в числовые индексы;

данные хранятся в плотных массивах;

геометрия загружается отдельно;

создаётся spatial index;

используются бинарные runtime-файлы;

не выполняются строковые lookup в каждом игровом тике;

состояние хранится отдельно от статики;

обновляются только dirty-объекты.
```

# 22. Runtime-индексы

При загрузке:

```text
province:2839
→ province_index 0

region:iberia:andalusia
→ region_index 12

macroregion:iberia
→ macroregion_index 2
```

Симуляция использует:

```csharp
provinceRegionIndex[provinceIndex]
provinceMacroregionIndex[provinceIndex]
provinceOwnerIndex[provinceIndex]
provincePopulation[provinceIndex]
```

Строковые ID нужны:

- при загрузке;
- при сохранении;
- в JSON;
- в логах;
- в модах;
- в инструментах.

Внутри частых расчётов лучше использовать числовые индексы.

# 23. Обратные индексы

provinces_by_region

provincesByRegion[regionIndex] = [provinceIndex, ...]

- получить список провинций;
- агрегировать статистику;
- дать AI список территорий.

# 24. Требования к валидатору

После правок должен запускаться:

```text
python scripts\tools\validate_map_ids.py
```

Ожидаемый результат:

```text
ID VALIDATION OK
```

Но валидатор нужно постепенно расширить.

---

## 24.1. Уникальность

Проверять:

```text
все id уникальны;
все numeric_id уникальны;
все legacy_id уникальны;
все region.id уникальны;
все macroregion.id уникальны.
```

---

## 24.2. Ссылки

Проверять:

```text
каждый province.region_id существует;
каждый province.macroregion_id существует;
каждый region.macroregion_id существует;
каждый scenario province_id существует;
каждый owner_country_id существует;
каждый culture_id существует;
каждый religion_id существует.
```

---

## 24.3. Согласованность геометрии и паспорта

Проверять:

```text
набор провинций в geometry совпадает с набором в game_data;

numeric_id совпадает;

legacy_id совпадает;

id совпадает;

нет геометрии без паспорта;

нет паспорта без геометрии.
```

---

## 24.4. Иерархия

Проверять:

```text
macroregion провинции совпадает
с macroregion её региона;

нет регионов без макрорегиона;

нет провинций без региона;

нет циклических ссылок;

нет неизвестных родителей.
```

---

## 24.5. Запрещённые поля

В паспорте провинции не должно быть:

```text
owner_country_id
controller_country_id
culture_id
religion_id
population
buildings
zone_id
parents.zone
zone_*
```

---

## 24.6. Формат ID

Проверять регулярными выражениями.

Пример текущего формата:

```regex
^province:[a-z0-9_]+:[a-z0-9_]+:[a-z0-9_]+$
```

Рекомендуемый стабильный формат:

```regex
^province:[0-9]+$
```

Регион:

```regex
^region:[a-z0-9_]+:[a-z0-9_]+$
```

Макрорегион:

```regex
^macroregion:[a-z0-9_]+$
```

---

## 24.7. Удалённые ID

Нужно хранить реестр использованных numeric ID.

Правило:

```text
удалённый numeric_id нельзя выдавать новой провинции.
```

Иначе старый сейв может загрузить совершенно другую территорию.

# 29. Итоговый вердикт

Основная идея архитектуры правильная и подходит для большой глобальной стратегии.

Следует сохранить:

```text
геометрия отдельно;

паспорт отдельно;

состояние сценария отдельно;

страна не входит в ID провинции;

культура и религия находятся в сценарии;

владелец и контролёр находятся в сценарии;

legacy_id сохраняется;

zone полностью удалён.
```

Обязательно улучшить:

```text
1. Отвязать постоянный ID провинции от region_slug и macroregion_slug.

2. Определить region_id источником истины,
   а macroregion_id — вычисляемым полем или валидируемым кэшем.

3. Добавить schema_version и content_version.

4. Добавить map_id_aliases.json.

5. Зафиксировать правила историко-географической классификации.

6. Разделить провинциальные, городские и клеточные здания.

7. Определить единственный источник истины для владельца и оккупации.

8. Использовать JSON как редактируемый источник,
   а плотные числовые индексы и BIN — в runtime.
```

Самая важная правка:

```text
province:<macroregion>:<region>:<province>
```

удобен для чтения, но противоречит идее постоянной личности провинции.

Наиболее надёжный вариант:

```text
province:<numeric_id>
```

Пример:

```text
province:2839
```

При этом историко-географическая принадлежность остаётся отдельными полями:

```json
{
  "region_id": "region:iberia:andalusia",
  "macroregion_id": "macroregion:iberia"
}
```

Так провинция сможет менять классификацию, название, локализацию и сценарное состояние, не ломая сохранения, события и ссылки.
